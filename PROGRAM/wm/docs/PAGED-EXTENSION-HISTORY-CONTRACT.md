# Paged extension history, native v1 and server roots v2

Current v2 backup extension: [Paged backup contract](PAGED-BACKUP-CONTRACT.md) adds compact streaming components, same-physical restore and fresh-target rebasing. The v1-only backup limitations below describe the prior checkpoint; production qualification remains open.

Status: implemented provisional, feature-first. This is an E08 storage slice and an E11 conversion foundation. The bounded server owner contract is now connected under an explicit provisional profile. It does not complete E08, E11, AC03, whole-plugin parity, or host/all-writer qualification.

## Source and preserved meaning

The extension proposal §7.4, §10.4 and §12 requires durable occurrence/result locks independent of the display window, exact lookup without full history residency, preserved fixed outcomes and explicit, verified migration. The existing E06 calculator, rule/permission checks, private projection and legacy seed/anchor policy remain unchanged. No new random sample, biological parameter, model role, provider request or execution permission is introduced.

The profile is `native-single-runtime-readback-v1`. Existing inline history remains the default. The extension recovery screen offers an explicit confirmed “이력 저장 분리” action only outside routed server mode. Each action copies or verifies at most 48 source rows and publishes progress through the existing verified canonical save. It never starts a provider or background migration. A later click resumes. Existing inline behavior remains usable during copying/verifying. If it changed, a new explicitly confirmed attempt retains the prior immutable manifest chain and uses a new source fingerprint.

## Physical layout and bounds

- Canonical lore contains one `lmai_extension_history` row with `wm.extension-history.v1`, scope, event scope, profile, phase, revision, count, limits, root references and migration receipt. The manifest is at most 8,192 UTF-8 bytes. After ready cutover, inline event and lock rows are absent.
- Existing cold owner keys `wm.cold.extension.eh-<SHA256>` contain immutable `wm.extension-history-page.v1` pages. This schema is classified into the existing `cold` domain; its explicit dependencies participate in the existing six-domain inventory closure. No seventh owner/domain or mutable global authority is introduced.
- Immutable AVL index pages store bounded keys and references. Records and pending membership have separate roots. An exact old-event/lock read traverses at most 64 index levels, then only that record's chunks. Pending windows are at most 48 records, using key continuation and a packet prefix for superseding prior pending revisions. The common path does not enumerate all keys, scan the historical source or call the old bundle-wide companion finder.
- Maximum persisted page: 65,536 UTF-8 bytes; chunk: 32,768 decoded bytes; key: 8,192 UTF-8 bytes; decoded logical row: 262,144 bytes. These are explicit versioned storage/consumer limits, not model/calculator defaults. Limits may be lowered, not silently raised for the same manifest. Oversize rows can be stored losslessly in chunks, but ordinary decoding fails explicitly; they are never truncated, treated as missing or automatically recalled from a provider. The raw chunk iterator supports bounded archival reading.
- Zero retained history-page cache. The legacy decoded lock cache stays at its prior 48-entry bound. A pending operation can hold up to 48 decoded rows. This is not a measured whole-plugin RSS bound. Native getItem returns a whole individual page before its byte limit can be checked; a corrupt oversized external value is rejected after retrieval. Writes and explicit legacy conversion start with their already supplied logical rows.
- Previous event versions have immutable predecessor references; each root manifest retains the prior manifest. Original migration versions have a separate retained index. No garbage collection, source deletion or physical-storage quota is claimed; total durable history intentionally grows.

## Write, migration and recovery semantics

Every new page is content-addressed from scope, body and dependencies. Existing differing bytes under the same ID reject. A page is read back before a new root can reference it. Canonical publication occurs through the existing owner and its readback. A rejected page write cannot remove the old inline source or advance its persisted root. A lost canonical acknowledgement remains governed by the existing owner recovery behavior; no extra overwrite retry is invented.

Conversion fingerprints the supplied original history, checks duplicate identities, copies bounded batches, and then compares each stored original's bytes in separate bounded verification batches. Only the ready result omits inline history. Original event/result/lock bytes remain reachable through `legacyRoot` and prior manifests. Non-history lore entries are preserved unchanged, including DLC IDs, seed/anchor values, definitions, versions and unfinished jobs. Already lost pre-window history is not reconstructed. Explicit conversion still scans the already hydrated legacy source to check its fingerprint; it is not a streaming legacy host-read contract.

The migration API returns a prepared candidate; its caller must use verified canonical publication, as the GUI does. Ordinary native get/set plus readback provides neither atomic CAS nor a distributed writer lease. The profile and qualification flags say so. Multi-runtime ownership, concurrent writes, adversarial native mutation, cross-physical adoption and complete crash/restore matrices remain unqualified.

Consumers use the same existing journal operations. They remain synchronous on inline data and become awaited on the paged profile. Normal maintenance, staged roles, semantic-lock consumers, the fictional calculator and pending/retry GUI are connected. Corrupt/missing pages are errors, not absent events. Short display journal trimming cannot remove the cold occurrence/result locks. Public/private projection behavior remains unchanged.

## Server pinned dependency roots v2

Status: implemented provisional, feature-first. The service must explicitly receive `pagedHistoryEnabled: true`; the routed writer must explicitly select `server-pinned-roots-v2`. The assembled runtime accepts this only through the trusted `environment.pagedHistoryProfile` injection. Both defaults remain closed, the host gate still applies, production profiles remain empty, and `runtimeActivation` / `serverActivation` remain false. The GUI does not offer server cutover by default. Existing unselected inline v1 behavior is retained. Selection does not confer real server rights or native/all-writer qualification.

### Durable staged pages

`history/begin` establishes `wm.page-stage-receipt.v1`, bound to physical identity, scope, exact expected canonical head, route generation, writer epoch, stable operation ID/fingerprint and a 300,000-ms expiry. The retained receipt is replayed unchanged. Page writes use `history/stage` with a stable content-derived operation ID and exact fingerprint. Each page is limited to 65,536 bytes and 128 direct dependencies; its content address, origin, payload digest and embedded dependency list are checked. Existing inventory keys and blobs remain immutable. Every successful stage stays in the existing six-domain inventory, including pages never published by a canonical root.

`history/read` reads an exact staged logical ID in bounded chunks through an authenticated retained receipt and a durable head-scoped membership record. It does not list inventory. Expired receipts reject. `history/renew` is an explicit idempotent successor after definitive expiry, with its own deterministic operation identity and the same head/route/epoch. Old receipts and page receipts are retained. Renewed sessions may read prior stage evidence for that exact head. Renewal is single-flight within an owner. Uncertain replies never cause a new page or canonical operation ID to be invented.

Published reads are attempted through the retained pin first. A published read neither starts a staging session nor depends on stage expiry or on the pinned generation still being the current head. A staged miss creates a session lazily; a read/write error never switches to native storage. Cancellation is checked before and after each awaited owner action. Cancellation may leave immutable orphan pages but cannot publish a cancelled canonical candidate.

### Small roots and bounded structural proof

`wm.generation-roots.v2` is separate from `wm.generation-manifest.v1`; it has no full `items` list. It carries at most 32 dependency-root IDs, a 16,384-byte manifest ceiling, and the exact `baseGenerationId` bound to expectedHead. The server creates small immutable `wm.dependency-root.v1` cold records linking the new roots and inherited closure. A v1 predecessor is bridged in bounded groups. This preserves prior history, staged results, lineage and other companions without returning a complete closure to the client. Reset/remove follow their existing epoch/CAS behavior; all previous durable rows remain on disk.

The server builds the closure with SQLite FILE-backed scratch frontier/visited tables and streamed descriptors, retaining no JS archive-wide Map, Set or item array. Each descriptor is limited to 65,536 bytes and 128 dependencies. A streamed, sealed `wm.root-closure-proof.v1` binds generation, manifest digest, root ID, item count, total bytes and ordered descriptor digest. Construction checks cycles, missing descendants, scope, immutable descriptor identity, content addresses and payload hashes. Publication rechecks the complete proof and payloads before the existing transactional head comparison and durable receipt commit.

Authoritative acquire/head/final observations retain full healthy-head certification through streamed closure verification. This work is O(total closure) in time and I/O, not a constant-time certification claim. Individual pinned page reads use exact indexed generation membership and bounded payload reads; they do not re-enumerate the closure. Canonical payload limits and other non-history residency remain their existing separate bounds.

`snapshot/roots` returns the small manifest/proof. `snapshot/closure` returns count- and exact encoded-byte-bounded descriptor pages whose digest can be independently recomputed. `snapshot/find` supplies bounded schema-filtered companion pages, so lineage lookup does not disappear behind a root wrapper. Legacy full-bundle consumers explicitly reject a v2 source rather than returning a false absence. Explicit-profile writes remain v2 after reset/remove, even when no history row is present.

The normal six-domain inventory endpoint includes the small canonical root, every descendant and unreferenced staged/orphan inventory. It remains paged and chunk-readable. No seventh domain, new storage authority or deletion/garbage-collection path was added.

### Canonical uncertainty and retained identity

The existing operation journal stores the bounded root manifest alongside the canonical operation reference. The deterministic canonical intent includes pending companion descriptors. A lost prepare acknowledgement replays the exact idempotent prepare to recover Prepared; a retained prepared operation can then resume publish through current fences and expected-head CAS. Unknown publish outcomes reconcile through the original operation ID/fingerprint after restart. Recovery must match the expected head, candidate operation and bounded dependency roots, or prove that the exact prepared head is already the current observed head with no new companion candidate. Same raw text alone never selects an older sidecar candidate. Ambiguous or changed recovery candidates block explicitly.
