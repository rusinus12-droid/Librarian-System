# Namespace reset physical admission

New pending reset jobs use `memory-suite.namespace-reset-job.v2`. The normal server reset producer captures the existing certified `memory-suite.physical-data-identity.v1` DATA identity by read-only physical read before backup and again before publishing the first epoch fence and pending journal. The job stores the exact 32-character physical ID and contract. Runtime tokens and endpoint URLs do not establish this authority.

Server startup checks a pending job before interrupted-restore recovery, DATA layout or identity creation, schema preparation, runtime-token/signing writes, workers, repository metadata, or diagnostic writes. Namespace reset rechecks the same authority and actual persisted job before reset transactions and catalog clearing. An original physical DATA folder can resume the same job once; canonical filesystem aliases and unrelated token rotation preserve that identity. A byte-identical copy at another physical DATA root cannot resume a destructive job from its source.

Pending jobs with an absent/invalid contract or physical pin, foreign identity, malformed namespace/completion lists, malformed journal, missing seed, or corrupt seed fail closed before startup DATA writes. A present history on an active pending job must be an array of non-null objects with nonblank string IDs; malformed history is refused before reset deletion. Valid old history rows retain their existing contents and need no new physical fields. No missing pin or seed is silently regenerated or rebound to the currently opened folder. Preserve those DATA and journal bytes for a separately authorized recovery review. Startup does not upgrade terminal legacy journal/history bytes, including history shapes that are checked only for active pending jobs.

This changes durable reset admission only. The existing RETRACE public target-all handler, manager plan/execute protocol, backup selection, five namespace ownership, epoch counts, shared SDK, and plugin behavior retain their existing paths. Tests use synthetic Temp DATA and real server SQLite; installed/native GUI, five-plugin refresh/reupload, and all-accessible owner/chat global policy require separate evidence.

Relevant narrow tests are `namespace_reset_physical_admission_test.cjs`, `namespace_reset_runtime_test.cjs`, `namespace_reset_recovery_test.cjs`, and `namespace_reset_all5_composition_test.cjs`. Composition tests require an explicit exact candidate source-pin artifact; the immutable 389 baseline and its copied-pending failure remain separately preserved.
