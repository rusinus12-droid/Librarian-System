# State 선별 제한 제거와 최신값 보존 정책

## 요청과 변경 이유

사용자는 관측한 사실을 상위 16건처럼 선별하지 말고 정본과 Micro 모두 State에 반영하도록 요청했다. 심한 State 누락의 원인 중 하나로 중요도/건수 선별이 의심되어 제한을 제거했다. 선별이 모든 누락의 단독 원인으로 입증됐다는 의미는 아니다. 이 이유를 Micro 검증기와 정본 검증기, 서버 코덱의 코드 주석에 남겼다.

같은 속성이 변경되면 최신 근거의 값을 현재 State에 적용하고 이전 값은 `supersededState[]`에 `status:pending`, `reason:latest_value_preferred`로 보존한다. 값·대상·필드·이전 근거·대체한 근거를 함께 저장한다. 리롤/롤백 복원은 보류값을 무조건 재적용하는 방식이 아니라 선택된 원문·정본 체인을 다시 재생성한다.

## 제거한 선별 경로

- Micro 생성 프롬프트의 16건 지시, 검증 후 상위 16건만 보존하던 정렬·절삭, 64건 입력 개수 제한.
- Micro에 제공하던 원문 인용 후보의 첫 16구간 제한 및 관련 인물/기존 대상 목록의 건수 절삭.
- 정본의 100 entity / 120 fact·binding 개수 제한. 서버 authoritative codec도 같은 계약으로 변경했다.
- 프로필·지식의 32항목 검증/반영/조회 제한과 프로필 수동 편집의 32항목 제한.
- State 인물·관계·세계 목록 및 서사 목록의 보관·정규화 개수 절삭, 사건 최근 60건 제한.
- 서사 구성의 최대 흐름/전환/소재/유지 조건 수와 보완 분석의 첫 12개 항목 및 첫 36개 원문 창 제한.

원문 근거, scope/worldline, 원문 revision/digest, 타입, 불확실성, 참조 무결성, 순환 관계 및 저장 원자성 검증은 유지한다. Provider 출력/문맥 한도와 전체 artifact 바이트 검증은 별개의 자원 보호다. 이러한 실패를 중요도 선별로 숨기지 않으며 기존 승인 기억을 보존한다. UI 페이지 크기나 recall 문맥의 크기를 무제한으로 바꾼 작업은 아니다.

## 건수 제한 외의 누락 보강

기존 선호·경계 보완 호출을 외모·배경·성격·말투·습관·능력·목표·감정·지식, 명시적인 관리/소유/보유 관계와 이전 과제의 종결까지 검토하도록 확장했다. 새 호출을 계속 추가하는 대신 기존 보완 호출의 범위를 넓혔다.

같은 인용이 머리색과 눈 색을 함께 증명할 때 하나를 중복으로 버리던 인용 중복 판정을 수정했다. 동일 필드의 동일 값만 중복으로 취급한다. 대명사 묘사는 같은 원문 창에서 가장 가까운 이름과 주체를 확인할 수 있을 때만 연결하며, 선호·경계의 발화자를 추측해서 연결하지 않는다.

Micro가 이미 관측한 한 문장이 위치뿐 아니라 명시적인 습관/목표/색상 외모도 뒷받침할 때 해당 State intent를 추가 보완한다. 원래 관측은 그대로 남긴다. 습관은 `평소처럼/매일/습관적으로/항상` 등의 명시적 표현, 목표는 `목표/지켜야/보호해야` 표현, 외모는 인용 속의 명시적 머리·눈 색상에 한정한다. 주체·원문 위치·근거가 확인되지 않거나 소문/불확실성으로 분류된 경우에는 임의로 확정하지 않는다. 이는 모든 자연어를 완전하게 분류하는 의미 검증기라는 주장이 아니다.

반복 출력으로 생성이 잘렸을 때는 독립 사실을 빼지 않고 중복 반복을 억제하도록 1회 재시도한다. 실패한 Micro 배치를 실측 성공으로 집계하지 않도록 실측 도구도 수정했다.

## 최신값 정책 검증

정본은 검증된 원문 안의 인용 위치로 선후를 판단한다. JSON fact 순서가 뒤집혀도 원문에서 나중에 나타난 값이 현재 State가 된다. 같은 위치의 구분 불가능한 제안은 검증된 최신 제안 순서를 사용하고 이전 값을 보류 이력에 보존한다. 출처를 알 수 없는 제안을 최신이라는 이유만으로 승인하지 않는다.

이전 단일값, 같은 topic/scope의 교체된 collection 항목, 삭제·해제된 값, 서사 압력/구조/이야기 상태 변경을 보류 이력으로 보존한다. 의미가 같은 값의 단순 재확인은 기존 provenance를 유지한다. 서로 독립적인 지식·특성은 계속 누적한다.

`libra_state_latest_value_retention_test`는 아래를 확인한다.

1. 원문 순서와 반대로 제안된 '누워 있다/서 있다'에서 현재는 '서 있다'.
2. 이전 '앉아 있다/누워 있다'는 근거가 있는 pending 이력으로 남는다.
3. 서사 압력도 최신값이 적용되고 이전 압력은 pending으로 남는다.
4. 저장·조회·재생성이 동일하다.
5. T5 롤백에서 이전 상태와 압력이 복원되며 이후 정본/원문 근거도 보존된다. 호스트 대화가 여전히 T10이면 그 역사적 State를 응답의 현재 권위로 위장하지 않는다.

## 정적/격리 실행 검증

관련 35개 스크립트가 통과했다. 플러그인 단독·미러·서버 모드 회귀, source 보존, State 재생성, GUI 모델, typed server writer, Micro→정본 종합을 포함한다.

- Micro 17·64·65·1000개의 유효 claim을 건수 선별 없이 검증한다.
- 정본 120개 초과 fact, 프로필/지식 각각 40개, 사건 145개, 흐름 30개가 저장·조회·재생성을 통과한다.
- 보완 분석 27개 외모 항목과 명시적인 목표·습관·관리 관계를 보존하고 지어낸 인용은 거부한다.
- 한 관측 문장이 위치와 습관을 함께 반영하고, 한 문장의 머리색/눈 색을 각각 반영한다.

전체 수백 개 회귀를 다시 통과시킨 결과는 아니다. 별도 `authority_libra_typed_source` suite는 Windows `fsync`의 EPERM으로 재시도 후에도 실행하지 못했다. 실제 HTTP/SQLite를 사용하는 관련 writer 회귀와 codec 직접 검증은 통과했다. 기존 baseline에서도 재현된 Recall closure/reopen 문제를 해결했다고 주장하지 않는다.

## 이번 보강 회차의 실제 모델 요청

대상은 로그인된 로컬 Ollama 경유 `deepseek-v4.1-flash:1017-cloud`, 응답 모델은 `deepseek-v4.1-flash:1017`이다. 기존 승인 원문 T1~10·선택 로어 3건과 개인정보 없는 합성 자료를 격리 저장소에서 사용했다. 실제 사용자 DB는 읽기 전용이다.

## 실제로 확인한 결과

### 건수 제한을 넘는 양성 자료

동시에 제시한 상자 상태 **24/24**가 Micro와 정본 State에 모두 남았다. 머리색·눈 색·습관·목표·선호까지 정답 체크리스트 **29/29**가 충족됐다. Micro 제안 28개인 것은 머리색·눈 색이 한 외모 문자열로 묶였기 때문이며, 사실 한 가지가 빠진 것이 아니다. 정본 보류 0, 재생성 동일.

### 실제 원문

- 전체 T1~10 실행에서 Micro 저장 claim **116→180**, State intent **13→34**로 늘었다. 다른 모델 응답 사이의 비교이므로 증가분 전체를 선별 제거의 단독 효과로 해석하지 않는다.
- 전체 실행에서 세아의 검은 머리/붉은 눈, 세희의 붉은 눈, 방문 요구 이행에 대한 closedThreads 1건이 기록됐다.
- 보강 후 T1~5 정본에서 세희의 **딸들 보호 목표와 평소 아침 준비 습관**이 각각 저장됐다.
- T3 단독 Micro에서 모델 관측 37개에 원문에 근거한 State intent 2개를 추가하여 39 claim을 보존했다. 위치만 남던 관측에서 습관과 보호 목표도 직접 State에 들어갔다.
- T4 단독 Micro에서는 원응답 41 claim 중 잘못된 계약 1개를 거부하고, 관측된 외모의 State intent 1개를 추가해 유효 claim 41개를 보존했다. 세아의 붉은 눈동자가 appearance에 반영됐다.
- 전체 T1~10의 저장 자료를 최종 코드로 모델 호출 없이 재생성해 이전 값의 pending 이력 **8건**을 확인했다.

이 결과들은 서로 다른 보강 단계와 범위의 실행이다. 최종 코드로 전체 T1~10을 다시 생성한 한 번의 100% 무누락 결과로 합산하지 않는다. 마지막 Micro 단독 실행은 앞선 모든 턴의 Micro를 생성한 전체 coverage 검사도 아니다.

## 남아 있는 검증/품질 항목

전체 T1~10 실행의 정본에는 위치 fact의 근거 격리 1건과 thread 참여자 불일치 1건이 보류됐다. 카페 managerRef도 여전히 0이다. 이 항목을 채워졌다고 보고하지 않는다. 어떤 값이 background에 서술됐다는 이유만으로 현재의 관리 관계를 자동 확정하지 않는다.

건수 선별 제거는 **저장량 때문에 유효 사실을 버리지 않게 하는 변경**이다. 모델이 아예 관측하지 못한 사실이나 잘못 분류한 내용까지 모두 해결됐다는 뜻이 아니다. 최종 코드 전체 원문의 추가 실측은 기존 40회 상한을 모두 사용했으므로 별도 요청 예산 승인이 필요하다.

실제 설치 RisuAI UI에서의 검증, 설치 파일 교체, 실사용 기억의 재분석, 커밋·푸시는 하지 않았다. 이전에 선별돼 저장되지 않았던 사실은 소스가 남아 있어도 새 코드 적용만으로 자동 복원되지 않으므로 원문 재분석이 필요하다. 원문·모델 원응답·격리 저장소는 `.development/`에 보관하며 커밋 대상이 아니다.
