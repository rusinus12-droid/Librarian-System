# LIBRA 상설 그래프 게시 복구 및 실제 저장본 탐색 — 2026-11-10

## 입력과 확인 범위

사용자 제공 `libra-debug-2026-11-10 (5).json`은 LIBRA 2.6.41 / 서버 0.5.1을 기록한다. `durableGraphPublication`은 null이고 자동 구축의 마지막 결과는 시작 시 채팅 문맥을 읽지 못해 보류된 기록이다. 수동 구축의 INDEX_BUDGET 및 서버 점검 실패 상세는 이 파일에 남아 있지 않다. 따라서 실제 채팅의 어느 자료가 몇 바이트로 초과했는지는 이 파일로 단정할 수 없다.

구조 화면의 구현 오류와 게시 실패 경로는 현재 소스를 검사하고 합성 데이터로 재현했다. 실제 사용자 채팅·실행 중인 서버·설치된 플러그인을 변경하거나 검증한 것은 아니다.

## 원인과 수정

### 구조 화면

기존 `inspectMemoryGraphStructure`는 `readMemoryGraphProjection`을 호출했다. 게시된 상설 그래프의 root/manifest를 읽지 않으므로 상설 그래프가 없어도 원본으로 만든 임시 구조가 보였다.

이를 실제 corpus reader로 바꿨다. 게시된 root와 manifest, 내용 해시로 고정된 projection을 읽으며 게시본이 없으면 `LIBRA_GRAPH_CORPUS_MISSING_GENERATION`으로 안내한다. 오래된 원본 세대도 임시 구조로 대체하지 않는다. DTO와 화면에 실제 게시 세대·저장소·묶음 위치를 표시한다. 큰 forest는 한 묶음씩 넘기며, 다음 페이지 요청의 게시 세대를 검증한다. 다른 묶음으로 향하는 간선은 별도 개수를 표시하고 현재 묶음의 그림에서 생략한다. 노드 식별자는 충돌할 수 있는 12자 접미사 대신 전체 내부 노드 ID를 사용한다. 표시 데이터에는 원본 검증 권한이나 binding을 전달하지 않는다.

### INDEX_BUDGET에서 멈추던 게시

64개 이하 window인 채팅은 먼저 기존 단일 corpus를 구축한다. 이 시도가 `index_budget`으로 실패할 때 forest 분할로 전환하는 오류 목록에 그 이유가 빠져 있었다. 인덱스 바이트 예산과 projection·source proof 바이트 예산이 같은 오류를 내므로 작은 채팅에서도 발생할 수 있다.

분할 전환에 이 예산 초과를 포함하고, 한 window 자체가 너무 크면 native reader의 window 폭도 20→10→5→2→1처럼 줄인다. 개별 예산은 올리지 않으며 항목을 잘라 게시하지 않는다. 한 레코드도 예산 안에 들어오지 않으면 실패를 유지한다. 성공한 폭은 게시 manifest에서 이후 증분 구축이 이어받고, checkpoint 자동 재개의 옵션에도 유지한다. `maxShardsPerStep` 같은 forest 전용 옵션을 단일 corpus의 정책 검사에 넘기던 별도 오류도 수정했다.

표시와 디버그 JSON에 수동 구축 실패의 코드·서버 오류·HTTP 상태·예산 단계·실제 바이트·한도·페이지 수를 남긴다. projection/source proof/인덱스 테이블의 예산 초과를 구분할 수 있다.

### 서버 점검

서버의 점검 게이트는 graph-lifecycle 라우트를 실행하기 전에 503을 반환한다. LIBRA SDK의 점검 재시도 목록에 이 라우트가 없어 lease 획득이 곧바로 실패했다. 해당 라우트도 기존의 유한한 대기·재시도에 포함했다. 원래 요청 ID를 유지하며, 점검이 계속되면 실패를 반환하고 기존 게시 root를 보존한다.

## 검증

- 기존 HEAD의 corpus 모듈로 신규 작은-corpus 시험을 실행하면 `LIBRA_GRAPH_CORPUS_INDEX_BUDGET`이 재현된다. 같은 입력의 수정본은 분할 게시, 재시작 후 저장된 라우팅 검색, 자료 변경 후 증분 게시 및 변경된 항목 검색을 통과한다.
- 하나의 큰 native window에서도 예산을 올리지 않고 폭을 좁혀 게시하고, 이후 증분 구축이 같은 폭을 사용하며 기존 묶음을 재사용한다.
- 실제 배포 플러그인 코드를 VM에서 실행하고 HTTP/SQLite 서버에 연결하는 신규 런타임 시험을 사용한다. RisuAI 호스트와 모델 응답만 fixture다. 서버 점검 503 두 번 뒤 같은 lease 요청으로 게시하고 상설 검색을 완료한다. 점검이 지속되면 기존 root를 그대로 둔다.
- 11턴 및 17턴 합성 채팅에서 낮춘 인덱스 예산으로 분할 게시한 뒤 `corpusMode: required`로 검색한다. `durable_common_index` 및 `routed_durable_shards` 경유, 목표 Micro 근거 전달, 같은 근거의 반복 검색, 재시작 후 저장본 검색, 증분 구축의 재사용을 검사한다.
- 11턴 예시에서 원본 재투영 검색은 요청 168회, 첫 상설 검색은 약 160–161회, 반복 상설 검색은 125회였다. 요청 수는 실행 타이밍에 따라 조금 다르다. 이는 동일 합성 데이터의 요청 수 비교이며 실제 사용자 환경의 지연 개선 배수는 아니다.
- 17턴의 원본 전체-window 비교 경로는 기존 64-key 소스 pin 한도로 실패한다. 이 경로의 완료 시간이나 최종 근거 동등성은 측정하지 않는다. 상설 검색의 성공·목표 근거 전달은 독립적으로 검사한다. 이 pin 한도를 완화하는 변경은 하지 않았다.
- 17턴은 5묶음으로 게시했다. 첫 상설 검색/반복 검색의 요청 수는 한 실행에서 218/170회, 최종 실행에서 221/169회였다. 두 실행 모두 목표 근거 전달, 증분 재사용, 재시작 후 저장 색인 검색을 통과했다.
- 상설 그래프가 없을 때 구조 화면의 API가 거부되는지, 게시 후 읽을 수 있는지, 페이지 간 게시 세대 불일치를 거부하는지, forest의 모든 묶음을 중복·누락 없이 순회하는지 검사한다.

최종 관련 7개 파일의 60개 시험이 모두 통과했다. LIBRA 내장 graph 모듈과 원본 동기화, LIBRA SDK 원본 일치, JavaScript 문법 및 `git diff --check`도 통과했다. 전체 저장소 회귀와 실제 RisuAI UI 시험은 수행하지 않았다.

사용자의 요청에 따라 main에 이 패치·시험·검증 기록을 함께 커밋한다. 측정용 `.development/`는 커밋에서 제외한다. 설치·서버 교체·푸시·배포는 하지 않았다.
