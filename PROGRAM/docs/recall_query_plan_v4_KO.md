# 요청 계획을 공유하는 리콜

적용: HAYAKU 3.0.66, Flashback 1.0.45. 공통 특징: `recall_query_plan_v4`.

현재 사용자 입력의 출처를 기존 호스트 규칙으로 선택한 뒤, 길이를 제한하기 전에 요청과 참고 배경을 분리한다. 명시한 이름·표현과 문맥 참조를 따로 보존한다. Flashback은 공개 인물 메타데이터의 파생 사전을 기존 샤드 요약에 저장하고, 샤드 선택 전에 요청 계획을 확정한다. 후보를 읽은 뒤 대상 목록을 새로 만들지 않는다. HAYAKU는 자신의 인물 사전 스냅샷을 사용하며 지식 접근 판정은 기존 소유자 경계를 유지한다.

## 달라진 동작

- 긴 참고 자료 뒤의 질문을 먼저 배정한다. 명확한 블록 인용과 코드 블록의 이름이 현재 질문의 대상 한도를 소모하지 않는다.
- `민수의 약속은 언제고 그의 약속 장소는?`의 대상은 민수이며, `그의`는 별도 문맥 참조다. 대상 충족률의 분모가 선택과 발췌 사이에서 바뀌지 않는다.
- `붉은 수정구슬은 어디에 있어?`에서 `붉`을 독립 대상으로 승격하지 않는다. 수식어는 일반 검색 단서로 남는다.
- 확인 가능한 대상 표현이 있는 샤드는 기존 읽기 한도 안에서 우선 배정한다. RRF 후보 절단과 최종 선택에서도 아직 전달하지 못한 다른 대상을 우선 고려한다.
- 발췌 결과에는 요청 계획 ID, 대상 ID, 발췌 문자열과 저장 기록 문자열 각각의 UTF-16 일치 좌표를 기록한다. 두 좌표계는 구분한다. 저장 원문을 요약문으로 바꾸지 않는다.
- 대상 표현이 발췌에서 빠진 경우(`target_evidence_omitted`)와 전달 예산에 들어가지 않는 경우(`not_delivered_budget`)를 구분한다.
- 검색 휴리스틱을 끈 설정에는 새 강제 우선순위를 적용하지 않는다.

## 저장·호환성

새 정본 저장소, 기억 재분석, 자동 재임베딩, 추가 생성 모델 호출은 도입하지 않는다. 원문·벡터·세계선/접근 적격성 검사는 기존 소유자에게 남는다. 파생 자료는 HAYAKU 요청 캐시 v4, Flashback sparse v5 / shard v7 / memory lane v4로 구분한다.

Flashback의 공개 인물 사전은 기존 정상 저장·인덱스 유지보수 시 생성한다. 구버전 요약에 사전이 없으면 불완전한 사전이라고 표시하고 원문 표현으로 검색한다. 누락된 사전을 채우려고 리콜 도중 사용자 기억을 재분석하거나 저장하지 않는다. 기존 구형 인덱스 전체 읽기 대체 경로는 유지한다.

## 범위와 한계

이 방식은 단계 간 불일치와 확인된 누락 원인을 고친다. 모든 자연어 문장의 의미, 표시 없는 인용 배경, 동명이인, 모든 굴절형을 완벽하게 판별하는 형태소 분석기는 아니다. 불명확한 별칭은 인물 ID로 인증하지 않는다.

대상 슬롯은 32개, 요약당 인물 연결은 256개, 요청 사전은 4,096개로 제한한다. 별칭은 연결당 32개이며 긴 이름·별칭이나 한도 초과는 사전 불완전으로 남긴다. 기존 읽기·후보·주입 상한은 유지한다. 알려진 대상이 예산보다 많거나 요약에 표현이 없으면 전체 발견을 보장하지 않는다. `scopeCoverage: partial`과 `catalogComplete: false`는 기억이 없다는 뜻이 아니다. 읽기 완료·적격성 검사·실제 전달 여부는 각각 구분해야 한다.

입력 예산은 기본 6,000자를 유지한다. 질문 우선의 제한 문자열과 원문 대응 캐시는 최대 8개·합계 524,288자, 개별 원문 262,144자 이내다. 요청 계획 캐시는 최대 32개이며 입력·사전·스코프/커밋 등의 바인딩 값으로 구분한다. 캐시가 없거나 제한을 넘으면 보존된 제한 입력만 해석하며 이전 요청의 원문을 가져오지 않는다.

회귀 검사는 모의 호스트와 로컬 hash 임베딩으로 실행한다. 실제 RisuAI와 외부 제공자, 사용자 기기 성능 검증은 별도다.
