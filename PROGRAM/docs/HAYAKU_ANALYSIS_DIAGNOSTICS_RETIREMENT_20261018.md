# HAYAKU 실패 진단 정리 — 2026-10-18

기준은 main `3d6a52a`, HAYAKU 3.0.151이다. 이번 변경은 3.0.152이며, LIBRA·Flashback 및 공통 SDK 구현은 변경하지 않는다.

## 문제와 판정

‘실패 후보 수리’ 화면에는 채택·직접 수정·AI 재분석 버튼이 있었지만, 연결된 해결 API는 이미 퇴역하여 항상 거절했다. 실제 복구는 Recovery Journal의 원문을 이용하는 누락 턴 생성 경로다. 실패 전문을 지워도 누락 복구·콜드스타트 재시도·이미 저장된 부분 기억의 검색이 동작함을 합성 모델 경계에서 확인했다.

전용 실패 화면과 모든 실패 전문의 상시 보관을 퇴역시킨다. 원문, 검증된 부분 기억, 검증 후 저장 대기 중인 후보와 정상 체크포인트는 보존한다.

## 기본 기록과 선택적 상세 보관

- 기본 모드에서는 실패 턴·시각·종류·원인·관측 호출 수·부분 저장 결과만 작업 로그에 남긴다. 별도의 실패 전문 index/manifest/chunk를 새로 쓰지 않는다.
- 실패 요약은 현재 실행 전체에서 최근 50건으로 제한하고 현재 채팅에 해당하는 항목만 조회한다. 기존 작업 로그의 상한과 복구 실행 기록의 저장 정책도 유지한다. 요약은 영구 실패 이력 데이터베이스가 아니다.
- 기존 **디버그** 설정을 켰을 때만 원문·모델 응답·후보가 포함된 상세 분석을 보관한다. 한 건 최대 20만 자, 채팅별 최신 10건·총 100만 자 이내다. 단위는 UTF-16 문자열 길이다.
- 상세 보관 상한은 이번 버전의 `debug_recent_v1` 기록에 적용한다. 새 기록이 들어오기 전에 오래된 해당 기록을 검증된 삭제 경로로 정리한다. 삭제 확인이 실패하면 기존 기록을 복원하고 새 상세 기록을 생략한다. 초과 크기의 단일 기록도 저장을 생략한다.
- 상세 저장 실패의 세션 임시 보관에도 건수·총 길이 상한을 적용한다. 상세 보관 실패가 부분 기억이나 정상 복구 결과를 실패로 바꾸지는 않는다.
- 이전 버전의 기록은 일괄 삭제하지 않는다. 기존 읽기·삭제 API와 스코프 저장소 관리 경로를 유지한다.

디버그 설정은 기존의 디버그 정보 기능도 계속 제어한다. 상세 보관의 의미와 크기 제한을 설정 화면에 표시한다.

## GUI와 내보내기

복구 탭에서 ‘실패 후보 수리’와 채택·편집·재분석 버튼을 제거했다. 누락 복구, 직접 원문 재분석, Cold Start는 유지한다. 과거 `failed_recovery` 화면으로 이동하는 요청은 일반 복구 화면으로 연결한다.

상세 진단은 **작동 기록 → 진단 · 내보내기 자료**에 모은다. ‘최근 상세 진단 읽기’는 사용자가 눌렀을 때만 최근 10개 보관 기록을 읽으며 모델을 호출하지 않는다.

일반 디버그 JSON은 실패 전문을 자동으로 읽거나 포함하지 않는다. ‘내보내기에 보관된 상세 분석 포함’을 사용자가 선택한 경우에만 포함한다. API는 `activityLog.snapshot({includeAnalysisDetails:true})` 또는 같은 옵션의 `activityLog.export`를 제공한다. 기본값은 false다. 상세 JSON에는 원문과 모델 응답이 포함될 수 있음을 화면에 표시한다.

`recovery.failedAnalysis.summaries()`는 현재 채팅의 세션 요약을 반환한다. 기존 `list/read/delete`는 보관 자료 관리용으로 유지하고, 퇴역된 `resolve`는 계속 거절한다.

## 실제 복구와의 분리

누락 자격 검사와 복구 상태 조회는 실패 진단 인덱스를 읽지 않는다. 이전 인덱스가 손상되거나 읽히지 않아도 Recovery Journal 원문으로 복구할 수 있다.

부분 기억 저장은 상세 진단 저장보다 먼저 독립적으로 실행한다. 전용 쓰기 큐로 동시 저장의 갱신 유실을 막으며 진단 쓰기 큐와 분리한다. 부분 기억의 원문·세계선·본문 검증과 물리적 저장 재조회는 유지하며, 진단이 생략되거나 실패해도 저장된 정상 항목을 잃지 않는다. 반대로 부분 기억의 저장 실패를 성공으로 표시하지 않는다.

복구 후보가 유효한 경우에도 상세 진단의 영구 보관을 성공 조건으로 요구하지 않는다. 실제 원장 채택·저장 재조회는 기존대로 필요하다. afterRequest 자동 복구, 사용자 누락 복구, Cold Start의 호출 예산과 검증 규칙은 변경하지 않는다.

## 검증과 한계

`hayaku_analysis_diagnostics_retirement_runtime_test.cjs`는 다음을 제품 플러그인과 DOM에서 실행한다.

- 기본 실패에 상세 저장 키가 생기지 않고 원문·실패 응답 없는 최근 50개 요약만 남는다.
- 기존 진단 인덱스 읽기를 강제로 실패시켜도 상태 조회·새 원문 기반 누락 복구·원장 저장이 완료된다.
- 디버그 꺼짐/켜짐 모두 진단 인덱스 손상과 독립적으로 부분 기억을 저장·검색한다.
- 같은 원문에 결속된 부분 기억을 동시에 저장해도 서로의 정상 항목을 잃지 않는다.
- 상세 보관은 물리적으로 재조회되며, 일반 내보내기는 전문을 제외하고 명시적 선택만 전문을 포함한다.
- 상세 건수·총 길이 제한, 단일 초과 기록 생략, 이전 기록 보존, 정리 중 오류의 원상복구를 확인한다.
- 실제 GUI 셸에 실패 수리 탭·버튼이 없고 누락 복구 버튼과 로그의 선택적 상세 조회가 남는다.

기존 상세 보관·삭제·원문 진단을 검사하는 시험은 디버그 보관을 명시적으로 켜서 실행한다. 원문 근거·부분 수용·Cold Start의 제한된 재시도·다른 세계선의 후보 거부·저장 응답 유실·세 저장 모드·설정 저장 검사를 함께 실행했다. 관련 27개 시험 파일이 통과했으며 전체 프로젝트 회귀 스위트를 실행한 결과는 아니다.

이번 검증은 합성 모델 출력과 검증용 호스트/DOM을 사용했다. 실제 공급자 모델을 재호출하지 않았으며 실제 사용자 RisuAI 앱, 운영 성공률 또는 성능 개선을 실측한 결과는 아니다.
