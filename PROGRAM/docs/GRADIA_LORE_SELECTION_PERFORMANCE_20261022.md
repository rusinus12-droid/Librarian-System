# GRADIA 대량 로어북 선별 계측과 개선

날짜: 2026-10-22 · GRADIA `0.26.5`

## 계측 방법

`tools/rag_eval/gradia_lore_selection_bench.cjs`로 실제 GRADIA.js를 테스트 호스트에서 돌렸다. 모델 응답은 가짜다. 캐릭터 로어북 N개를 합성했으며, 항목마다 다른 항목 3개를 언급하므로 재귀 활성이 연쇄로 일어난다. 대형 월드북에서 흔한 구조다. 4단계 경량 파이프라인으로 4턴을 실행했고, 단계별 함수는 소스 변환으로 감싸 시간을 쟀다. 표의 값은 2~4번째 턴의 중앙값이다. 클라우드 컨테이너 Node 22, 단일 스레드에서 측정했다.

선별은 요청마다 새로 한다. 직전 요청의 로어 스냅샷은 재사용하지 않는다(다른 플러그인이 직전에 로어를 바꿨을 수 있기 때문).

## 원인과 수정

모든 수정은 결과를 바꾸지 않는다. 확인 방법은 아래 "동일성 확인"에 있다.

1. **재귀 키 활성의 제곱 비용** (`activeRisuLorebooks`, `loreKeyMatchesSearchMessages`)
   - 원인: 최대 12회의 재귀 패스마다, 아직 활성되지 않은 모든 항목이 지금까지 활성된 모든 항목의 본문을 처음부터 다시 검색했다. 키는 메시지마다 다시 정규화했다.
   - 수정 ①: 키 정규화를 키당 한 번으로 줄였다.
   - 수정 ②: 재귀 검색을 증분화했다. 각 항목은 직전 검사 이후 추가된 재귀 본문만 찾는다. 1차 키는 맞았지만 조건 키(selective·추가·제외)에서 탈락한 항목은 예전처럼 같은 지점부터 다시 검사하므로, 다음 패스에 조건이 충족되면 똑같이 활성된다.
   - 수정 ③: 메시지별 2글자 쌍 집합으로 사전 거름을 둔다. 키의 공백 제거형을 이루는 글자 쌍이 모두 메시지에 있어야만 부분 문자열 검사를 한다. 정규식 키와 full-word 키는 그대로 검사한다.
2. **퍼지 정체성 점수의 캐시 붕괴** (`loreJaccardTokenSimilarity`)
   - 원인: 질의 토큰 × 항목 토큰 쌍 캐시가 FIFO 5,000개라 대형 로어북에서 계속 밀려났다. 캐시를 놓칠 때마다 두 토큰의 문자 n-gram을 새로 만들었다.
   - 수정: 토큰별 n-gram 키 집합을 메모하고, 쌍 캐시를 200,000개로 늘렸다.
   - 두 캐시 모두 한도에 닿으면 통째로 비운다. 한 개씩 가장 오래된 키를 지우면 V8 Map에 삭제 구멍이 쌓이고, 이후 `keys().next()`가 매번 그 구멍을 건너뛰어야 해서 느려진다. 실제로 1만 개에서 이후 턴이 첫 턴보다 2.6배 느려졌다.
3. **MMR 선택의 O(n·k²)** (`loreAdaptiveSelect`, `loreMmrSelect`)
   - 원인: 매 선택 단계마다 남은 후보 전부가 이미 선택된 항목 전부와 유사도를 다시 계산했다.
   - 수정: 선택 목록은 늘어나기만 하므로, 각 후보가 이전 평가 이후 새로 선택된 항목과만 비교하게 했다. 최대값과 `similarTo`(첫 최대 항목)는 같다.
4. **단계 뷰 중복 생성** (`runPipeline`)
   - 원인: 캐시 계획이 단계별 미리보기 뷰를 만든 뒤 `prepareStage`가 같은 뷰를 다시 만들어, 뷰 생성이 요청당 8회였다.
   - 수정: `prepareStage`가 같은 입력으로 만든 미리보기의 `recent`와 뷰를 넘겨받아 4회로 줄였다. 뷰가 읽지 않는 설정 두 개(외부 근거 세션, 캐시 사용 여부)만 다르다.

## 동일성 확인

- 무작위 후보 400세트로 `activeRisuLorebooks` 출력을 HEAD와 바이트 단위로 비교했다. selective·보조·추가·제외 키, 정규식, full-word, 재귀 끔, `dontSearchWhenRecursive`, 항상 활성, scan depth, 짧은 키와 빈 키를 섞었고, 활성 항목 합계 13,260개가 모두 같았다.
- 실제 파이프라인에서 로어 50·100·300·1,000·3,000개로 HEAD와 비교했다. 네 단계의 참조 패킷·선택·포장 hash, 공유 선별 메타, system 프롬프트, user 프롬프트(run ID·hash 정규화 후)가 모두 같았다.
- `tests/gradia/lore-activation-scale.test.cjs`
  - 조건 키 재검사 경로를 확인한다. 순진한 증분 구현이면 실패하도록 구성했다.
  - 2,000개 연쇄 활성의 상한도 확인한다. 이 합성 자료에서는 변경 전 2.0초, 변경 후 0.8초라 회귀 방지용 느슨한 상한일 뿐이다.

## 남은 비용

- 1만 개 기준으로 스냅샷·키 활성 11.9초, 후보 풀 8.8초가 남는다. 재귀로 거의 전체가 활성되는 자료에서는 키 검사가 여전히 "항목 수 × 활성 본문" 규모로 커진다. 더 줄이려면 다중 패턴 검색(Aho-Corasick 등)으로 바꿔야 한다.
- 로어 단위 전문 색인 캐시(최대 4,096)와 재순위 특징 캐시(최대 768)는 1만 개 로어북에서 매 요청 다시 계산된다.
- 실제 RisuAI·휴대폰 브라우저에서는 측정하지 않았다. 일반적으로 이 컨테이너보다 느리다.
