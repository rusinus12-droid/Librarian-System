# LIBRA·HAYAKU Other Ax 스트림 응답과 호출 큐 보호

기준은 main `1fedf52`, LIBRA 2.3.170 / HAYAKU 3.0.153이다. 수정 버전은 LIBRA **2.3.171**, HAYAKU **3.0.154**이다. 공통 실행 계약 SDK와 Flashback은 변경하지 않는다.

## 문제

RisuAI `runLLMModel`은 플러그인 제공 모델의 스트림을 `{type:'streaming', result:ReadableStream}` 형태로 반환할 수 있다.

HAYAKU는 응답 자체의 `getReader`만 검사하여 객체에 담긴 스트림을 빈 응답으로 처리했다. 스트림이 열린 상태에서 다음 요청이 공급자에 전달됐다. LIBRA는 일반 `result` 스트림은 처리했지만, 앞선 필드의 문자열을 먼저 반환하거나 `type:'fail'`을 먼저 처리하면 함께 담긴 스트림을 놓쳤다.

수정 전 소스로 새 회귀 검사를 실행해 LIBRA의 문자열·스트림 혼합 응답과 HAYAKU의 `result` 스트림에서 다음 호출이 너무 일찍 시작됨을 확인했다.

## 수정

- 두 제품 모두 일반 문자열 또는 실패 응답을 처리하기 전에 응답 자체와 지원하는 응답 필드의 스트림을 먼저 확인한다.
- 동일 스트림 객체의 중복 참조는 한 번만 읽는다. 여러 스트림은 각각 비우며, 하나가 종료되거나 읽기 오류가 나도 나머지 스트림이 끝날 때까지 물리 큐를 유지한다.
- 기존 `drainUnverifiedStream`을 사용한다. 미검증 본문·추론은 누적하거나 기억으로 채택하지 않으며, 정상 EOF에서도 `UNVERIFIED_STREAM_ROUTE`로 거부한다. 읽기 오류도 실패로 처리하고 reader 잠금을 해제한다.
- 스트림과 정상 문자열이 함께 있어도 문자열을 대신 채택하지 않는다. 실패 객체에 담긴 스트림도 정리 전에 무시하지 않는다.
- 사용자 취소나 논리적 기한 초과로 호출자가 먼저 돌아가도 물리 큐는 스트림 종료까지 유지한다. 다음 요청은 이후에만 제출한다. API 응답 객체가 먼저 반환됐다는 이유만으로 물리 작업 완료로 판단하지 않는다.
- HAYAKU의 스트림 거부 진단은 실제 호스트 호출이 제출됐음을 기록한다. 원시 문자열 등 Error 이외의 값으로 스트림 읽기가 실패해도 거부 오류를 생성한다.

Other Ax의 모드, 플러그인 모델 허용 설정, 호스트 소유 모델 선택, 호출 예산 및 자동 재시도 정책은 유지한다. 호스트가 스트림을 끝내지 않으면 물리 큐는 계속 점유된다. 논리적 취소를 물리 요청 종료로 간주하지 않는다.

## 검증

`otherax_wrapped_stream_queue_runtime_test.cjs`는 각 제품에서 다음을 검사하는 22개 실행 사례를 포함한다.

- 루트 스트림, `result` 스트림, 문자열·스트림 혼합, 실패 응답, 동일 스트림 중복 참조.
- 여러 스트림, 일부 읽기 오류 및 Error 이외의 읽기 오류. 모든 스트림의 종료 전에는 다음 공급자 호출이 시작되지 않는다.
- 취소·기한 초과 이후에도 유지되는 물리 큐, 늦게 도착한 스트림 본문의 거부, 이후 별도 요청의 정상 실행.
- 공개 연결 시험의 제출 여부·오류 표시·호출 1회 및 기억 쓰기 없음.

별도로 RisuAI upstream `e773240bfab72f3704f3efa52722ec7d105cdcf3`의 실제 API·모델 선택·플러그인 공급자 함수와 두 제품을 연결했다. 실제 호스트 함수가 스트림을 반환한 후 첫 스트림 EOF 전까지 공급자 호출은 1회였고, 종료 후 첫 요청은 `UNVERIFIED_STREAM_ROUTE`로 거부되며 다음 별도 요청은 성공했다.

이 연결 검사는 TypeScript AST로 추출한 실제 호스트 함수를 사용하되 데이터베이스·공급자 응답은 통제된 구현으로 대체했다. 실제 사용자 앱의 RPC/IPC 또는 유료 외부 모델을 실행한 결과는 아니다. 원본 모델 키나 사용자 채팅을 사용하지 않았다.

기존 Other Ax 호출·정본 저장 대기·복구 근거·직접 원문 재분석·검증된 직접 HTTP 스트리밍 경로와 배포 메타데이터를 포함한 19개 검사 파일이 통과했다. 실제 Full/Min 빌드 6개에서 공통 호출 예산과 작업 프로필을 확인했고, 두 제품의 Full/Min 공개 연결 시험 4개에서 스트림 종료 대기·미검증 응답 거부·후속 정상 호출·기억 쓰기 없음을 확인했다. 문법·SDK 삽입본 일치·체크섬도 검사했다. 전체 프로젝트 스위트나 실모델 성능 검증을 의미하지 않는다.

기존 HAYAKU 복구 시험 한 곳은 기본 모드에서 영구 실패 전문 ID를 요구하여 기준 커밋에서도 실패했다. 이미 적용된 진단 퇴역 정책에 맞춰 전문 ID 없음과 실제 호출 수를 담은 세션 실패 요약을 확인하도록 갱신했다. 복구 근거·원장·재시도 차단 검사는 유지한다.
