## 재현한 결함과 수정

1. **제공자 요청 전에 시간 예산 소진.** 예약 저장을 논리적으로 31초 지연하면 실제 제공자 요청 0회인데 청크가 `failed`로 남았다. 큐가 그룹을 호출하기 전에 단일 요청의 30초 마감을 생성하고, 제출 권한 저장·검증도 요청 타이머에 포함했다. 전체 작업의 명시적 마감·취소는 유지하면서, 준비 단계와 실제 요청 타임아웃을 분리했다. 명시적 마감이 요청 전에 끝나면 `pending`으로 되돌리고 제출되지 않은 예약을 정리한다.
2. **원문·예약 검증에 전체 벡터 재읽기.** 원문 집합, 작업 ID, 실행자, 레지스트리와 세계선 검증은 원문 메타데이터로 가능하다. 이 검증은 물리 원문을 계속 새로 읽되 벡터 hydration을 생략한다. 실제 변경에 사용할 전체 records 및 완료 readback은 계속 벡터를 읽고 검증한다. 차가운 사이드카 비교 시험에서 요청 전 읽기 15→8회, 전체 읽기 31→15회였다. 실제 RisuAI의 경과 시간 단축률은 측정하지 않았다.
3. **서버 동기화 내부 임베딩과 후속 큐 중복.** 서버 복구는 원문·세계선 준비를 먼저 끝내고 일반 임베딩 큐를 한 번 실행한다. 저장 준비 시작부터 적용되던 고정 120초 마감을 제거하고 호출자가 지정한 전체 마감은 계속 적용한다.
4. **파생 에피소드 지연을 원문 복구 차단으로 취급.** 임베딩 완료 후 에피소드 인덱스가 이전 벡터 상태를 기준으로 남을 수 있었다. 원문·구조·벡터 결함의 작업 소유권이 검증되면 파생 인덱스 지연만으로 큐를 차단하지 않는다. 큐 완료 후 현재 스코프·프로필을 다시 검사하며 파생 인덱스를 갱신한다. 원문 손상, 누락 샤드, 다른 작업과 연결되지 않은 벡터 손상은 계속 차단한다.
5. **최종 점검과 연결 갱신의 경합.** 실제 서버 부트스트랩 갱신을 최종 점검과 겹치게 해 재현했다. 해당 연결 증거 오류에만 한 번 연결 갱신을 기다리고, 승인된 원문·라우트 권한을 재검사한 뒤 점검만 다시 실행한다. 완료된 동기화·제공자 호출을 재실행하지 않는다. 실제 연결 불가·스코프·원문·프로필 변경은 그대로 거부한다.
6. **차단·실패 사유 은폐.** 서버 구조 판정에서 의도적으로 읽지 않은 자격 증명이 실제 구조 결함을 가리지 않게 했다. 파생 인덱스 지연·별도 벡터 손상을 구분해서 표시하고, 실패한 큐가 `queue_pass_complete`로 원인을 감추지 않게 했다. 미완료 임베딩이 있는데 누락·변경 턴이 0이라는 이유로 결과 문구가 정상이라고 판정하던 조건도 제거했다. 반대로 완전한 서버 스냅샷에서 원문·저장 점검을 통과하고 미완료 작업이 0이면 `실행 차단` 대신 `서버 저장 점검 통과`라고 표시하되, 제공자 준비 상태는 별도 확인 대상으로 남긴다. 디버그에는 마지막 유지보수 큐의 집계·시간·물리 요청 수·중단 사유를 최대 20패스만 포함한다.
7. **제공자 호출 이후 마감 초과 분류.** 실제 호출 이후의 `FLASHBACK_DEADLINE`은 `uncertain`으로 보존한다. 호출 전 만료와 구분하며 자동 재전송하지 않는다.

## 추가 재현: 실패 13건과 앵커 정리 3건의 조합

후속 입력 `flashback-memory-debug-2026-10-29T15-09-12-846Z.json`과 같은 commit의 로컬 Flashback SQLite를 `readOnly: true`로 열어 대조했다. 사용자 저장소에는 어떤 수정·복구·제공자 요청도 실행하지 않았다.

- T28의 실패 13개 모두 `lastError.code=FLASHBACK_DEADLINE`이었다. 작업 스키마가 유효하고 현재 프로필과 일치했다.
- 별개인 T27의 3개 레코드에서 entity anchor 재계산 차이가 있었다. 원문 변경, 메타데이터 정제 변경, 숨은 패킷·상태·생각·주석 추출은 모두 없었다.
- 같은 원문 28턴을 구성해 실제 판정 함수를 재생한 결과, 수정 전에는 `dirtyRecords=3` 때문에 `embeddingQueueSourceHealthy=false`, `server_inspection_only`로 막혔다. 이 앵커 차이 조합이 이전 합성 테스트에는 없었다.
- 순수 앵커 차이를 별도 계수해 일반 원문 오염과 분리했다. 유효한 실패 큐는 처리 가능하게 하고, 큐 처리 후 작업 중이지 않은 레코드의 entity anchor만 기존 writer/lock 경로로 갱신한다. 물리 readback에서 원문 revision, 벡터 값, 완료 영수증과 새 앵커를 확인한다. 원문 정제·메타데이터 권한 변경이 필요한 기록과 미완료 작업은 이 좁은 정리에서 수정하지 않는다.
- 같은 저장 데이터의 판정 재생에서 `dirtyRecords=3`, `anchorOnlyDirtyRecords=3`, `embeddingQueueSourceHealthy=true`, `automatic.strategy=embedding_queue`를 확인했다. 이 판정 재생은 현재 RisuAI 호스트 호출이나 Voyage 실행 증거가 아니다.
- 실제 인증 서버/SQLite 합성 시험에 `anchor_drift` 조합을 추가했다. 기존 유료 임베딩의 원문·벡터·완료 영수증을 그대로 보존하면서 실패 큐와 앵커 정리가 완료되고, 최종 미완료 0·dirty 0을 확인했다.
