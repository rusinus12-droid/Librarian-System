# Flashback 1.0.115 — 스코프 목록과 삭제 권한

기준은 Claude `claude/charming-feynman-lz1ayl`의 `139c91381c351fe9fd484e0e01f0c715c7daa40c`다. 최초 패치는 기존 `codex/integration`의 `284f9c3a1992d00fd20565efa64fe56f895ae35d`에 보존했다. 이후 사용자의 명시적 요청에 따라 같은 패치를 Claude 최신본에도 별도 커밋으로 반영한다. main 브랜치는 변경하지 않는다.

## 수정한 동작

- 필름 보관함과 스코프 정리의 배지는 마지막 성공한 목록의 고유 스코프 수를 표시한다. 검색·분류 필터로 전체 개수를 바꾸지 않으며, 성공한 삭제 후 새 목록으로 갱신한다. 첫 조회 전 또는 첫 조회 실패는 `—`, 성공한 빈 목록은 `0`이다.
- 강제 새로고침이 캐시를 무효화한 뒤 실패해도 마지막 확인 목록과 개수를 유지한다. 별도 상태 영역에 조회 실패와 오래된 목록임을 표시하고, 조회 복구 전까지 목록의 삭제·정리를 막는다. 첫 조회 실패는 빈 저장소로 표시하지 않는다. 이전 요청의 늦은 실패가 새 성공 화면을 덮어쓰지 않는다.
- Flashback의 일반 스코프 삭제, 선택 삭제, 목록 잔재 정리는 서버 원본을 삭제하는 경로로 사용하지 않는다. 서버 단독 및 레거시 mirror 대상은 `RE:TRACE → 서버 데이터 관리`로 안내한다. 별도의 현재 스코프 삭제와 공개 owner 삭제 API에도 같은 제한을 적용한다.
- 대상 스코프의 명시적 저장 모드를 먼저 확인한다. 현재 채팅이 로컬이라는 이유로 다른 서버 스코프의 로컬 사본 부재를 `registry_only`로 판정하지 않는다. 서버 대상의 로컬 목록을 지우거나 삭제 성공으로 집계하지 않는다.
- 로컬 관리 작업은 대상과 활성 owner proxy가 모두 검증된 `plugin_only`일 때 허용한다. 기존 Storage SDK의 읽기 전용 권한 증거와 변경 감지 fence를 사용하고, 잠금 취득 후 및 삭제 단계 사이에 권한과 활성 채팅을 재확인한다. 미확인 모드·전환 중·현재 활성 서버 scope를 따르는 proxy는 로컬 삭제 권한이 아니다.

## 서버 데이터 관리와의 관계

`확인 후 삭제`와 `삭제`는 기존의 동일한 선택 삭제 경로를 사용한다. 승인 후 실제 검사를 수행하며, 검증된 로컬 기억은 기존 원문·영구 이전 세션 기록 보호와 쓰기 잠금을 거쳐 삭제한다. 목록만 남았으면 두 번의 부재 확인과 물리 키 검사 후 목록만 정리한다.

서버 사본은 기존 RE:TRACE 경로에서 삭제한다. RE:TRACE가 Flashback에 `memory_suite_prepare_server_scope_delete`를 요청하면 owner는 해당 서버 스코프를 로컬에 복원·검증하고 `plugin_only`로 전환한다. 이후 서버 관리가 보존 고정·참조 관계·전체 키 범위·조건을 확인하고 삭제 전용 백업과 조건부 배치를 수행한다. 이 패치는 새 manager 권한이나 일반 KV 삭제의 우회 경로를 추가하지 않는다.

기존 owner 화면은 서버 카탈로그의 보존 고정·참조 보호를 조회하지 않고 일반 KV 쓰기·삭제를 수행했다. 재현에서는 manager가 각각 409로 차단한 대상도 owner에서 삭제했고, 카탈로그 보호 표시는 남았다. 수정본은 이 owner 경로를 서버 대상에 대해 차단한다. 혼합 모드에서 실제 서버 데이터가 있는데 로컬 목록만 제거하고 삭제 1개로 집계하던 경우도 차단한다.

현재 활성 채팅이 서버 단독이고 관리 대상이 로컬이면, 해당 로컬 채팅 또는 플러그인 단독 채팅으로 이동한 뒤 새로고침해야 로컬 삭제를 수행할 수 있다. 일반 owner proxy를 다른 스코프의 쓰기 권한으로 재해석하지 않는다.

## 검증

- `tests/flashback_scope_viewer_state_test.cjs`: 전체 플러그인과 JSDOM 호스트를 사용한 5건. 배지·검색·삭제, 조회 실패 시 목록 보존과 작업 차단, 첫 조회 실패, 실제 빈 목록, 이전 요청의 늦은 실패를 확인한다.
- `tests/flashback_scope_deletion_authority_test.cjs`: 전체 플러그인과 격리 HTTP/SQLite 서버를 사용한 7건. 현재/대상 혼합 모드, 공개 삭제·목록 정리·안전 정리, 카탈로그 보존 고정·참조 보호, mirror/미확인 모드, 서버 활성 proxy에 대한 로컬 대상 보호를 확인한다. 기존 owner 복원 API와 manager plan/execute의 양성 경로에서 서버 사본 삭제, 로컬 원문 유지, 삭제 전용 SQLite 백업을 검증한다.
- 기존 `flashback_scope_management_server_test.cjs`는 새 계약에 맞춰 온라인·오프라인 모두 owner 서버 삭제가 차단되는 것을 검사한다. 정상 서버 사본 삭제의 양성 검증은 위 owner 복원 + manager commit 검사로 유지한다.
- 새 검사 12건 모두 통과했다. 기준 소스를 대입한 음성 대조군은 11건 실패·1건 통과했다. 기존 owner 복원 + manager commit 양성 경로는 기준에서도 통과하며, 이를 새로 구현한 기능으로 집계하지 않는다.
- 관련 기존 검사 파일 15개가 통과했다: 스코프 관리·레지스트리 안전성·GUI 계약·내부 탭·발견·강제 scope 갱신·observer 재시도·GUI UX·원문 뷰어·세계선·서버 카탈로그·삭제 job·native branch 저장 모드·peer 고아 보호를 포함한다.
- Chromium에서 전체 실제 플러그인의 6개 화면을 7개 viewport 너비로 검증했다. SDK 동기화와 Flashback Full 소스 빌드/구문 검사도 통과했다. 빌더의 과거 파일 크기 기준 초과는 보고용 경고이며, 이 작업으로 배포 파일 크기나 실사용 성능을 검증했다는 뜻은 아니다.

## 범위와 한계

Storage/Compute SDK와 서버 코드는 변경하지 않는다. 기존 저장 형식과 원문·벡터 검색을 변경하지 않는다. 사용자 저장소와 외부 모델은 사용하지 않는다. 브라우저 검사는 실제 플러그인을 Chromium에서 실행하되 RisuAI 호스트/저장소 경계는 합성 fixture다. 서버 검사는 실제 HTTP/SQLite이지만 사용자 서버나 설치된 RE:TRACE UI를 조작한 검증은 아니다.

로컬 호스트 저장소에 여러 프로세스를 아우르는 원자적 CAS를 추가한 것은 아니다. 기존 로컬 쓰기 계약의 한계는 유지된다. 마지막 확인 목록은 GUI의 단일 메모리 스냅샷이며 새 조회 권한이나 삭제 증거로 사용하지 않는다. 원본 평가 스냅샷·비밀값·원시 로그는 저장소에 포함하지 않는다.
