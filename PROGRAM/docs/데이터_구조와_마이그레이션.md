# DATA 구조와 자동 마이그레이션

```text
DATA/
├─ config/
│  ├─ server-config.json
│  └─ scope-catalog.json
├─ stores/
│  ├─ flashback/flashback.sqlite
│  ├─ hayaku/hayaku.sqlite
│  ├─ libra/libra.sqlite
│  ├─ lia/lia.sqlite
│  └─ retrace/retrace.sqlite
├─ backups/
│  ├─ auto/
│  ├─ manual/
│  ├─ pre-migration/
│  └─ deleted-scopes/
├─ logs/
├─ migrations/
├─ data-layout.json
└─ runtime-token.txt
```

서버는 플러그인 value의 내부 의미를 해석하지 않고 namespace, space, key, value, revision, digest, tombstone만 관리합니다. 플러그인 자체 데이터 스키마 마이그레이션은 해당 플러그인이 소유합니다.

PROGRAM은 DATA를 열기 전에 지원 버전을 읽기 전용으로 검사합니다. 더 새로운 DATA/DB 형식이면 어떤 metadata도 갱신하지 않고 중단합니다. 마이그레이션 전 백업과 완료 영수증은 DATA 안에 남습니다.

## 0.2.9 Windows data/DATA in-place adoption

Windows에서는 `data`와 `DATA`가 같은 실제 디렉터리일 수 있습니다. 0.2.9는 이 경우 파일을 자기 자신에게 복사하지 않고 `case_only_in_place` 이전 영수증을 한 번만 기록합니다. 이 영수증은 기존 `memory-suite-config.cmd`의 host/port를 새 JSON 설정으로 가져오는 근거가 되며, 두 번째 실행부터는 같은 이전을 반복하지 않습니다. 원본 파일은 그 자리에서 보존됩니다.

## 서버 scope catalog

`DATA/config/scope-catalog.json`은 RE:TRACE가 opaque KV를 논리 스코프로 묶어 표시하는 보조 색인입니다. 실제 기억 정본은 각 namespace SQLite에 남습니다. 고아 후보도 자동 삭제하지 않으며 사용자 `pinned` 상태를 보존합니다.

## 0.2.8 플러그인 스코프 라우팅 registry

각 플러그인은 작은 라우팅 registry로 스코프별 저장 모드를 보존합니다.

```text
schema: memory-suite.scope-routing.v1
local key:  __memory_suite_internal_scope_routes_v1__:<namespace>
server key: __memory_suite_scope_routes_v1__:<namespace>
```

라우팅 registry는 실제 기억 payload와 분리되고 현재 스코프 pluginStorage 삭제 대상에서 제외됩니다. 로컬 pluginStorage와 device-local storage에 작은 복사본을 보존하고, 서버가 가능할 때 namespace에도 best-effort로 동기화합니다. 서버가 꺼져도 어느 스코프가 server_only인지 알 수 있으므로 pluginStorage로 잘못 fallback하지 않습니다.

스코프별 모드는 ARG에 저장하지 않습니다. `memory_suite_server_mode`는 0.2.6 전역 모드의 일회성 이전 슬롯일 뿐이며, 활성 스코프 하나로 가져온 뒤 plugin_only로 초기화됩니다. `memory_suite_server_url`만 플러그인 전역으로 유지됩니다.

## 스코프별 서버 레코드

원래 한 JSON에 여러 스코프가 함께 있던 LIA container는 서버에서 다음 접미사를 붙인 scope-specific opaque record로 투영됩니다.

```text
<logical-key>::memory-suite-scope:v1:<encoded-scope-id>
```

로컬 원본 container는 기존 플러그인 호환을 위해 유지될 수 있으며, SDK가 현재 스코프 부분만 project/merge/remove합니다. 공유 archive/index 및 plugin-global 설정은 단일 스코프 삭제 sweep에서 제외됩니다.

DATA layout version과 SQLite database schema version은 1로 유지됩니다.


## 서버 진단 journal

```text
DATA/logs/server-debug.jsonl
DATA/logs/server-debug.1.jsonl ... .4.jsonl
```

진단 journal은 SQLite 정본과 별개의 append-only JSONL 보조 로그입니다. 삭제·복원·마이그레이션 정본이 아니며, 서버/SDK/HTTP/SQLite 경계의 문제를 진단하기 위한 privacy-scrubbed metadata만 보존합니다. 파일 손실은 기억 데이터 손실을 의미하지 않습니다.

일반 owner 플러그인은 구조화된 journal만 읽습니다. RE:TRACE manager debug export는 필요할 때 `DATA/logs/startup.log`, `startup-error.log`, `server.log`의 제한된 최근 부분도 서버에서 읽습니다. 이 text tail은 별도 정본이 아니며, 각 파일 전체가 아니라 길이 제한된 일부만 반환되고 credential 패턴은 서버에서 마스킹됩니다.
