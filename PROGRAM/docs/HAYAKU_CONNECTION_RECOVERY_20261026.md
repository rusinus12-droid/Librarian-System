# HAYAKU 연결 표시와 복구 저장 시간 초과 조사

기준: `main`의 `11fa816` (HAYAKU 3.3.8). 첨부된 2026-10-26 디버그 JSON은 진단 자료로만 사용했다. 실제 사용자 DATA에 접근하거나 모델 API를 호출하지 않았다.

## 확인한 사실

- 수동 복구 대상은 3·9·13턴이다. 모두 작업 잠금 저장 단계에서 `storage_write_timeout`으로 중단됐고, 모델 호출은 0회다.
- 첨부 서버 이벤트 500개는 모두 성공했다. 읽기 480회는 서버 내부 처리 시간이 최대 2ms, 쓰기 6회는 10–12ms였다. DB 무결성도 `ok`다. 이 수치는 서버 처리 시간이며, 호스트 RPC·라우팅·왕복·읽기 검증 시간을 포함하지 않는다.
- 루트 Recovery Vault 키의 SHA-256 앞 16자리 `91c88ce384a6ecf7`이 서버 로그의 키 해시와 일치한다. 같은 루트가 클라이언트 실패 선언 뒤 서버에 저장됐다.

| 대상 턴 | 클라이언트 실패 시각 (한국 시간) | 서버 쓰기 완료 시각 (한국 시간) | 실패 선언 후 지연 | 루트 revision |
| --- | --- | --- | --- | --- |
| 3 | 09:14:26.328 | 09:14:26.691 | 363ms | 14 |
| 9 | 09:14:31.694 | 09:14:31.946 | 252ms | 15 |
| 13 | 09:14:36.947 | 09:14:37.412 | 465ms | 16 |

저장되지 않았다고 단정할 상황이 아니라, 원래 저장 작업이 끝나기 전에 HAYAKU가 대기를 종료한 상황이다. 코드의 일반 호스트 호출 제한은 1.5초인데 Recovery Vault도 이를 그대로 사용했다. SDK 쓰기는 저장 영수증과 정확한 읽기 검증까지 수행한다. 제한 시간 이후에도 원래 Promise는 계속 실행된다.

연결 표시는 같은 대화·서버의 상태 갱신 때마다 직전 확인 결과를 지우고 `확인 중`으로 되돌렸다. 겹친 연결 검사가 무효화된 경우에도 `연결 확인 중`으로 바뀌었다. 이 표시 변동은 재현했다. 첨부 구간의 성공 이벤트와 마지막 `connected` 스냅샷만으로 사용자가 겪은 실제 연결 단절 전체를 배제하거나, 모든 단절의 원인을 확정할 수는 없다.

## Recovery Vault의 현재 역할

`hayaku.v2.recovery_vault.*`는 현재도 쓰고 읽는 저장 형식이다. Recovery Journal의 누락 자료, 복구 상태와 작업 잠금이 이 계층에 보관된다. 예전 화면이나 재시도 기능의 이름이 남은 것만은 아니다. 이를 삭제하면 현재 복구 경로와 기존 자료 호환성이 깨지므로 유지한다.

## 수정

- Vault의 읽기·쓰기에는 별도의 15초 제한을 적용한다. 일반 실시간 호출의 1.5초 제한은 유지한다.
- 기존 저장 요청을 기다리고, 영수증 및 정확한 읽기 검증 후에만 복구를 진행한다. 새 저장 요청이나 모델 호출을 자동으로 추가하지 않는다. 무응답은 여전히 제한 시간 후 중단한다.
- 로컬 대기 시간 초과를 곧바로 서버 접속 실패라고 안내하지 않는다. 처리 결과가 아직 확정되지 않았음을 알린다.
- 동일한 GUI·대화·주소·저장 설정을 다시 확인하는 동안 직전 상태를 유지한다. 실제 실패 응답은 경고로 표시하며, 대화·주소·저장 방식 변경 때는 다시 확인한다.
- 상태 표시 코드는 공통 생성 원본과 HAYAKU·Flashback의 삽입본을 함께 동기화한다. Flashback의 저장·복구 로직은 변경하지 않는다.
- 기존 수동 복구 진단 테스트의 격리 VM에 빠져 있던 `hayakuReanalysisRunning` 의존성을 추가한다. 실제 런타임의 복구 동작은 이 테스트 보정으로 바뀌지 않는다.

## 검증

`NODE_PATH=/workspace/librarian-cloud/dependencies/node_modules`로 아래 런타임 테스트 8개 파일을 실행했고 모두 통과했다. 새 지연 재현 테스트는 수정 전 소스에서 쓰기·읽기 시간 초과로 실패하고 수정 후 3개 시나리오 모두 통과했다. 상태 GUI 테스트도 수정 전 표시 유지 검증이 실패하고 수정 후 12개 시나리오 모두 통과했다.

- `hayaku_recovery_storage_latency_runtime_test.cjs`: 임시 HTTP 서버·SQLite에서 저장 응답과 읽기 검증을 1.7초 지연해 복구 완료와 모델 1회 호출을 확인한다. 응답 없는 저장의 제한 시간·모델 0회·루트 미게시 및 지연 읽기도 검사한다.
- `current_status_gui_runtime_test.cjs`: 같은 설정 재확인의 표시 유지, 무효화된 검사, 실제 접속 실패, 주소 변경과 HAYAKU·Flashback·LIBRA GUI를 검사한다.
- `hayaku_recovery_storage_error_surface_test.cjs`: 실제 저장 거부 시 모델을 호출하지 않고 오류를 표시하며, 대기 시간 초과 문구가 접속 실패와 구별되는지 검사한다.
- `hayaku_recovery_vault_shards_runtime_test.cjs`, `hayaku_server_only_recovery_shards_test.cjs`: 대용량 분할 저장, 기존 형식 이관, 부분 갱신, 실패 시 기존 그래프 보존과 실제 서버 복구를 검사한다.
- `hayaku_storage_eventual_confirmation_runtime_test.cjs`: 일반 원장의 1.5초 경계와 지연 저장 확인을 검사한다.
- `hayaku_manual_preflight_diagnostics_runtime_test.cjs`, `hayaku_simple_recovery_runtime_test.cjs`: 복구 전 검증·작업 잠금·취소·실제 호출 횟수·기존 복구 경로를 검사한다.
- 공통 상태 삽입본 동기화 검사, 변경 대상 HAYAKU·Flashback의 SDK 정확 일치 검사, 플러그인 구문 검사와 `git diff --check`가 통과했다.

통합 `check_sdk_sync.cjs`는 최신 `main`에서 가져온 변경하지 않은 LIBRA 삽입본에 `sdk=MISMATCH(count=0)`를 보고한다. HAYAKU·Flashback은 이 검사에서도 `OK`다. 기존 LIBRA 문제까지 수정하거나 전체 저장소 검사가 통과했다고 판정하지 않았다.

릴리스 버전 변경·배포·사용자 설치본 적용은 포함하지 않는다.
