# RE:TRACE 서버 관리 GUI 점검과 수정

기준은 main `acb7ce3`, RE:TRACE 1.9.85이며 수정 버전은 **1.9.86**이다. 별도 브랜치 없이 main에서 작업했다. 서버·SDK·다른 플러그인의 버전은 변경하지 않는다.

## 판정과 변경

서버 관리는 화면만 있는 기능이 아니다. 실제 서버 API와 SQLite에서 사본 고정·해제, owner의 로컬 보존 증명을 거친 사본 삭제, 백업 생성·검사, 복원 미리보기·취소·실행, ZIP 이관·복원, 연결 진단, 이력과 namespace 초기화를 확인했다. 다음 결함을 수정했다.

| 문제 | 수정한 동작 |
|---|---|
| 성공한 백업·삭제 작업의 단계가 완료로 표시되지 않음 | 백업은 생성 후 실제 파일 무결성 검사와 저장 목록 재조회를 통과해야 완료한다. 삭제는 백업·커밋 결과와 최신 목록에서 대상 부재를 확인해야 완료한다. |
| 백업 검사가 실패해도 생성 응답만 성공으로 보일 수 있음 | 검사 실패는 미완료로 표시한다. 이미 생성한 백업은 보존하며 자동으로 다시 생성하지 않는다. |
| ZIP 작업에도 완료 증명이 전달되지 않음 | 내보내기는 전체 파일 SHA-256 일치, 가져오기는 서버 파일 검사·복원 계획 검증을 완료 표시의 근거로 사용한다. 브라우저 다운로드 시작과 실제 디스크 저장 완료는 기존 안내대로 구분한다. |
| ISO 시각을 숫자로 변환하여 `마지막 -` 표시 | ISO 날짜·epoch 숫자·숫자 문자열을 지원하고 유효하지 않은 값은 미확인으로 표시한다. ZIP·초기화 후 관리 상태도 다시 읽는다. |
| 실제 접속한 owner도 `마지막 접촉 미확인` 표시 | `flashback_memory`, `hayaku_locator_continuity`, `lia_persona_linker` 등 실제 plugin ID와 대조한다. 읽기 전용 소비자의 접촉을 owner 접촉으로 오인하지 않는다. |
| 활성 스코프를 일괄 선택하지 않는다는 안내와 실제 동작 불일치 | 고아 후보 중 보호 조건을 통과한 항목만 일괄 선택한다. 표시 개수·체크박스·선택 목록·실행 대상을 같은 기준으로 제한한다. 활성 스코프의 개별 보존·삭제 절차는 유지한다. |
| 데이터 탭의 첫 조회 버튼이 접힌 상세 영역 안에 있음 | 사용자가 빈 서버 데이터 탭을 직접 선택하면 첫 조회를 실행한다. 개요를 열기만 해서는 전체 스캔하지 않으며, 진행 중 조회를 중복 시작하지 않는다. |
| 조회·삭제 후 내비게이션 개수가 과거 값 또는 `—`로 남음 | 목록 렌더링 시 현재 조회 상태와 같은 개수로 배지를 갱신한다. |
| 요청한 복원 미리보기가 접힌 상세 영역에 남음 | 백업 복원 미리보기와 ZIP 가져오기 결과 영역을 요청 후 펼친다. |

보존 고정·승계 참조·불완전 데이터 보호, owner 보존·저장 모드 증명, 삭제 전 백업과 revision/digest 조건, 복원 계획 만료·변경 검사, 정확한 확인 문구 입력을 유지한다.

## 삭제 후 목록 재등장 처리

Chromium 실행 시점에 따라 Flashback 시작 작업이 삭제 이후 공유 레지스트리 항목을 다시 게시하는 경우가 있었다. 본문 manifest·shard·vector는 삭제됐어도 공유 목록 항목이 남으면 서버 목록에 다시 나타날 수 있다. 이 패치가 모든 오래된 owner의 레지스트리 재게시를 차단하는 것은 아니다.

이때 기존 커밋은 유지하면서 **`삭제 반영됨 · 새 항목 재조회 필요`**로 표시하고 전체 단계 완료를 확정하지 않는다. namespace 재조회 실패도 완료 증명으로 사용하지 않는다. 이미 커밋한 삭제를 자동 반복하여 새 데이터를 지우지 않는다. 정상 관리 시나리오는 owner 시작 작업이 안정된 뒤 실행했고, 재등장·응답 유실·부분 완료는 별도 부정 사례로 검사했다.

## 검증 결과

`tools/retrace_server_management_browser_audit.cjs`는 공식 빌드한 Full/Min RE:TRACE를 변형하지 않고 등록 GUI로 실행한다. 실제 Flashback writer로 서버 데이터를 준비하고 실제 owner IPC 경로로 삭제 전 로컬 보존을 수행한다. 별도 loopback HTTP 서버와 실제 SQLite·백업·ZIP 파일을 사용한다.

- Full/Min 각각 **30개 Chromium 관측 검사 통과**, 브라우저 예외 0개, 모델·임베딩 호출 0회.
- 활성 2개·고아 1개 조회, 정확한 선택 개수와 내비게이션 배지, 고정 시 삭제 차단, 해제 후 삭제, 서버 tombstone과 owner 로컬 manifest 보존을 확인했다.
- 백업 파일 검사, 실제 값이 달라진 SQLite canary의 복원 취소·확정 복원, 실제 ZIP 다운로드·업로드·전체 복원과 파일 검사 표시를 확인했다.
- 연결·관리 진단 두 단계, 실제 작업 이력, Flashback 초기화 후 서버 데이터 부재, 데스크톱과 390px 모바일의 가로 넘침 없음을 확인했다.
- `retrace_server_restore_gui_runtime_test.cjs`: 실제 HTTP 백업 검사 거부 시 완료 차단, 원문 보존, 복원 후 구 epoch 읽기·쓰기 409, 재시작, 조회 대상 변경, 부분 응답 혼합 차단, 초기화와 최종 상태 조회를 확인했다. 수정 전 바이트는 새 백업 단계 검사에서 `0 !== 3`으로 실패한다.
- `retrace_delete_flow_runtime_test.cjs`: 부분 실패·응답 유실·명시적 재시도·작업 창 재개·중복 삭제 방지·목록 재등장을 검사한다. 새 일괄 선택 회귀는 활성·고정·조상·페어링·미확인 항목을 보호하고 날짜 형식을 검사한다.
- 서버 고정·참조·삭제 조건 검사, GUI 렌더·탭 이동·키보드, 39개 관리 조회 currentness 사례와 `acb7ce3`의 지연 승계 회귀 7개도 통과했다.

재현에는 Node의 SQLite 지원, Playwright와 Chromium이 필요하다. `PLAYWRIGHT_MODULE`로 설치한 Playwright 모듈 경로를, `RETRACE_SOURCE_FILE`로 Full/Min 파일을 지정할 수 있다. `CHROMIUM_PATH`는 선택 사항이다.

```sh
PLAYWRIGHT_MODULE=/path/to/node_modules/playwright \
RETRACE_SOURCE_FILE=/private/build/Full/RETRACE.js \
AUDIT_OUT=/private/retrace-audit \
node PROGRAM/tools/retrace_server_management_browser_audit.cjs
```

기본 출력은 저장소 밖 비공개 임시 폴더다. 도구는 저장소 안의 출력 경로를 거부하고 매번 별도 DATA 폴더를 만든다. 스냅샷·서버 capability·백업·ZIP·로그·화면 캡처는 Git에 넣지 않는다.

## 한계

Chromium과 HTTP·SQLite·백업·ZIP 처리는 실제 구현이다. RisuAI 캐릭터·대화·저장소 어댑터와 IPC 전달자는 합성이며, 연결된 사용자 앱의 API 3 iframe/RPC·모바일 WebView를 실측한 검사는 아니다. 서버 데이터도 합성이고 실제 사용자 서버를 변경하지 않았다. 실모델은 필요하지 않은 관리 경로이므로 호출하지 않았다. 특정 실제 서버의 대규모 DATA 처리 시간이나 모든 namespace의 모든 스키마 조합을 보증하지 않는다.
