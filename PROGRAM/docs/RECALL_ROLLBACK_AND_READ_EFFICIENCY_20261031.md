- **Flashback 무반응:** `model`을 본 요청으로 분류했고 원장·검색·쿼리 임베딩 활동도 있으나 `lastRecall=null`이다. 최종 manifest/worldline/readset 확인에서 변경을 감지하면 진단 없이 반환하는 실제 경로를 재현했다. 원본 세션에서 어느 필드가 변경됐는지는 로그가 없어 확정할 수 없다.
- **GRADIA LIB 읽기:** 제공된 결과는 `LIB_READ_NATIVE_ID_UNAVAILABLE`로, 연결 실패나 기억 없음과 구별되는 호스트 메시지 ID 결합 실패다. ID 없는 `Current Input` 포장문과 현재 호스트 원문이 같은 경우에도 별도의 bare 입력 행이 없으면 실패하는 경로를 재현했다. 코드 펜스 포장도 시험했다.
- **GRADIA 콘솔 경고:** `provider_length_retry aide_world`는 길이 종료에 대한 출력 한도 확대 재시도, `thinking_only_retry aide_plot`는 본문 없는 생각 전용 응답에 대해 thinking을 끄는 재시도다. 두 경고 자체는 최종 실패 이벤트가 아니다. 제공된 finalDraftMeta에는 최종 산문이 있지만, 이 자료만으로 각 보조 단계의 재시도 성공까지 확정할 수는 없다.

## HAYAKU와의 비교

HAYAKU는 현재 채팅 패킷과 저장 원장을 결합하고, 세계선·슬롯 head를 대조한 뒤 요청용 투영과 메모리 색인을 구성한다. 현재 입력·최근 대화에 대해 BM25F, 연관 그래프 및 에피소드 경로로 검색한다. 검색 시 외부 임베딩 호출이 필요 없다. 패킷 투영 캐시와 요청 내 검색 특성을 재사용하고, 검색·복구 원문·부분 기억 조회를 함께 진행한다.

이번 로그는 원장 로드 167ms, 투영 수집 81ms, 색인 재구성 57ms, 검색 23ms, 병렬 회상 구간 475ms다. 원장 대조 저장 1,862ms와 복구 부채 대조 1,460ms가 더 큰 비중을 차지했다. 후보 48행 중 12행·4,461자를 전달했다.

**계측 한계:** HAYAKU `elapsedMs=4571` 및 `beforeRequest:done`은 소스상 마지막 `verifyHayakuReadset` 직전에 기록된다. 따라서 4.571초를 최종 검증까지 포함한 전체 시간으로 주장할 수 없다. `returned_to_hook`은 최종 전달 성공을 확인하지만 최종 검증의 독립 소요 시간은 이 자료에 없다.

HAYAKU도 설정·저장소 모드·DATA 바인딩·호스트 원문·원장 head·입력의 현재성을 다시 검사한다. 차이는 검증 여부보다 **검증 단위와 재사용 범위**다. LIBRA의 cold 경로는 한 번 만든 그래프를 선택·최종 검증마다 원문 전체에서 다시 구성했고, Micro의 닫는 원문 검사에서 스코프 객체를 새로 만들어 요청 read frame과 예산을 벗어나는 중복 읽기도 있었다.

## 적용한 변경

1. LIBRA 전체 리콜 제한을 **40→90초**, 일반 단계 제한을 **30→45초**로 늘렸다. 원문 관찰 세션도 90초에 맞췄다. 임베딩 한도·유료 호출 횟수는 늘리지 않았다.
2. 첫 회상에도 기존 durable 색인과 같은 owner source proof를 발급한다. 그래프는 한 번 구성하고 후속 검증은 원문 계보·정본 참조·Micro 게시 head/work·State·Lore 증거와 실제 소비한 본문을 재검증한다. 증거 발급이나 재검증이 실패하면 전달하지 않는다. 요청용 증거는 저장소에 게시하지 않는다.
3. Micro 닫는 원문 검사는 동일 스코프의 기존 read frame과 자원 예산을 유지한다. 프레임 종료 시 물리 본문·서버 revision/tombstone·mirror 양쪽을 다시 대조한다.
4. head와 의존 본문을 최대 4개씩 묶어 읽는다. LIBRA 전용 SDK의 readset도 요청이 현재 남은 I/O·바이트 예산으로 정한 크기만큼 묶는다. 각 값의 SHA-256, revision, 존재·삭제 상태와 앞뒤 저장소 바인딩 검사는 유지한다. 누락 키·과대 응답의 기존 fallback·자원 반환도 검증했다.
5. 백그라운드 색인은 실시간 회상과 최종 검증에 양보한다. 기존에는 두 번 양보한 뒤 회상 도중 다시 시작할 수 있었고, 묶음 읽기의 I/O 예약과 충돌했다. 새 요청은 진행 중인 배경 I/O가 정리된 뒤 시작하고 최종 전달까지 우선권을 유지한다. 계속 요청이 들어오면 파생 색인 완성은 유휴 시간까지 늦어질 수 있다.
6. 그래프 owner frame·색인 열기·cold 구성·선택 검증·배경 작업 정리 시간을 별도 기록하고 시작 오프셋도 남긴다. 겹치는 구간을 구별할 수 있다.
7. Flashback 최종 기준 변경 시 같은 요청·스코프·설정과 남은 시간 안에서 최대 두 번 새로 준비한다. 계속 변하면 `FLASHBACK_RECALL_FINAL_BINDING_CHANGED`와 activity를 남기고 주입하지 않는다. 새 요청 결과를 이전 요청이 덮어쓰지 않는다.
8. GRADIA는 포장문 본문을 최신 호스트 사용자 메시지와 정확히 대조해 ID를 결합한다. 중복·부분 일치·과거 입력·스트리밍은 거부하고 원래 프롬프트와 단계별 대화창은 보존한다.

## 버전 상승과 커밋 범위

실제 변경된 LIBRA는 2.6.10, Flashback은 1.3.10, GRADIA는 0.28.4로 올린다. HAYAKU 3.3.9, LIA 0.29.4, RE:TRACE 1.12.7 및 서버/패키지 버전은 유지한다. 이번 수정·관련 SDK·회귀·보고서와 버전 안내·무결성 메타데이터만 커밋 대상으로 선택한다. 기존 DATA 변경, `.development/`, 별도 GRADIA 관찰 문서는 제외한다. 릴리스 ZIP과 실제 호스트 검증은 이 커밋의 성공 조건에 포함하지 않는다.
