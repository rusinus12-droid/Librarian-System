# 0.3.55 — HAYAKU 복구 저장소 / Flashback 스코프 관리

## 설치 대상

- Librarian System Server: 0.3.55
- HAYAKU Locator Continuity: 3.0.131
- Flashback Memory: 1.0.93
- LIBRA / LIA / RE:TRACE: 이 패치에서 변경하지 않음

서버 updater는 RisuAI 내부에 설치된 플러그인을 바꾸지 않습니다. 서버 배포본 적용과 별도로 `PROGRAM/plugins/HAYAKU_Locator_Continuity.js`, `PROGRAM/plugins/Flashback_Memory.js`를 RisuAI에서 직접 갱신해야 합니다. 기존 DATA를 새 ZIP의 빈 DATA로 덮어쓰지 마세요.

## HAYAKU — 서버 단독 누락 복구

과거 누락 패킷의 복구 자료를 한 개의 큰 JSON에 저장하던 방식 대신, 작은 인덱스와 복구 항목별 스냅샷으로 저장합니다. 누락 자료 전체가 4 MiB를 넘더라도 전체 JSON을 서버의 한 항목으로 전송하지 않습니다. 서버의 단일 KV 4 MiB 제한은 유지합니다.

저장 순서:

1. 변경된 복구 항목의 새 스냅샷을 저장합니다.
2. 각 항목을 다시 읽어 내용과 해시를 검증합니다.
3. 검증된 참조만 작은 루트 인덱스에 게시합니다.
4. 과거 세대의 더 이상 참조되지 않는 스냅샷은 유예 기간 이후 정리합니다.

기존 단일 Vault는 읽기만으로 삭제하거나 덮어쓰지 않습니다. 다음 저장 때 새 조각을 검증한 뒤 루트를 전환합니다. 전환 전 실패하면 기존 단일 Vault가 그대로 남습니다. 새 형식의 읽기에 실패한 경우 이를 빈 복구 목록으로 간주하지 않습니다.

lease·복구 승인·해제 등 특정 항목 변경은 해당 항목만 읽고 저장합니다. 다른 항목의 원문 전체를 매번 다시 쓰지 않습니다. 복구 자료의 원문 보관 조각, 패킷, 보관 아카이브는 이 임시 세대 정리의 대상이 아닙니다.

서버 연결 오류, 저장 거부, 읽기 검증 실패는 단계와 원래 진단 코드를 보존합니다. 선행 저장 실패를 ‘복구할 누락 없음’으로 표시하지 않으며, 선행 저장이 실패한 경우 LLM을 호출하지 않습니다.

### 백업·서버 이관

JSON 백업에는 현재 루트가 참조하는 조각만 포함합니다. 누락되거나 손상된 활성 조각이 있으면 백업 검증을 중단하고 실패를 알립니다. 오래된 임시 세대 조각은 현재 복구 자료처럼 내보내지 않습니다.

서버 논리 이관 시 일시적인 lease/승인 권한을 지우는 기존 정책을 유지합니다. 조각 내부의 권한을 지운 뒤 해시를 다시 계산하며, 이 과정으로 손상된 원문을 정상 데이터처럼 만들지 않도록 입력 조각을 먼저 검증합니다.

### 제한

복구 자료 전체의 4 MiB 초과는 해결하지만, 개별 항목 하나가 직렬화된 저장 한도까지 커지면 명시적인 크기 오류로 보류합니다. 안전 한도를 무작정 올리거나 원문을 잘라서 저장하지 않습니다. 새로운 분할 저장 형식으로 전환한 후 예전 HAYAKU를 함께 활성화하지 마세요.

## Flashback — 현재 채팅과 기존 기억 연결

실제 활성 캐릭터/채팅 ID가 없는 경우 ‘현재 활성 채팅 없음’으로 처리합니다. 첫 채팅을 임의로 현재 채팅으로 선택하거나, `Current Character / Current Chat`이라는 가짜 저장 스코프를 만들지 않습니다. 단순히 채팅에 진입하거나 GUI를 여는 것만으로 미사용 채팅을 기억 목록에 등록하지 않습니다.

복사본을 먼저 열어도 legacy/persona 스코프의 원본 후보를 탐색합니다. 호스트가 제공한 같은 원본 채팅의 정체성과 저장된 대화 지문을 대조하여 후보를 연결합니다. 원본 기억을 바꾸지 않고 검증된 복사 대상에만 기억을 승계합니다. 제목이나 메시지 수만 같다는 이유로 다른 대화의 기억을 복사하지 않습니다.

원본 기억이 나중에 저장되면 현재 채팅을 이동하지 않아도 비어 있는 복사 대상의 연결을 제한적으로 재평가합니다. 옵저버가 이미 작업 중이거나 일시적인 저장소 오류가 발생한 경우 재평가 신호를 소모하거나 옵저버를 영구 중단하지 않습니다.

## 필름 보관함

### 선택 삭제

미리 전체 ‘목록 상태 검사’를 실행하지 않아도 여러 스코프를 선택할 수 있습니다. 실제 삭제 시 선택된 항목을 다시 확인합니다. 서버 오류·저장소 열거 실패·손상 상태는 데이터 없음으로 간주하지 않으며 해당 항목은 보존합니다. 현재 채팅은 다중 선택 삭제 대상에서 제외합니다.

### 안전 정리

- `빈 목록·저장소 선택`: 목록 잔재 및 검증된 빈 저장소를 확인하고 선택합니다.
- `선택 항목 안전 정리`: 선택된 항목을 실행 시점에 다시 검증하고 정리합니다.
- `고아 기억 선택`: 원본 채팅이 없는 것으로 확인된 기억을 선택만 합니다. 실제 기억 삭제는 별도 확인 후 진행합니다.
- 분류 필터: 기억 저장소 / 정리 후보 / 고아 기억 / 전체.

안전 정리는 실제 기억, 공유 아카이브, 벡터, 이전 복구용 매니페스트, 은퇴된 세계선 기록, 현재 실행 중 작업을 가진 항목을 임의로 지우지 않습니다. 알 수 없는 물리 키가 있으면 비어 있다고 확정하지 않습니다.

고아 판정은 **현재 캐릭터에 대해 완전하게 읽을 수 있는 호스트 채팅 목록**에 한합니다. 다른 캐릭터나 일부만 읽힌 채팅 목록에서 ‘못 찾았다’는 이유로 고아로 확정하지 않습니다. 따라서 이 버튼은 전체 RisuAI 데이터베이스의 무조건적인 고아 삭제기가 아닙니다.

### 검사 결과

- `정상 manifest 확인`: 정상적으로 읽고 검증한 수.
- `메타데이터 실제 보정`: 기존 목록 캐시의 의미 있는 정보가 실제로 바뀐 수.

이미 정상인 항목을 다시 검사한 경우 보정 건수는 0입니다. 검사 자체를 마치 모든 항목을 복구한 것처럼 표시하지 않습니다.

## 독립 사이드 패널

- 기억 유지보수: 상태 진단 및 유지보수 실행.
- 원문 수정 동기화: 변경 감지, 비교, 명시적 승인 및 반영.
- 기억 복원: JSON 백업, 복원 및 채팅 이사.

기존 동작을 복제해 중복 UI를 만들지 않고, 원래 컨트롤과 이벤트 연결을 각 독립 패널로 옮겼습니다. 원문 변경을 사용자 동의 없이 적용하는 기능은 추가하지 않았습니다.

## 검증 범위

자동 회귀의 실제 실행 결과는 배포 시 제공하는 보고서와 로그가 기준입니다. HAYAKU 실제 HTTP/SQLite 테스트는 서버 단독/로컬 단독의 대용량 복구 결과를 비교하며, 모델 제공자 응답만 테스트용으로 고정합니다. Flashback Chromium 테스트는 실제 플러그인 소스의 DOM·이벤트·확인창을 실행하며 RisuAI 호스트 API 경계는 테스트용 구현입니다. Windows/macOS/Termux와 실제 RisuAI 앱의 실기기 검증은 테스터 범위입니다.
