# LIBRA 검색·리콜 후속 패치 (2026-11-11)

## 확인 자료

사용자가 제공한 `libra-debug-2026-11-10 (12).json`의 Classic 전달은 40개,
7,489자였고 리콜 준비·최종 검증에 28.47초가 걸렸다. 로그의 본문 내용은 이 문서에 복사하지 않는다.

## 변경

- Micro frontier가 현재 `family`/`turn` 행과 기존 `kind`/`turnRange` 행을 모두 인식한다.
  원문 근거만 있는 Micro는 `source_only`로 전달하며 분석 완료로 표시하지 않는다.
  작업 결과에는 스코프를 붙여 다른 채팅의 게시 상태를 현재 frontier에 섞지 않는다.
- State의 첫/마지막 턴, evidenceSpans, 승인·후보·투영 메타데이터는 독립 사실이나
  중첩 검색 본문으로 펼치지 않는다. 실제 필드의 근거 객체와 근거 키는 유지한다.
- 질문 관련 신호가 없는 State에는 기본 가점·권위 순위 신호를 부여하지 않는다.
  축별 최소 전달은 유지하므로 질문과 무관한 장면 정보가 모두 사라지는 정책은 아니다.
- 렌즈의 직접 관련 후보를 장면 유지 후보보다 먼저 선택한다. 관련도 기준 미달 장면
  후보는 같은 렌즈·같은 인물 그룹당 하나로 제한한다. 서로 다른 인물, 관련도 기준을
  통과한 후보, 렌즈 40% 배분은 유지한다.
- 혼합/현재 질문에서 동일 근거를 공유하고 내용도 정확히 같은 사실의 중복을 억제한다.
  과거·정확한 발언 질문의 원문 선택은 유지한다. 비슷한 문장만으로 근거를 합치지 않는다.
- 선택 결과의 State 권위·미확정 사유, 유형 배분, 중복 억제 수, 스냅샷·의미 검색·렌즈·정본·Micro·
  검증 소요 시간을 진단에 남긴다. Classic 디버그 내보내기의 `recallDiagnostics`에서도 확인한다.
- 각 Micro 후보에서 반복하던 마지막 호스트 컨텍스트 읽기는 선택 전체의 최종 검증으로
  맡긴다. 소스·스코프·승인·저장소 변경에 대한 최종 전달 검증은 유지한다.
- 불확실한 Micro 계획은 `runtime_changed`, `restore_generation_changed`,
  `invocation_history_unproven` 사유와 `manual_retry_required`를 남긴다.
  자동 모델 재호출 제한은 유지한다. 복구 실행은 기존 원문 재분석 경로의 책임이다.
- 원본 턴 집계에는 실제 전달 행과 유형별 단위를 넣는다. 현재 공개 행에는 원본 메시지/
  리비전 식별자가 없으므로 원본 턴 수는 계속 `unknown`, 완전 집계는 `null`이다.
  기록 턴 번호를 원본 식별자로 추정하지 않는다.

## 검증과 한계

최종 실행 로그: `.development/recall-patch-20261111/final-tests.log`.
엔진, Classic/GRADIA 전달, 세 저장 모드, State 투영, 원문 변경 거부, 의미 검색,
렌즈 인물 유지·예산, frontier, Micro 불확실 작업의 무호출 처리를 검증한다.
문법과 `sync_libra_state_memory.cjs --check`, `git diff --check`도 확인한다.

기존 `libra_micro_stage_retry_test.cjs`는 폐기된 수동 API 때문에 수정 전 HEAD와 수정본
모두 6/30 통과이며 실패 항목 24개가 동일하다. `libra_recall_diagnostic_owner_test.cjs`의
폐기된 그래프 자원 오류 코드 기대도 양쪽에서 동일하게 실패한다. 이 패치로 해당 API를 복구하지 않는다.
예산 DOM 테스트는 기존 `PROGRAM/build-support/node_modules`를 `NODE_PATH`로 지정해 실행한다.

실제 RisuAI 설치 교체, 원격 제공자 호출, 기존 T21/T25 저장 데이터 복구는 수행하지 않았다.
첨부 로그의 `plan_boundary_changed` 발생 당시 경합은 저장된 디버그 스냅샷만으로 재현할 수 없어
해결됐다고 주장하지 않는다. 실환경 28.47초가 얼마나 단축되는지는 새 로그로 측정해야 한다.
작업 시작 전에 있던 LIBRA.js의 읽기 컨텍스트/캐시 변경은 보존했다.

## 서버 왕복 수 축소 (2026-11-11 후속)

요청 훅 전체를 구간별로 재면, 계산 시간은 수십 ms이고 나머지는 서버 왕복이다.
읽기 캐시(20초)가 만료된 뒤의 요청이 실제 다음 턴에 해당하므로 그 조건에서 잰다.
53턴 서버 fixture에서 요청 1회의 서버 왕복은 292회 → 37회다.

| 구간 | 변경 전 | 변경 후 | 바꾼 것 |
|---|---:|---:|---|
| State 검색·검증 | 264 | 12 | 아래 세 항목 |
| 저장된 대화 원문 확인 | 20 | 2 | 최근 10턴의 receipt head·본문을 두 번의 묶음 읽기로 |
| 질의 근거 확인 | 20 | 1 | 사용한 receipt를 한 번의 묶음 읽기로 다시 확인 |
| 주입 직전 검증 | 10 | 7 | 방금 직접 읽은 키는 닫는 확인에서 제외 |

- State 투영(`projectActiveMicroStateForResponse`)은 턴마다 다섯 기록(receipt head·본문,
  Micro head·본문·작업)을 하나씩 읽었다. 읽기 프레임이 있으면 head를 먼저 묶어 읽고,
  head가 가리키는 기록을 다시 묶어 읽는다. 턴별 검사는 그대로 그 바이트 위에서 실행한다.
- 같은 투영이 검색마다 LIBRA 저장소의 전체 키 목록을 받아왔다. 이제 해당 스코프·세계선의
  Micro head와 State 승인 결정만 접두어로 조회하고, 한 프레임 안에서는 한 번만 조회한다.
- 정본 후보 본문을 한 번에 묶어 읽고, 후보별 근거 기록은 8개씩 나란히 읽는다. 결과는 순위
  순서로 보관하므로 도착 순서가 선택에 영향을 주지 않는다.
- Classic 요청 훅은 주입 전에 항상 전달 증명을 실행하므로, 검색 자체의 닫는 확인은 그 증명에
  맡긴다(`diagnostics.readFrame: deferred`). GRADIA와 직접 호출은 기존대로 검색 안에서 확인한다.
- 예산이 없는 읽기 프레임의 묶음 크기를 32 → 128로 올렸다(서버는 512키, 응답은 바이트로 분할).

검증 범위는 줄이지 않았다. 원문·스코프·승인·저장소 변경은 전달 증명에서 거부한다.
`libra_state_memory_runtime_test.cjs`가 캐시 만료 뒤 요청 수(60 이하), 전체 키 목록 조회 0회,
턴별 단건 읽기 상한을 고정한다. 변경 전후 567개 테스트 파일 비교에서 새로 실패한 파일은 없다.

합성 fixture는 정본이 1개이고 Micro 48턴이 State Head보다 앞서 있어 실제 채팅과 구성이 다르다.
실환경 28초가 얼마나 줄어드는지는 새 디버그 로그의 `recallDiagnostics.timings`로 확인해야 한다.
"채팅 분기와 기억 기록 대조" 구간은 fixture에서 1~2회뿐이라 이번 변경 대상이 아니다.
