# 보안과 복구

- 서버는 loopback HTTP만 허용하고 공식 plugin ID에 결속된 서명 capability token으로 인증합니다.
- bootstrap은 server master token을 노출하지 않습니다. 일반 owner는 자기 namespace만 읽고 쓰며, RE:TRACE의 peer/manager 교차 namespace 접근은 읽기 전용입니다.
- admin/manager 헤더는 권한 증명이 아닙니다. 관리 API는 `DATA/runtime-token.txt`에 접근할 수 있는 로컬 관리도구의 master token을 추가로 요구합니다.
- API key/credential 계열 key는 서버 저장 대상에서 제외하고 서버도 민감 key를 거부합니다.
- 새 스코프는 항상 plugin_only입니다.
- 저장 모드는 스코프별이며 서버 URL만 플러그인 전역입니다.
- 서버를 사용하는 스코프가 남아 있을 때 전역 URL 변경을 차단하여 DATA가 두 서버로 분리되는 것을 막습니다.

## 선택적 Compute 보안 경계

- Compute는 사용자 token/pairing 입력이나 Storage bootstrap 없이 loopback의 `/v1/compute/bootstrap`으로 직접 자동 인증합니다. 사용자가 `shadow` 또는 `prefer_server`를 선택하는 것이 네트워크 연산의 명시적 opt-in입니다.
- `DATA/config/compute-signing-key.txt`는 30분짜리 Compute token 서명에만 사용하는 서버 내부 비밀입니다. 플러그인에 전달하지 않으며 `DATA/runtime-token.txt`와 역할·서명 키·권한을 공유하지 않습니다.
- 구 `compute-pairing-key.txt`가 남아 있으면 signing key 최초 생성 시 값만 이관해 기존 token 계보를 보존하며, 이후 플러그인 인증 입력으로 사용하지 않습니다. 상태 보존을 위해 구 파일은 자동 삭제하지 않습니다.
- signing key 원문은 HTTP 응답, health, 진단 journal, 디버그 export에 기록하지 않습니다. 서버는 시작 로그에 파일 경로만 표시합니다.
- Compute bearer는 `roles: ['compute']`, 빈 read/write namespace 권한만 갖습니다. Compute token으로 Storage API를, Storage token으로 Compute API를 호출하면 거부합니다.
- 자동 bootstrap은 Storage와 같은 loopback·공식 plugin ID 신뢰 경계를 사용합니다. plugin ID 헤더는 암호학적 코드 서명이 아니므로 악성 로컬 프로세스를 구분하는 강한 신원 증명은 아닙니다.
- 서버는 allowlist operation만 Worker에서 실행합니다. 임의 JS/eval, module/file 경로, shell 명령 실행을 받지 않습니다.
- Compute Plane에는 canonical SQLite repository나 DATA 경로를 전달하지 않습니다. 결과는 candidate이며 owner 플러그인이 fingerprint, digest, binding과 현재 상태를 검증한 뒤에만 채택합니다.
- signing key 파일이 손상되면 덮어쓰지 않고 Compute만 503으로 닫습니다. Storage 서버와 KV는 계속 동작합니다.
- 전체 DATA 재해 백업에는 signing key 파일을 포함하되, clean 배포 ZIP·지원 로그·외부 공유 자료에는 runtime token, signing key, DB, 운영 backup을 포함하지 않습니다.

## 서버 장애

- plugin_only는 서버와 무관하게 동작합니다.
- mirror는 로컬 정본을 보존하고 서버 복귀 후 보충합니다.
- server_only는 서버 DATA를 권위 저장소로 유지하며 서버가 없을 때 스코프 메모리 I/O를 fail-closed합니다.
- 서버 장애가 플러그인 GUI, 서버 연결 페이지 또는 등록된 훅 자체를 없애지 못합니다. routing registry와 plugin-global UI 설정은 로컬에서 읽고 서버 확인은 비동기·실패 허용으로 수행합니다.
- Compute local은 서버와 무관한 zero-network 경계입니다. prefer_server에서도 서버 중단, overload, timeout 또는 검증 실패 시 같은 로컬 kernel을 정확히 한 번 실행합니다. 이는 server_only 저장 데이터가 오프라인에서 생긴다는 뜻은 아닙니다.

## 현재 스코프 pluginStorage 삭제

삭제 전에 현재 스코프의 namespace SQLite integrity, 서버 record/tombstone coverage와 value parity를 확인합니다. 하나라도 실패하면 삭제하지 않습니다. 병존 모드에서는 현재 스코프만 server_only로 전환된 뒤 삭제합니다.

다른 스코프, routing registry, credential, plugin-global 설정, 실제 RisuAI Persona와 공유 기반 자료는 삭제하지 않습니다.

## 현재 스코프 복구

서버 단독 스코프의 `서버 → pluginStorage 복구`는 현재 스코프 record만 복원하고 readback을 검증합니다. 서버 단독에서 plugin_only로 전환할 때도 복구 검증을 먼저 수행합니다.

서버 DATA 전체 백업은 서버를 종료한 뒤 DATA 폴더를 통째로 복사하면 됩니다.

## Recovery Safe Mode와 crash-safe restore

- SQLite 손상으로 정상 서버가 열리지 않으면 일반 저장 API를 제공하지 않고 복구 전용 모드로 기동합니다.
- 복구 모드에서는 백업 목록, scrub, restore plan, restore, shutdown만 허용합니다. plugin bootstrap/KV/scope mutation은 차단합니다.
- 복원 전 선택 namespace의 현재 raw DB와 scope catalog를 `DATA/backups/recovery-quarantine/`에 그대로 보존합니다. 손상 파일도 자동 삭제하지 않습니다.
- 복원은 `restore-transaction.json` journal을 사용합니다. 프로세스가 PREPARED/INSTALLED/VERIFIED 단계에서 죽으면 다음 기동이 원래 DB로 rollback합니다. COMMITTED 이후라면 새 DB를 유지하고 잔재만 정리합니다.
- 서버가 시작되지 않는 특수 상황에서는 `admin.cjs restore-offline ... --yes`를 사용합니다. 자동 복원은 하지 않으며 사용자가 명시적으로 backup ID와 namespace를 선택해야 합니다.
- 더 새로운 DATA layout/schema를 오래된 PROGRAM이 연 경우는 Recovery Safe Mode로 우회하지 않고 기존처럼 쓰기 없이 실패합니다.

## Backup 건강도와 보존

- `scrub`은 manifest, SHA-256, SQLite integrity, scope catalog JSON/digest를 검사합니다.
- auto backup은 최신 12개, 일별 7개, 주별 4개 세대를 유지하여 최근 오류와 오래된 오류 모두 복구할 수 있게 합니다.
- 자동 backup은 DATA 내부의 재해 복구점입니다. SSD/드라이브 자체 손상에 대비하려면 서버 종료 후 DATA 전체를 다른 물리 위치/NAS/외장 드라이브에 추가 복사해야 합니다.

## RE:TRACE 승계와 서버 스코프 삭제

RE:TRACE 1.9.59에는 provider 설정·호출 기능이 없습니다. 초기화 직후, 선택적 IPC·UI 등록을 기다리기 전에 과거 RE:TRACE가 사용한 `memory_session_bridge:settings:v1`과 `memory_session_bridge:settings_local_backup:v1` 두 키만 background에서 정확히 삭제하며, 다른 플러그인이나 RisuAI의 provider 설정은 건드리지 않습니다. 각 저장소 호출은 제한 시간과 최대 2회 시도를 적용하고 삭제 후 부재 readback을 확인합니다. 삭제 거부·시간 초과·잔존은 디버그 export의 credential purge 상태와 warning에 기록되지만 LIBRA·HAYAKU·Flashback·LIA IPC나 RE:TRACE UI 시작을 막지 않습니다. 배포 API는 Flashback·HAYAKU·LIBRA·LIA의 범용 IPC dispatcher를 노출하지 않으며, 각 내부 dispatcher도 조회·승계·명시적 삭제에 필요한 고정 allowlist 밖의 액션을 전송 전에 거부합니다. 이 두 credential 키는 삭제 후에도 서버 DATA 전송 denylist에 남습니다. 다음 세션 승계에서는 owner별 Librarian System handoff proof를 확인하며 RE:TRACE가 peer payload를 임의로 해석·수정하지 않습니다. 원본 세션은 승계 전후 불변이어야 합니다.

활성 또는 고아 후보 스코프의 서버 복사본을 삭제하기 전 owner 플러그인이 그 **대상 스코프만** 반대편 저장소에 복원하고 plugin_only로 전환했음을 증명합니다. 서버는 `DATA/backups/deleted-scopes/<backup-id>/`에 namespace SQLite snapshot을 만든 뒤 revision/digest 조건부 mutation을 실행합니다. 승계 조상, inbound reference, 확인 불가, 보존, 범위 불완전 스코프는 차단됩니다.


## 서버 진단 로그 개인정보 보호

`DATA/logs/server-debug*.jsonl`에는 다음 항목만 기록됩니다.

- operation/route, namespace, space
- scopeId SHA-256 앞 16자리
- key 종류, key SHA-256 앞 16자리, key 길이
- request/value/response bytes, item count
- revision, digest 앞 16자리, tombstone 여부
- 지연시간, HTTP status, 안전하게 축약된 오류 코드

다음은 기록하지 않습니다.

- RP·채팅·메모리·Persona 본문
- 원본 storage key와 원본 scope ID
- API key, service-account JSON, Authorization/Bearer token
- 실제 저장 value

로그는 DATA에 속하므로 DATA 폴더 백업에 함께 포함됩니다.

일반 owner 플러그인은 자기 namespace·현재 스코프의 구조화된 event만 받을 수 있습니다. suite-global process text log는 다른 owner의 진단을 포함할 수 있으므로 일반 owner endpoint에서는 항상 제외합니다.

RE:TRACE manager 디버그 내보내기만 `startup.log`, `startup-error.log`, `server.log`가 존재할 경우 각각 최근 240줄·최대 약 32,000자 범위의 tail을 함께 받을 수 있습니다. 서버는 내보내기 전에 줄 길이를 제한하고 Bearer token, URL query token, API key·authorization·secret·password·credential 형태를 `[REDACTED]`로 바꿉니다. 원본 로그 전체나 runtime token 파일은 내보내지 않습니다.

외부에 디버그 JSON을 전달할 때도 메모리/채팅 본문과 credential을 포함하지 않는 위의 제한·비밀 제거 형태만 기본 포함됩니다.
