# Explicit source reanalysis through shared repair orchestration

Main-request source tracking now observes changes and protects affected ranges without calling owner reanalysis. Historical saved `auto` tracking values remain compatible but mean detection only. Rule changes, declined work, failures, interrupted runs, and restarts do not grant automatic model permission.

Each owner has one MemorySuiteHealthRecovery.createOrchestrator instance shared by derived-cache controls and explicit selected-source work. inspect and preview are model-free. An explicit reanalysis preview holds the private source/scope proof; apply consumes the public ticket before awaiting and reuses existing owner execution:

- LIBRA: existing selected canonical ranges and runManagedScan source_edit route
- HAYAKU: existing selected turn picker and targeted regeneration route; ordinary selected missing-turn recovery remains its existing flow
- Flashback: selected tasks in the existing source-history card and existing verified raw replacement route; no summary model is introduced

Original raw/evidence and prior versions retain their existing immutable ownership. Unchanged source, scope, identity, revision, and explicit selection are revalidated before publication. Close/scope/request changes revoke source proof. Duplicate applies are single-flight; completed model tickets cannot be reused. The owner-wide in-flight latch remains until work finishes even after close. Cache retries retain existing bounded/idempotent semantics.

Explicit canonical save can complete while derived embedding remains pending. The owner embedding queue keeps its original lifecycle guards: source, scope, or canonical-reference changes prevent old vectors from attaching. Pending is not a claim that all vectors are ready.

Flashback's new shared health adapter reads strict local metadata without invoking storage preparation, migration, provider probes, or physical repair. It remains an incomplete metadata check. The older physical automatic-maintenance button is unchanged and is not represented as a safe derived-cache operation. Full physical-maintenance unification needs a separately typed adapter.

No live Risu/provider validation or all-product acceptance is implied by this candidate.
