# HAYAKU 패킷 안전망 (2026-10-16)

응답 모델이 RP 응답과 숨은 HAYAKU 패킷을 함께 쓰는 현재 방식은 그대로 둔다. 누락 복구는 한 단계로 줄였고, 패킷이 왜 빠지는지 사용자가 볼 수 있게 했다.

## 복구 단계: 3단계에서 1단계로

이전 구조:

1. afterRequest 자동 복구: 패킷이 없거나 못 쓰는 상태면 응답 처리 안에서 Other Ax(RisuAI 보조 모델)를 1회 호출해 복구한다.
2. 실패 복구 자동 처리(3.0.61): 코드에는 남아 있었지만 이미 퇴역 상태였다(`failedAutoMode = () => 'off'`). 설정 화면의 안내만 살아 있었다.
3. 백그라운드 자동 복구: 누락 턴의 Recovery Journal 항목마다 확인창을 띄우고, 승인하면 Other Ax를 1회 더 호출했다. 같은 날 오전 커밋에서는 건너뛴 턴의 확인창을 생략하게 바꿨다.

지금 구조:

- **자동 복구는 afterRequest 1회뿐이다.** 누락 패킷 하나에 Other Ax 호출은 많아야 1회다(`maxPhysicalCalls: 1`). 성공하면 패킷을 응답에 넣어 정상 경로와 같이 기록된다.
- 실패했거나 건너뛴 턴(보조 모델 연결 테스트 중, 원문 미확정, 요청 계보 없음)과 설정을 끈 경우의 턴은 Recovery Journal에 원문이 보존된다. 이 턴들은 복구 화면의 수동 복구나 실패 복구 화면의 수동 채택·LLM 복구·직접 수정으로 처리한다.
- 백그라운드 복구 예약(`scheduleNativeRecoveryDebtRepair`)은 실패 복구 자동 처리와 같은 방식으로 퇴역시켰다. 이제 아무 작업도 예약하지 않는다. 확인창, 자동 승인, 타이머도 없다.
- `hayaku_background_auto_repair`와 `hayaku_native_auto_repair`는 무시된다. 기존 저장값이 있어도 오류는 나지 않는다. 설정 화면과 복구 화면에서 해당 항목을 지웠고, 간편 설정 목록은 8개가 됐다. 설정 저장 스키마에는 `retired` 표시로 남겨 저장할 때 값을 보존한다.
- 복구 화면의 afterRequest 설명을 "유일한 자동 복구 단계"로 고쳤다. 작성 현황 안내의 "실패 복구 자동 처리가 다시 시도" 문구는 실제 동작과 달라 "자동 재시도는 하지 않으니 수동 복구"로 바꿨다.

## 바뀌는 점

- 한 턴의 최대 자동 비용은 Other Ax 1회로 고정된다. 이전에는 확인창을 승인하면 2회째 호출이 생겼다.
- 확인창이 더 뜨지 않는다.
- afterRequest가 건너뛴 드문 턴은 이제 자동으로 복구되지 않는다. 복구 화면의 누락 턴 수와 작성 현황 카드의 "건너뜀" 항목으로 확인한 뒤 수동 복구하면 된다.

## 패킷 작성 현황

`패킷 · 세계선 → 이번 패킷 작성` 카드 아래에 현재 채팅의 최근 작성 결과를 집계해 보여 준다. 범위는 이번 세션의 최대 60턴이다.

| 항목 | 의미 |
| --- | --- |
| 메인 모델이 정상 작성 | 응답 모델의 패킷을 바로 쓸 수 있었음 |
| 패킷 생략 | 패킷 표시가 전혀 없음 |
| 패킷 잘림 | 시작 표시만 있고 끝이 없음(출력 길이 부족 가능성) |
| 형식 오류 | JSON·schema·계보 검사 실패 |
| 보조 모델 복구 성공 / 실패 / 건너뜀 | afterRequest 복구 결과와 건너뛴 사유 |

반복되는 원인에는 할 일도 함께 표시한다.

- 잘림이 실패 턴의 1/3 이상이면 응답 최대 토큰(출력 길이)을 늘린다.
- 생략이 실패 턴의 1/3 이상(최소 2턴)이면 프롬프트 방식을 전체(full)로 바꾸거나 지시를 잘 따르는 모델을 쓴다.
- 보조 모델 복구가 실패하면 복구 화면에서 수동 복구한다. 계속 실패하면 RisuAI 보조 모델 설정을 확인한다.

기록은 메모리에만 두고 저장하지 않는다. 새로고침하면 초기화된다.

## 확인 범위

- `tests/hayaku_packet_safety_net_test.cjs`:
  - 백그라운드 예약과 실패 자동 처리가 퇴역했는지 확인한다.
  - GUI에 백그라운드 항목이 없는지 확인한다.
  - afterRequest가 1회 호출만 하는지 확인한다.
  - 작성 현황 집계와 안내를 확인한다.
- `tests/hayaku_recovery_confirmation_queue_test.cjs`: 누락 항목을 예약해도 타이머, 확인창, 호출이 생기지 않는지 확인한다.
- `tests/hayaku_after_request_recovery_journal_runtime_test.cjs`: 실패한 턴과 afterRequest를 끈 턴 모두 Journal은 남고, 추가 호출과 확인창은 생기지 않는지 확인한다.
- `tests/hayaku_gui_ux_contract_test.cjs`: 백그라운드 제어가 GUI에 없는지 확인한다.
- `tests/hayaku_settings_easy_view_test.cjs`, `tests/hayaku_settings_gui_transaction_test.cjs`: 퇴역한 `hayaku_background_auto_repair`는 화면에 보이지 않는 숨은 입력으로만 남는다. 설정을 저장해도 기존 저장값이 그대로 유지되는지 확인한다.
- HAYAKU 관련 테스트 162개를 변경 전 코드와 나란히 실행했다. 새 실패는 없다. 변경 전 실패 10개 중 2개(`hayaku_capture_delta_runtime_test`, `hayaku_inline_ledger_readset_runtime_test`)는 이번에 통과했고, 8개는 그대로다.
- 실제 RisuAI와 실제 보조 모델로는 측정하지 않았다.

## 하지 않은 것

- 응답 모델 대신 보조 모델이 매 턴 패킷을 쓰는 분리 작성 모드(선택하지 않음).
- afterRequest 복구의 즉시 재시도. 응답 표시가 그만큼 늦어진다.
- 확인창 관련 코드 삭제. 진입점만 막았다. 수동 복구 경로(`runNativeRepairSweep`)는 그대로 쓴다.
