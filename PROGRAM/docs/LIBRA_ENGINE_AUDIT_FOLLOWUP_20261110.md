## 긴 채팅: 요구사항은 아직 충족하지 못함

`PROGRAM/tools/libra_memory_graph_corpus.cjs`의 `policy()`는 `limit:20`, `maxWindows:64`를 기본값으로 쓰며, 명시적으로 지정해도 `maxWindows`는 128까지만 허용한다. `enumerate()`는 누적 구간 수가 상한에 이르면 `window_budget`으로 구축을 실패시킨다. 이 값은 작업 한 회의 분할 크기가 아니라 전체 corpus 상한이다.

`maxWindowsPerStep`와 체크포인트/재개 기능은 이미 있지만 전체 `maxWindows` 상한을 없애지는 않는다. 자동 구축은 `{incremental:true,resume:true}`를 전달하고 기본 전체 상한을 사용한다. 새 패치의 30분 재시도 억제는 반복 비용 완화이며 긴 채팅 지원은 아니다. 타이머가 30분 뒤 반드시 실행되는 것도 아니다. 이후 예약 트리거가 재시도 가능 시간을 확인한다.

남은 구현은 전체 과거 구간을 보존하면서 구축 작업과 검색 검증의 메모리 사용을 나누는 것이다. 구간 수만 늘리면 중간 직렬화 4 MiB, 인덱스 16 MiB 기본 제한, 페이지 수 및 읽기/디코드 예산에 다시 걸릴 수 있다. 원본·게시본 검증에서도 `maxWindows`를 사용하는 경로가 있어 함께 바꿔야 한다. 첫 구간만 검색하고 전체 검색으로 표시하는 우회는 요구를 만족하지 않는다.

## 서버 모드: 구축·증분·검색은 지원, 게시 후 자동 정리가 빠짐

`memoryGraphCorpusContext()`는 서버 모드에서 `server_storage` backend를 제공한다. `scheduleDurableIndexBuild()`는 모드에 따른 차단 없이 같은 `buildMemoryGraphCorpus()`를 증분·재개 옵션으로 호출한다. 서버 모드 영속 corpus를 구축하고 검색하며 재시작 후 다시 읽는 런타임 테스트가 통과했다.

`buildMemoryGraphCorpus()`의 게시 후 정리는 `indexeddb`일 때만 `collectLocalMemoryGraphGarbage()`를 호출한다. `host_storage`는 자동 정리 불가 상태를 반환하고, `server_storage`는 정리 호출 없이 결과를 반환한다. 따라서 이전 보고서는 서버 그래프 미지원이 아니라 **서버 자동 구축·증분·수동 구축 후 이전 파생 페이지의 자동 정리 누락**을 뜻한다.

서버의 수동 `collectMemoryGraphGarbage()`는 GC lease를 얻고 원자적 도달 가능성 검사로 고아 페이지를 삭제한다. 수동 정리 테스트 3건이 통과했다. 원본 기억 삭제와는 다르다. 서버 `libra-graph-lifecycle.cjs`는 GC lease와 읽기/구축 lease를 배타적으로 처리한다. 이미 읽는 중이면 정리가 `blocked_active_leases`로 물러나지만, GC 중에 새 읽기가 오면 `LIBRA_GRAPH_NAMESPACE_BUSY`로 거절될 수 있다. 자동 정리를 붙이려면 idle 예약과 읽기 우선 양보/대기, 여러 클라이언트 경쟁 처리 및 재시도가 필요하다.

## 테스트 변경 및 검증

- 새 상설 그래프 탭으로 이동하는 GUI 테스트는 이전 작업자가 이미 수정했다. 이번에는 수동 정리 버튼의 노출도 검사하도록 보강했다. 실제 DOM에서 탭 전환·설정 저장·재구축·게시 상태를 검증한다.
- 페이지 읽기 테스트는 자동 구축이 fixture 준비 중 저장소를 초기화하는 경쟁을 제거하도록 해당 테스트에서만 자동 구축 예약을 끈다. 읽기의 원본 검증·캐시·무쓰기·무공급자 호출 검사는 유지한다. 자동 구축은 별도 테스트로 검증한다.
- Live Tail/이야기 시각 테스트는 제거된 항목 번호·종류 태그 대신 새 섹션·시각·본문 줄 형식을 검사한다. 근거 본문 보존 검사는 유지한다.
- 집중 묶음: GUI/자동 구축/화면 모델/corpus 런타임 15/15 통과. 별도 수동 정리 3/3 통과.
- 실제 Chromium IndexedDB 테스트: 두 탭, 프로세스 재시작, 원자적 롤백, 읽기 pin 보존 및 해제 후 정리 통과. 샌드박스 내 Chromium 연결 실패 후 외부 실행에서 확인했다.
- 최초 진단 실행에서는 기본 임시 폴더의 `EPERM` 및 Chromium 연결 제한이 발생했다. 작업 트리 루트에서 실행한 차이도 발견하여 이 결과를 최종 비교에 사용하지 않았다.
