# GRADIA 인풋 작성기 맥락 정비

날짜: 2026-10-22 · GRADIA `0.26.6` · LIBRA 묶음 크기 조절은 이번 범위에서 제외

## 우선순위

1. 직전 상황에 정확히 이어지는 것
2. 정확도에 필요한 만큼만 맥락을 주는 것

## 바뀐 점

### 직전 상황

- **마지막 응답 인정 규칙.** 종전에는 마지막 assistant 응답이 이번 세션의 출력 영수증(메모리, 최대 256개)과 일치해야만 직전 상황으로 쓰였다. 그래서 RisuAI를 새로 열거나, 마지막 응답을 수정했거나, GRADIA를 끈 채 생성된 응답이면 **그 이전 응답**이 직전 상황으로 들어갔다.
  - 작성기는 응답이 끝난 화면에서 실행되므로, 이제 화면에 보이는 마지막 응답을 그대로 쓴다.
  - 스트리밍 중·오류·코멘트·비활성·빈 응답은 예전처럼 제외한다.
  - 초안 파이프라인(SHADOW)의 엄격한 완료 규칙은 그대로다.
  - 실행 기록 `lastInputAssistContext.terminalProof`에 근거가 남는다(`settled_visible_reply`, `verified_completion`, `closed_conversation_boundary`).
- **직전 유저 입력.** 마지막 응답이 답한 유저 입력을 최대 600자, "이미 일어난 일" 블록으로 함께 준다. 로어 검색 질의에도 포함한다.
- **짧은 응답 보충.** 마지막 응답이 800자 미만이면, 그 앞 응답의 끝부분을 직전 장면 예산(2,400자)의 남은 만큼 "이전 맥락" 블록으로 앞에 붙인다.
- 블록 순서는 시간순이다: 이전 맥락 → 직전 유저 입력 → 직전 장면 → 현재 입력.

### 로어

- 작성기 로어 패킷은 이미 본문 3,200자 안에서 **항목 단위**로 선별된다. 그런데 프롬프트에서 렌더된 블록(제목 포함)을 다시 3,200자로 잘라 마지막 항목이 중간에서 끊겼다(`…[truncated]`).
- 이제 선별된 블록을 그대로 넣고, 비정상적으로 긴 경우에만 6,400자 안전 상한을 적용한다.

### 하야쿠·플래시백

- 작성기 요청(proposal)에서는 두 소유자의 기록이 합쳐서 8,000자 안의 **완전한 기록**만 들어간다. 첫 기록 하나는 항상 넣어서, 종전에 쓰이던 근거가 사라지지 않게 한다.
- 순서는 기존과 같다: 소유자별 최신 2개 → 현재 입력과의 BM25 관련도.
- LIBRA 묶음은 손대지 않았다.
- 기억 근거에는 작성기용 사용 지침을 붙인다.
  - 기억은 과거 상태이며, 다음 입력의 타당성을 판단하는 데만 쓴다.
  - 지금 장면이 어디인지는 직전 장면이 정한다.
  - 기억 속 장면을 재개하자고 제안하지 않는다.

### 정리

- 은퇴한 Story Arc의 작성기 프롬프트 코드를 제거했다(항상 비어 있던 블록과 `arcInputManagerPromptBlock`).

## 계측 (오프라인 호스트, 가짜 모델)

| 상황 | 변경 전 | 변경 후 |
|---|---|---|
| 12턴 채팅, 마지막 응답에 영수증 없음 | 11번째 응답을 직전 장면으로 사용 | 12번째(실제 마지막) 응답 + 그 직전 유저 입력 |
| 마지막 응답 35자 | 11번째 응답만 | 마지막 응답 + 직전 유저 입력 + 앞 응답 끝 1,952자 |
| 로어 1,000개 | 마지막 항목이 잘림 | 항목 7개 전부 완전 |
| 로어 100 / 3,000개 대기 시간 | 0.3 / 6.5초 | 0.3 / 6.1초 (선별 비용은 그대로) |

## 남은 일

- LIBRA 묶음의 작성기용 크기 힌트(LIBRA 쪽 프로토콜). 묶음이 4만 자면 지금도 작성기 프롬프트의 대부분을 차지한다.
- 로어가 수천 개일 때의 대기 시간. 작성기 창을 열 때 직전 장면 기준으로 선별을 미리 시작하는 방안은 이 계측을 보고 결정한다.
