# 원문 수정 추적 패치 및 재감사

LIBRA 2.3.107 · HAYAKU 3.0.112 · Flashback 1.0.73
공통 Source Edit Consent SDK 1.3.1

## 수정 결과

| 이전 감사 항목 | 패치 | 재검증 |
|---|---|---|
| F1: 이전 applied 기록으로 변경된 의존 근거의 쓰기를 허용 | 현재 unit과 이전 작업의 digest, sourceDigest, basis, identity 전체를 비교. 불일치는 새 허가가 필요한 임시 보호 대상으로 처리 | HAYAKU 실제 소유 경로에서 후속 턴의 canWrite가 true → false. OFF에서도 네 필드 각각의 변경을 차단하며 추적 저널을 새로 만들지 않음 |
| F2: 재활성화 이후 새 기억의 후속 영향 누락 | 기준점에 없는 직접 수정도 후속 영향 플래그에 반영 | HAYAKU 실제 생산자가 반환한 T2·T3가 모두 기록됨. 이전에는 T2만 등록. OFF 기간 누적을 소급하지 않는 기존 검사도 통과 |
| F3: 열린 확인창의 승인이 다음 요청 완료 대기를 우회 | 요청 진입 시 즉시 세대를 갱신하고 실행을 보류. 승인 반환 후·검증 후·실행 상태 저장 후·실제 실행 직전에 새 요청 여부 확인 | 다음 afterRequest 이전 Other Ax 모의 호출은 1 → 0회. 요청 완료 뒤 새로 승인하면 1회 정상 처리 |

이미 실행이 시작된 소유 작업은 기존 허가로 저장 확인까지 마무리한다. 새 요청이 들어왔다는 이유로 저장 트랜잭션 중간의 허가를 제거하지 않는다. 다음 항목은 실행하지 않고 재확인 대상으로 남긴다.

## 재감사에서 추가 확인한 경계

- 원문 snapshot을 읽기 전, 요청 훅 입구에서부터 이전 승인을 막는지 확인했다. LIBRA·HAYAKU·Flashback의 진입 경로에 연결했다.
- 확인창이 열린 동안 다음 요청이 시작된 뒤 완료되더라도, 이전 승인은 자동 재사용하지 않는다.
- running 저널 저장 도중 요청이 시작되면 모델 호출 전에 중지하고 작업을 interrupted로 남긴다.
- 실제 소유 실행 중 요청이 시작되면 현재 작업의 저장 확인은 유지하고 다음 작업을 중지한다.
- 본문 digest뿐 아니라 의존 근거나 메시지 식별만 달라진 경우도 과거 applied 허가를 재사용하지 않는다.

## 검증

관련 회귀 검사 45개 통과, 실패 0개. 여기에는 기존 원문 근거·승인·저장·재시작·모드 전환·모바일 GUI·z-index 검사와 신규 감사 회귀가 포함된다.

새 검사:

- tests/source_tracking_audit_regressions_test.cjs — 기존 공통 재현 F1/F2/F3를 정상 동작의 회귀 조건으로 전환.
- tests/source_tracking_hayaku_patch_test.cjs — 실제 HAYAKU snapshot 생산자와 소유 원장으로 F2 확인.
- tests/source_tracking_hayaku_guard_patch_test.cjs — 승인·저장 후의 실제 HAYAKU 의존 근거 변화로 F1 확인.
- tests/source_tracking_hayaku_request_patch_test.cjs — 실제 HAYAKU 재처리 경로의 F3 차단과 요청 완료 후 재승인 확인.
- tests/source_tracking_modes_test.cjs — 필드별 변경, 요청 진입·저장 중·실행 중 경계 추가.

세 플러그인의 공통 SDK 내장본과 원본 동기화를 확인했다. 원본 감사 재현 파일과 당시 실패 결과는 비교 자료로 보존했다. 제품의 기존 기억이나 사용자 저장 데이터는 수정하지 않았다.

이번 재감사 범위에서는 이전 결함 3건이 해소됐고 추가 회귀는 발견되지 않았다. 실행 검증은 격리 저장소·모의 호스트/모델과 Chromium 모바일 모의 환경에서 수행했다. 실제 RisuAI 기기, 실서버 및 외부 모델의 실사용 검증이나 모든 동시 요청 조합에 대한 보증은 아니다.
