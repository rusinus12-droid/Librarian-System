# GRADIA 인풋 작성 지연 분석 보고서

- 작성일: 2026-10-31 (Asia/Seoul)
- 대상: GRADIA 0.28.8 / 현재 체크아웃의 LIBRA 2.6.13
- 범위: 사용자가 제공한 단일 실행 로그와 현재 소스의 읽기 전용 분석
- 상태: 원인 후보 및 개선안 보고. 성능 패치·실제 호스트 재현은 수행하지 않음

## 1. 결론

이번 실행의 가장 큰 지연은 모델 호출 전에 발생했다. 실행 시작부터 논리적 `input_assist` 호출 시작까지 91.729초가 걸렸고, 이 안에서 기억 준비 진단은 82.869초를 기록했다. 실제 제공자 시도는 1회이며 재시도는 없다.

소스에서는 GRADIA의 다층 현재성 검사, 세 owner의 순차 조회·검증, LIBRA의 그래프 및 렌즈 재검증, RisuAI 원문 스냅샷 재로딩이 확인된다. 이 구조가 지연을 증폭하는 유력한 원인이다. 다만 owner별 소요 시간과 검사 횟수가 로그에 없으므로 82.869초를 특정 owner 또는 함수 하나의 비용으로 단정할 수 없다.

우선 조치는 구간별 계측과 동일 요청 내부의 중복 검증 공유다. 모델 변경, 로어 예산 확대, 타임아웃 연장만으로 해결하려는 접근은 현재 증거와 맞지 않는다. 이전 버전의 동일 조건 실행 자료가 없어, 어느 변경부터 느려졌는지는 확정하지 못했다.

## 4. 인풋 작성과 기억 사용 흐름

### 4.1 공통 흐름

1. 현재 캐릭터·채팅·DB 스냅샷을 읽고 직전 장면과 로어 참고자료를 구성한다.
2. 제출 전 입력 제안임을 나타내는 proposal과 원문 지문을 만든다. 제안을 이미 발생한 사건이나 정본으로 채택하지 않는다.
3. 모델 문맥 한도를 확인하고 기억 읽기 세션을 연다.
4. 연결된 owner의 기억을 수집하고 무결성·스코프·현재성을 검사한다.
5. 중복 제거·관련도 정렬·예산 선택을 거쳐 모델 요청에 넣는다.
6. 모델 호출 전후, 선택 결과 전달 및 복사 과정에서 변경 여부를 재확인한다.
7. 취소·종료 시 요청에 묶인 근거와 파생 런타임 내용을 정리한다.

### 4.2 owner별 최초 조회

| owner | 읽는 자료 | 특징 |
|---|---|---|
| LIBRA | 통합 그래프 조회 결과와 별도 비정본 렌즈 근거 | owner가 조회 결과를 묶어 전달하고 그래프·렌즈 일관성을 검증 |
| HAYAKU | 공개된 기억 원장의 활성·과거 선택 기록과 패킷 원문, 명시적으로 참조된 상속 아카이브 | slot head·삭제 표시를 반영하고 패킷 형식·해시·참조를 확인 |
| Flashback | 공개 manifest와 기록 shard, 명시적으로 참조된 상속 아카이브 | 자동 응답 기억·자동 에피소드 인덱스를 대상으로 수동 GUI·자동 정적 기억 등을 제외 |

첨부 로그의 서버 연결 경로에서는 LIBRA가 `unified_engine`, HAYAKU와 Flashback이 `server_logical_read`를 사용한다. HAYAKU·Flashback에 별도 LLM 분석이나 자체 벡터 검색을 요청하는 경로가 아니다. 각각의 공개 기억을 서버에서 읽고 GRADIA가 후보를 선별한다. 이 설명을 별도 `plugin_ipc` 모드의 transport 구현과 혼동하면 안 된다.

### 4.3 GRADIA의 선택과 모델 전달

- 내용이 같은 기억은 해시와 원문을 비교해 중복 제거하고, 기여 owner의 provenance를 보존한다.
- owner별 최근 후보를 먼저 배치한다. 이후 입력·직전 장면으로 만든 query에 대한 BM25 관련도, 남은 후보의 순환 배치를 적용한다. 이 정렬에는 LLM 호출이 없다.
- HAYAKU·Flashback 기록은 작성기에서 합산 8,000자 기준을 적용한다. 첫 기록은 이 기준을 넘더라도 전체 근거 예산에 맞으면 허용한다. 이후 기록은 잘라 넣지 않고 완전한 단위로 선택·생략한다.
- LIBRA 묶음은 위 8,000자 기록 합산에서 제외되지만 전체 근거·모델 문맥 예산은 적용된다.
- 실제 요청 본문을 기준으로 원문과 중복되는 근거 및 문맥에 들어가지 않는 근거를 추가 제외할 수 있다.

따라서 세 owner가 연결됐다는 사실만으로 세 owner의 기억이 모두 최종 모델 요청에 포함됐다고 판단할 수 없다. 이번 로그는 취소 후 관련 내용이 정리돼 실제 선택 개수·본문을 확인할 수 없다.

### 4.4 이후의 변경 확인

HAYAKU·Flashback의 서버 `current` 경로는 최초에 읽은 저장 항목들의 revision·digest·삭제 여부 등 메타데이터와 데이터 인스턴스·reset epoch를 비교한다. 매번 본문을 재검색하거나 압축 아카이브를 다시 해제하는 구조는 아니다.

LIBRA의 `current`는 owner transport를 거쳐 그래프 근거 검증과 렌즈 스냅샷 확인으로 이어진다. 활성 렌즈가 있으면 렌즈 기록·벡터 저장소·상속 아카이브 등을 다시 읽어 지문을 계산하는 경로가 있다. 두 종류의 검증 비용을 동일하게 취급하면 안 된다.

1.5초 현재성 검사 공유는 `coalesce: true`로 호출되는 일부 경로에만 적용된다. 다른 경로는 직접 재검증하며, 모델 전송 시 기존 검증 결과를 무효화한다. 이미 공유 장치가 있다는 이유로 중복 비용이 해소됐다고 볼 수 없다.

HAYAKU·Flashback은 최종 프롬프트에 일부 기록만 넣더라도 최초에는 공개된 대상 기록군과 연결된 아카이브를 예산 한도 내에서 읽어온 뒤 GRADIA에서 선별한다. 저장량에 따라 최초 조회·해시·정렬 비용이 커질 가능성이 있다. 이번 로그에는 corpus 크기가 없어 그 기여도는 미확정이다.

## 6. 오해하기 쉬운 로그

- `expected.displayedTotalCalls: 10`: 일반 호출 계획값이다. 실제 이번 실행에서 10번 호출했다는 뜻이 아니다.
- `runs: 0`, `stageTrace: []`: 별도 인풋 작성 telemetry에 실제 호출이 기록돼 있다. 이 값만으로 미실행이라고 판단하면 안 된다.
- `lastInputAssist: null`, 빈 결과: 취소·종료 시 요청 근거와 파생 내용을 지우는 경로가 있다. 빈 값만으로 모델이 아무것도 생성하지 않았다고 단정할 수 없다.
- `reference_packet_budget_omission`, `capacity=12000`: 로어 참고자료의 선택·생략 경고다. 12,000 토큰의 모델 문맥 제한을 의미하지 않는다. 해당 기록은 기억 준비 진입 시점에 이미 남아 있어 82.869초 전체를 이 경고 탓으로 돌릴 수 없다.
- `configured_model_context`, 기억 준비 `ready`: 이번 실행은 문맥 한도 미확인 때문에 기억 조회가 차단된 사례와 다르다.
- GUI 렌더 최대 14ms: 기록된 설정 GUI 렌더는 짧지만, 작성기 전체 UI 응답성과 host bridge 성능을 증명하는 지표는 아니다.

## 7. 개선안과 우선순위

### P0. 계측을 먼저 분리

다음 항목을 동일 request ID로 연결해 본문·인증정보 없이 기록한다.

- 단계별: native snapshot, 로어 준비, 문맥 preflight, owner capture, 후보 정렬·선택, 요청 예산 계산.
- owner별: capture/current 횟수·누적/최대 시간, 항목 수·본문 바이트·dependency 수.
- LIBRA 내부: 그래프 검증, 렌즈 스냅샷 검증 시간과 읽기 횟수.
- 모델: 실제 transport 전송·응답 수신·파싱 완료 시점. 제공자가 제공하는 경우 입력·출력 사용량.
- UI: 선택 화면 표시, 검증 시작/완료, 선택 확정, 최종 확인 표시, 복사·취소 시점.
- 취소 후 자원 정리 시간 및 늦게 도착한 작업의 종료 여부.

이 계측으로 82.869초와 제공자 시도 29.885초를 실제 작업별로 설명할 수 있어야 한다.

### P1. 동일 요청 내 중복 검증 공유

하나의 논리적 경계에서 동일 근거·대화·설정에 대해 중첩 호출하는 검증은 진행 중 Promise와 검증 결과를 공유하도록 한다. 단순한 전역 TTL 확대가 아니라 요청·근거 revision·binding generation·dispatch 상태를 기준으로 설계한다.

모델 전송, 응답 수신, 사용자 편집·재생성, 최종 복사처럼 외부 상태나 제안이 바뀔 수 있는 경계에서는 필요한 최신 검증을 수행한다. 취소·스코프 이동·설정 변경·저장 모드 전환·reset·기억 변경 시 공유 결과를 폐기한다. 삭제·복원·기억 변경 감지를 약화해 속도를 얻어서는 안 된다.

### P2. LIBRA와 native 원문 검증의 읽기 비용 축소

LIBRA는 렌즈 본문·벡터 전체를 반복 지문화하는 비용을 revision 기반 확인으로 대체할 수 있는지 검토한다. 해당 revision이 모든 쓰기·삭제·복원·이관·외부 변경을 포괄한다는 계약이 먼저 필요하다. 이를 보장할 수 없는 저장 경로는 기존 검증을 유지한다.

native 대화·로어도 신뢰할 수 있는 변경 지표나 동일 검증 범위의 스냅샷을 활용할 수 있는지 검토한다. 다른 플러그인의 로어 변경을 놓치는 요청 간 TTL 캐시를 성급하게 추가하지 않는다.

### P3. 최초 조회량 축소와 owner 병렬화

HAYAKU·Flashback은 공개 manifest·원장을 기준으로 최근 후보와 필요한 기록을 먼저 제한해 읽는 계약을 검토한다. 상속·삭제·선택 버전·관련도·완전한 기록 단위가 유지돼야 한다. 조회량 축소는 검색 결과를 바꿀 수 있으므로 단순 성능 변경보다 엄격하게 평가한다.

owner 병렬화는 이후 검토한다. 현 구현은 남은 corpus/raw 예산을 순차적으로 배분하므로 단순 `Promise.all` 교체로는 충분하지 않다. 합산 상한, 부분 실패 정리, 공통 스코프·reset 검증과 결과 순서의 결정성을 유지해야 한다.

### P4. 진행 상태와 통계 개선

실제 진행 상태를 대화·로어 준비, owner별 기억 확인, 모델 생성, 선택 대기로 나누어 표시한다. 작성기 전용 예상 호출 계획을 사용하고 자동 처리 시간과 사용자 검토 시간을 분리한다. 표시 개선 자체를 성능 개선으로 계산하지 않는다.

## 8. 권하지 않는 우선 조치

- 타임아웃만 늘리기: 대기 실패를 늦출 뿐 반복 작업량을 줄이지 못한다.
- 로어·근거 예산부터 늘리기: 최초 읽기와 모델 입력 비용이 커질 수 있다.
- 특정 모델명에 대한 예외 최적화: 주된 병목은 호출 전 공통 읽기 경로다. 문맥 예산은 설정·검증된 모델 메타데이터를 기준으로 유지한다.
- HAYAKU·Flashback 또는 현재성 검사를 일괄 비활성화하기: 기능·안전 계약을 바꿔 얻은 시간 절감을 동일 품질 개선으로 취급할 수 없다.

## 9. 검증 계획과 완료 기준

### 9.1 기능·변경 감지 검증

- 같은 입력·스냅샷·근거에서 후보 순서와 최종 선택 내용이 유지되는지 확인한다.
- 모델 호출 전후 기억 수정·삭제·복원, 채팅 이동, 로어 변경, reset·모드 변경 시 오래된 근거 전달이 차단되는지 확인한다.
- 선택지 편집·번역·재생성·복사·취소 경로를 확인한다. 취소 후 늦은 응답이 결과를 되살리지 않아야 한다.
- 각 owner 단독·세 owner 조합, 빈 기억·큰 기록·상속 아카이브·예산 초과를 확인한다.
- server 경로와 `plugin_ipc` 경로를 별도로 검증한다. 한 경로의 fixture 성공을 다른 경로의 실제 호스트 성공으로 간주하지 않는다.

### 9.2 성능 비교

동일 채팅·입력·모델·로어·기억 설정으로 변경 전후를 반복 비교한다. 기억 조합별로 최초 실행과 반복 실행을 나눠 중앙값·최대값을 기록한다. 반복 수가 충분하지 않으면 p95 같은 백분위 수치는 제시하지 않는다.

성공 판단은 첫 선택 화면까지의 자동 처리 시간, 실제 모델 전송 전 시간, owner별 current 횟수·누적 시간, 읽기 바이트 감소로 한다. 사용자 검토 시간은 제외한다. 실제 제공자 지연은 별도 기록해 서버/호스트 경로 개선과 구분한다.

첫 패치의 완료 기준은 주요 미계측 구간 해소, 동일 경계의 중복 current 감소, 변경 감지 계약 유지다. 목표 초 수와 절감률은 live baseline을 확보한 뒤 정한다. 이 보고서는 특정 시간 이내 완료나 개선률을 보장하지 않는다.
