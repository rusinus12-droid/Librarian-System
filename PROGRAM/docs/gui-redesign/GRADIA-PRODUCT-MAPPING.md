# GRADIA mockup adoption: product mapping and evidence

Scope: GRADIA only. `ensureSettingsShell()` mounts the app DOM copied from `gradia.html`; the view uses the mockup's `suite.css`, `themes.css`, and GRADIA inline CSS embedded in `GRADIA_MOCKUP_STYLE`. The prototype toolbar and sample overlay templates are omitted; the product creates a live overlay host and only puts product dialogs in it. `assets/suite.js` is not loaded. The sample results/list rows are replaced by `Runtime.stageTrace` or an explicit empty state.

In 0.26.10, the Skill view presents nine responsive genre cards with short staging copy and localized skill names. Actual library descriptions are shown in a read-only dialog. ## Specific control-level compromise

As of GRADIA 0.26.9, automatic Skill routing, numeric priorities and Top-K competition are retired. The Skill tab uses explicit stage selections, optional explicit reference documents and selection order. Basic quality rules remain an independent fixed layer. Old numeric preferences are archived and never interpreted as selected skills. Nine user-applied genre presets populate explicit selections. Whole compiled skill/reference text is capped at 24,000 characters and 10% of the model safe input estimate; the complete real request is admitted separately without truncating core draft sources.

Input Assist's scope/confirmation/target/lore controls were absent from the approved mockup's visible main cards. They are exposed in a collapsed detail fold inside the existing Input Assist stage destination. The existing LIBRA Hosting Bridge controls were also absent from the mockup; they are placed in a collapsed detail under Management > 전문가 설정 because removing them would remove an existing setting and host-bridge action. These additions use existing destinations and leave the mockup's primary visual structure intact.

## Source cleanup and visual comparison

The production shell uses `GRADIA_MOCKUP_MARKUP` from the approved mockup. Old full-screen GUI builders/navigation/style and unused provider editor builder were removed; no old-screen DOM fallback is mounted. Remaining `sga-rp-gui-root` names are host-container IDs. Standalone product confirmation flows use the mockup `.overlay` and `.dialog` classes; no compact-modal marker or second product screen remains. No prototype `suite.js` is loaded. Search for the retired `.sga-redesign-app` root and old builder names returned no active view fallback. The separately registered storage-management panel (`openManagementDialog()` / `mountConnectionPanel()`) is a manager-owned surface outside this GRADIA settings view: it retains its own `.mscx*` panel CSS and is not launched from this view. The platform `promptInput` fallback also remains for the case where the host cannot provide a GUI confirmation container; that Risu-owned prompt cannot take mockup CSS.

The storage-management panel remains independently reachable through its registered RisuAI menu button (`registerManagementButton()`), and owns synchronization, server restore and plugin-storage deletion workflows; it is not a hidden GRADIA settings fallback. Its `.mscx*` panel and `.ms-dialog-card` use their separately registered manager implementation. The storage-mode transition fallback also invokes the platform's native `confirm`; neither platform-owned prompt API accepts the mockup dialog stylesheet.

Savebar uses the exact mockup DOM and suite CSS. The earlier 2px discrepancy came from the test host lacking `<!doctype html>` and running in quirks mode. With both sides in `CSS1Compat`, app, topbar, sidebar, page body and savebar dimensions match at 1440×1000, 820×1000, 390×844, 900×900 and 640×900. No production CSS geometry override was added. Captures move the pointer outside the app to avoid a retained hover on the previously clicked navigation item.
