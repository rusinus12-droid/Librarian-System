## 9. 아직 남은 것 / 정직한 한계

1. **제품 통합 검증은 하지 않았습니다.** 감사 §12의 "제품 통합 후 별도로 필요한 시나리오"(실제 API·저장·복구·취소·동시성·scope 보호)는 정적 목업 범위 밖이라 그대로 남아 있습니다.
2. **일부 항목은 감사 본문을 근거로 반영했고 제품 코드와 직접 대조하지 못했습니다.** 해당 표의 "감사 기준" 표시를 참고하세요. 특히 (a) LIA 생성 모드별 논리 요청 수(2/3회) (b) HAYAKU 실패 기억의 수리 3방식 세부 (c) GRADIA 전문가 설정의 세부 항목명 (d) LIBRA 복구 5종의 세부 동작. 실제 구현 전에 코드와 한 번 더 대조해야 합니다.
3. **개별 선택 UI의 깊이는 대표 항목까지만 보여줍니다.** 예: LIA 캐릭터·모듈 로어북을 항목 단위로 고르는 화면, LIBRA 분석 입력 규칙의 모든 옵션, HAYAKU 설정 48개의 값 범위 검증은 "위치와 의미"만 보여주며 모든 값을 구현한 것은 아닙니다.
4. **상태 표현은 대표 시나리오 위주입니다.** 부분 성공·결과 불명·차단·미저장은 RE:TRACE·Flashback·HAYAKU·LIBRA·LIA 핵심 경로에 넣었지만, 모든 기능×모든 상태 조합을 만든 것은 아닙니다. 로딩 상태는 거의 표현하지 않았습니다.
5. **접근성은 레이블 연결 + 기존 포커스/ESC 처리까지만** 확인했습니다. 실제 스크린리더, 키보드 전용 전체 순회, 화면 확대, 실기기 모바일은 검증하지 않았습니다.
6. 이 환경의 Chromium에서 한국어 글리프는 표시되지만 서체에 따라 줄바꿈 위치가 달라질 수 있습니다.

## 10. 2차 검토(커밋 a2c0644 대조) — 선택 → 확인 → 실행 결과 대상 일치

2차 검토에서 지적한 5건은 모두 "고른 대상과 확인·결과 화면의 대상이 다르다"는 같은 유형이었습니다. 지적된 화면만 고치지 않고, 대상 정보를 **선택 → 확인창 → 진행창 → 결과 → 다음 행동**까지 넘기는 공통 구조를 `suite.js`에 만든 뒤 6개 화면에 적용했습니다. 같은 유형의 불일치는 지적되지 않은 곳에서도 찾아 함께 고쳤습니다.

### 공통 구조 (`assets/suite.js`)

| 장치 | 역할 |
|---|---|
| `data-ctx` | 버튼이 여는 확인창·작업·페이지에 대상 정보를 넘김 |
| `data-fill` | 대상 값으로 텍스트·입력값을 채움. 값이 없으면 **원래 기본값으로 되돌려** 이전 대상이 남지 않음 |
| `data-variant` | 작업 종류에 맞는 단계·결과·다음 버튼만 보이게 함 (예: LIBRA 재생성은 "후보 보관" 단계와 "정본 변경 없음" 결과) |
| `data-inherit-ctx` | 확인창 → 진행창 → 비교창처럼 이어지는 창이 같은 대상을 물려받음 |
| 토스트 `{key}` | 완료 안내에 대상 이름을 넣음 |
| 작업 단계 문구 `ctx.labels` | 진행 중 문구에 대상(턴·구간·플러그인)을 넣음 |

이 과정에서 공통 버그 1건도 고쳤습니다. 완료 버튼이 여러 개인 작업창에서 첫 버튼만 활성화되던 문제입니다(LIBRA 누락 생성 완료 후 "확인" 버튼이 보이지 않던 현상).

## 13. 자체 감사 (외부 검토 없이 실시) — 우회 경로·결과 반영·고정 표시값

지금까지의 외부 검토는 주로 "정상 진입 경로에서 대상이 일치하는가"를 봤습니다. 이번에는 독립 감사자 두 명을 따로 두고 6개 시안을 다시 훑게 했습니다. 감사 대상은 정상 경로가 아닌 진입로(`?open=`, 상단 시연 바, 대상 없이 열리는 창), 작업 뒤 결과 반영, 고정 문구입니다. 감사 보고서 두 개의 항목은 브라우저에서 재현한 89건과 코드로만 본 의심 22건, 모두 111건입니다. 처음에 적은 "95건 모두 고침"은 정확하지 않았습니다. 항목별 상태는 §14의 `verification/findings.tsv`가 기준입니다.

### 공통 구조 (`assets/suite.js`)

| 문제 | 수정 |
|---|---|
| `?open=` 창이 화면 데이터보다 먼저 열림 (빈 목록, TypeError) | `suite:ready` 다음에 `?open=`·`?sub=` 처리. 작업창은 `runJob`으로 연다 |
| 대상 없이 열린 확인창이 표본 대상을 보여 주고, `{name}` 같은 원시 문자열로 성공을 알림 | `data-require="키…"`: 대상 키가 없으면 실행 버튼을 잠그고 이유를 표시. 토스트는 닫히는 창의 대상으로 채우고, 채울 값이 없으면 "실행하지 않았습니다"로 바꿔 표시 |
| 최소화·Esc로 닫은 작업을 다시 열 방법이 없음 (HAYAKU 후보 비교 단계에 도달 불가 — P0) | **작업 트레이**: 진행 중이거나 끝났지만 확인하지 않은 작업을 상단에서 다시 연다 |
| 같은 작업창에서 진행 중인 작업을 다시 시작하면 이전 작업이 사라짐 | 진행 중이면 새로 시작하지 않고 진행 중인 창을 연다 |
| 기본값 불러오기가 토스트만 띄움 | `data-load-defaults`: 처음 연 시점의 값으로 실제로 채우고 저장 전 변경으로 남김 |
| 즉시 바뀌면 안 되는 선택지(서버 전환 등)가 클릭만으로 바뀜 | `data-readonly`: 현재 값 표시 전용, 누르면 이유 안내 |
| 저장 단계 중에도 취소 버튼이 활성 | `data-cancel-until`: 해당 단계부터 중단 버튼 잠금 |
| 메뉴에 없는 하위 화면(편집·에셋)의 미저장 변경이 안 보임 / 닫힌 서랍의 미저장 변경이 안 보임 | `data-unsaved-for`로 상위 메뉴에 표시. 서랍을 여는 버튼에도 ● 표시 |
| 저장 뒤에도 메뉴 툴팁 "저장하지 않은 변경 N개"가 남음 | 툴팁 정리 |
| 입력 확인 활성화가 화면마다 따로 있어 Flashback 복원에서 동작 안 함 | 공통 처리로 이동 |
| 숫자·영문 이름 뒤 조사 | `suiteJosa()` (v1을, v3으로, v2를 …) |

같은 유형으로 RE:TRACE `?open=job-next`도 '다음 세션' 확인창을 건너뛰고 있어 같은 규칙으로 막았습니다. 18개 작업창 전부를 `?open=`으로 열어 확인한 결과는 다음과 같습니다.

- 정식 경로에도 확인 단계가 없는 3개(Flashback 다국어 검증, LIA 후보 만들기, RE:TRACE 백업)만 시작됩니다.

### 증거 묶음 `verification/`
- `run_all.sh`: 시나리오 스크립트(`scripts/`)를 브라우저에서 실행하고 시나리오별 원본 결과(`results/*.json`)와 `results/summary.tsv`를 남깁니다.
  - 시나리오마다 빈 페이지를 거쳐 새로 엽니다. 이전에는 같은 파일의 해시만 바꿔 열면 페이지가 다시 로드되지 않아 앞 시나리오 상태가 남았습니다.
- 최신 실행: 86회, 이름 붙은 검사 350개가 모두 통과했고 페이지 JS 오류는 0건입니다.
  - 여기에는 대상 없이 모든 확인창 실행, `?open=` 22가지, 작업창 18개, 정적 점검 7개, 6개 파일 × 3개 폭의 가로 넘침 검사가 포함됩니다.
- `findings.tsv`: 감사 보고서 두 개의 모든 항목(111건)과 6차 검토 4건, 같은 유형 1건, 모두 116행입니다. 각 행에 상태와 근거 검사를 적었습니다.
  - `check_findings.js`는 근거로 적은 검사가 최신 결과에 없거나 실패이면 실패합니다(현재 0건).
