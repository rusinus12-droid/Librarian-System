# 원문 재분석 실패·State 자동 반영·메모리 사용 점검

## 근거와 확인 범위

- 사용자 디버그 `(4).json`, `(5).json`, RisuAI의 `Out of Memory` 화면을 확인했다. 첨부 자료는 진단 데이터로만 취급했다.
- 해당 채팅의 로컬 SQLite를 `DatabaseSync(..., {readOnly:true})`로 조회했다. 실제 DATA/정본/Micro/사용자 설정은 수정하지 않았다. 원문과 모델 응답은 이 문서와 테스트에 싣지 않는다.
- 클라우드 생성 요청 없이 격리된 VM·임시 서버·JSDOM으로 검증했다. 실제 RisuAI에서 재분석 완료와 OOM 해소를 재현 확인한 것은 아니다.

## 재분석 실패

정본 source_edit 작업은 T1~5를 revision 3으로 저장했고, T6~10은 `LIBRA_GRAPH_READER_BODY_CHANGED`로 실패했다. 이전 T6~10 revision 2는 보존됐다. 전체 새 재분석 성공이나 T6~10의 새 모델 응답 성공으로 해석하면 안 된다.

이 오류는 읽은 물리 데이터와 마감 재검증 시 데이터가 달라졌을 때 발생한다. 디버그에는 변경된 키·스택이 없어 어느 저장 키가 직접 원인이었는지는 확정하지 못했다. 코드에는 이전 배치의 Micro State 재판정이 다음 배치와 동시에 실행되는 경로, 원문/인물 후보 준비의 일시적 읽기 충돌을 곧바로 전체 배치 실패로 올리는 경로가 있었다.

수정:

- 정본 이후 Micro State 재판정은 해당 scope의 정본 쓰기 큐가 끝난 뒤 실행한다. 같은 scope의 요청 범위를 합쳐 한 작업으로 처리한다.
- 영수증 준비, 정본 원문 읽기, 인물 후보 읽기는 읽기 충돌 때 새 프레임으로 최대 2회 재시도한다. 모든 종료 검증을 다시 수행하며 변경된 결과를 그대로 승인하지 않는다.
- 일반 작업과 모델 호출은 이 재시도에 포함하지 않는다. 계속 바뀌는 데이터는 여전히 실패한다. 영수증 준비는 기존의 멱등적 원문 검증/저장 경로를 사용한다.

## State는 전체 정상 상태가 아니었다

읽기 전용 DB 조회 시 저장 Head:

| 영역 | 상태 | 반영 턴 |
| --- | --- | --- |
| 인물 | ready | T10 |
| 관계 | ready | T10 |
| 세계 | ready | T10 |
| 서사 | not_updated / unified_bindings_pending | T5 |

T10은 이전 정본을 포함한 현재 활성 체인의 도달 턴이다. 이번 재분석의 T6~10 성공 증거가 아니다. 서사에는 `thread_anchor_evidence_missing` 2건이 남았다. 근거 없는 서사 연결을 강제 승인하지 않는다.

T1~5는 엔터티 25개·사실 57개를 승인했지만, 장소 엔터티 1개가 `UNIFIED_ENTITY_NAME_UNBOUND`로 거부되면서 위치 2건·세계 설명 1건·시각 1건이 연쇄 거부됐다. 이 사실들은 자동 반영으로 복구할 수 있는 승인된 사실이 아니다. 현재 T1~5 정본의 `character_preference`/`character_boundary` 사실 수는 각각 0이다. 이것이 원문에 선호/경계 근거가 없다는 뜻은 아니며, 저장된 정본 출력에 없다는 뜻이다.

활성 Micro 11턴의 관측은 190개, State intent는 31개다. 각 활성 관측의 가장 최근 저장 판정은 승인 7개, 이전값 대체 5개, 보류 14개, 저장 판정 없음 5개였다. 보류 14개는 정본 중첩 충돌 8개·값 근거 불충분 4개·장소 미해결 1개·순간 동작 조각 1개다. 저장 판정은 과거 basis일 수 있어 현재 화면의 최종 반영 수와 같지 않다.

자동 반영 결함도 있었다. 기존 코드는 정본 Head 전체가 ready일 때만 Micro 재판정을 예약했다. 서사 하나가 partial이면 정상인 다른 도메인도 재판정하지 않았다. 이제 성공한 정본 추적에서 Head가 있으면 예약하고, 개별 claim의 도메인·원문·정본 중첩 검증은 그대로 수행한다. 승인/보류 여부와 최신값 우선·이전값 보존 원칙은 유지한다.

## OOM과 겹치는 부하 경로

화면의 Out of Memory는 호스트 페이지의 메모리 부족 증거다. 프로세스 힙/할당 추적이 없어 단일 원인을 확정하거나 실제 OOM이 해결됐다고 단정할 수 없다. 디버그에는 2~4초대 main-thread long task가 반복 기록됐다.

확인한 코드 경로와 수정:

- State 자동 갱신은 100ms debounce만 있었고 실행 중인 수초짜리 갱신을 합치지 않았다. 느린 갱신 제어 실험에서 기존 코드는 6개를 겹쳐 실행했다. 수정 후 동시 실행은 1개이며, 대기 알림들은 다음 갱신 1개로 합친다.
- Micro 재분석은 매 턴 선택적 전체 State/그래프·벡터 투영을 요청했다. 선택 중에는 화면 갱신과 벡터 워밍을 미루고 선택 종료 후 갱신한다. 각 턴의 원문/Micro 저장과 State 판정은 계속 수행한다.
- volatile 전체 기억 그래프의 일반 스케줄러는 startup prewarm과 달리 기억 쓰기 작업 중에도 실행할 수 있었다. 이제 Micro/정본/재분석 작업 중에는 기다리고, 이미 실행 중인 선택적 빌드도 다음 yield 경계에서 양보한다.
- 관측·사실을 상위 N개로 선별하거나 삭제하는 메모리 절감 방식은 추가하지 않았다.

## 검증

- 신규 회귀 5개: 새 프레임 재시도, 지속 변경/일반 작업의 실패 유지, 느린 State 갱신 단일 실행, 쓰기 큐 대기·범위 병합, partial Head의 정상 도메인 재판정, 선택적 그래프 부하 대기를 확인했다.
- 수정 전 원본에서 읽기 재시도·갱신 단일 실행 검사가 실패했다. 갱신 제어 실험의 기존 동시 실행 수는 6이었다.
- 관련 11개 테스트 파일, Node test 기준 **27/27 통과**. plugin_only/mirror/server_only State matrix·자동 반영·정본/Micro 합성·리플레이·이전값 보존·읽기 fence·대기/취소 UI·volatile 그래프 회귀 포함.
- 로컬 개발 의존성은 `PROGRAM/build-support/node_modules`를 NODE_PATH로 지정했다. 첫 검사 환경의 임시 폴더 rename EPERM은 작업 폴더 내부의 전용 임시 경로로 옮겨 재검사했다. 제품 검증 조건은 완화하지 않았다.
- `node --check PROGRAM/plugins/LIBRA.js`, `git diff --check` 통과.

남은 실제 호스트 확인: 수정 파일을 로드한 RisuAI에서 같은 원문 재분석을 수행해 T6~10 새 정본 생성, 보류 원인 및 실제 State 표시, Micro 선택 완료, 프로세스 메모리 최대 사용량과 OOM 재발 여부를 확인해야 한다. 기존 저장 Head나 거부된 사실을 이번 코드 패치만으로 수정했다고 주장하지 않는다.
