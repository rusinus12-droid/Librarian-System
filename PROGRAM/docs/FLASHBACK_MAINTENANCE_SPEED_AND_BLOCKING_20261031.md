# Flashback 자동 점검·복구: 속도 저하와 반복 실행 차단 (1.3.13)

근거: `flashback-memory-debug-2026-10-31T04-41-46-048Z.json`, `DATA/logs/server-debug*.jsonl`
(04:39:15–04:41:10 구간 984건), 작업창 캡처, 로컬 재현(`flashback_maintenance_server_read_budget_test`).

## 1. 왜 느렸나

캡처의 작업은 **누락 1턴(11청크)** 복구에 115초가 걸렸다. 그중 제공자 임베딩은 8초였다.

| 구간 | 시간 | 실제 내용 |
|---|---|---|
| 원문 동기화 | 2→62초 | 턴 1개 수집 |
| 대기열 처리 | 62→94초 | 임베딩 8초 + 저장 |
| 최종 확인 | 94→115초 | 에피소드 갱신·재점검 |

서버 로그로 보면 같은 115초 동안 플러그인이 **135MB**를 GET 했다. 서버 처리 시간은 건당 1–5ms였다.

| 키 | 크기 | 읽은 횟수 |
|---|---|---|
| 범위 manifest `scope:*:manifest:v2` | 63KB | 391 |
| 범위 레지스트리 `scope_registry:v2` | 297KB | 36 (+ 쓰기 후 재확인) |
| manifest 백업 `:previous:v1` | 71KB | 36 |
| 로컬 벡터 샤드 | 최대 392KB | 7–24 |

원인은 세 가지가 겹친 것이다.

1. **읽기 캐시가 없다.** 커밋 한 번마다 manifest를 저장 경로·임베딩 작업 경계 검사·manifest 저장이
   각각 다시 읽는다. 로컬 재현에서는 한 턴 복구에 서버 호출이 503건이었고 그중 manifest 읽기가 171건이었다.
2. **커밋마다 writer fence를 따로 잡고 놓는다.** 그래서 매번 acquire/release 왕복이 생기고, 커밋 사이의
   결과를 재사용할 근거도 없었다.
3. **커밋마다 전역 범위 레지스트리 전체(297KB)를 다시 쓰고 다시 읽는다.** 이 레지스트리는 GUI 목록용
   인덱스일 뿐 저장 권위가 아니다.

여기에 RisuAI `nativeFetch` 전송이 느린 환경(기존 기록 참고)이 곱해져 분 단위가 됐다.

### 패치

- **fence 범위 읽기 캐시** (`fencedReadCaches`): 이 인스턴스가 만료되지 않은 writer fence를 잡고 있는
  동안에는 서버가 다른 소유자의 같은 alias 쓰기와 maintenance 쓰기를 모두 거부한다. 그래서 그 안에서 읽은
  값은 뒤에서 바뀔 수 없다. 이 동안의 GET만 캐시한다.
  - 우리 쓰기(set/remove/batch)는 요청을 보내기 **전에** 해당 키를 무효화한다. 키를 특정할 수 없는 쓰기는
    전체를 비운다.
  - 쓰기 epoch로, 진행 중이던 읽기가 쓰기 이전 값을 저장하지 못하게 한다.
  - 남은 리스가 15초 미만이면 캐시를 쓰지 않는다. fence가 닫히면 캐시도 버린다. 반환값은 복제본이다.
- **복구 한 번에 fence 하나** (`withMaintenanceWriterHeld`): 서버 턴 동기화와 임베딩 대기열 복구는
  시작할 때 fence를 한 번 잡는다. 내부 커밋은 그 세션에 합류한다. 세션에는 리스 갱신 heartbeat가 붙어서
  제공자 대기가 길어도 만료되지 않는다.
- **레지스트리 쓰기 지연**: fence를 잡은 동안의 레지스트리 갱신은 마지막 값만 모아 두었다가, 작업이
  끝날 때 한 번 쓴다.

결과(같은 재현): 서버 호출 503 → 165건, manifest 읽기 171 → 16건, 레지스트리 쓰기 12 → 1건.

## 2. 왜 자꾸 "실행 차단"이 되나

이번 덤프의 최종 판정은 `server_inspection_only / blocked / derived_schema_rebuild_required`였다.
`liveChunkSchemaMismatch 25`는 0.9.x 시절 기록 25개에 문장 청크 스키마 버전이 없다는 뜻이다.
원문과 벡터는 정상이다.

서버 모드에서 실행할 수 있는 전략은 턴 동기화, 임베딩 대기열, 에피소드 재구축 셋뿐이고 나머지는 모두
"차단"이 된다. 1.3.11은 이 경우에도 누락 턴 동기화는 열었다. 그러나 동기화가 끝나면 청크 문제만 남고,
**그 뒤의 모든 점검이 영구적으로 "실행 차단"이 됐다.** 지금까지의 반복 패턴은 늘 같았다. 새로운
파생/일시 조건이 하나 발견될 때마다, 그것을 처리할 서버 경로가 없어서 전체가 막혔다.

### 근본 대응

1. **파생 데이터는 서버 모드에서도 다시 만들 수 있게 한다.** 구형 청크를 가진 턴은 원문이 일치하더라도
   `diffLiveChatSourcesAgainstRecords(..., { rechunkLegacy: true })`에서 "변경 턴"으로 분류된다. 그러면
   기존 턴 동기화(`replaceTurnPair`, `reuseRecords`)가 현재 원문으로 다시 나눈다. 청크 텍스트가 같은
   벡터는 재사용하고 바뀐 청크만 다시 임베딩한다. 인계(상속) 기록은 건드리지 않는다.
   - 누락 턴이 없어도 `server_turn_sync`(reason `derived_chunk_rechunk_available`)가 선택된다.
   - 복구 결과에 `operation.sync.rechunkedTurns`가 남는다.
2. **일시 조건은 차단이 아니라 대기로 처리한다.** 다른 창이나 새로고침 전 페이지가 남긴 writer fence
   (최대 120초)는 지금까지 즉시 `FLASHBACK_WRITER_BUSY` 실패였다. 이제 복구 작업은 아무것도 쓰기 전,
   fence를 잡는 단계에서 최대 130초를 기다리고 재시도한다. 작업창에는 "저장 잠금이 풀리기를 기다립니다"
   단계로 보인다. 중지 요청이 들어오면 즉시 멈춘다.
   (설정 재쓰기 오탐 `HEALTH_SETTINGS_CHANGED`는 1.3.12에서 값 지문 비교로 이미 처리됐다.)

남은 차단은 실제 물리 손상(샤드 누락·개수 불일치·정제기 구버전·아카이브 무결성)뿐이다. 이런 경우는
서버 모드에서 자동으로 고치면 안 되므로 그대로 막는다.

## 3. 작업창

- 상태 카드: 현재 메시지와 대상·경과·마지막 보고를 한 블록에 묶고, 왼쪽 띠 색으로 진행/완료/주의/실패를 구분한다.
- 단계 카드: "진행 확인" 하나로 뭉뚱그리던 표시를 완료 / 진행 중 / 대기·필요 시 실행 / 해당 없음 / 실패로 나눈다.
- 큐 진행 카드: 제목·개수·백분율을 막대와 묶는다. 막대 색은 상태를 따른다.
- 카운터 4개를 개별 타일로 표시한다.
- 진행 내역: 한 줄에 하나씩 경과 시간 · 단계 태그 · 메시지를 보여 준다. 요청/응답 왕복은 `×N · 마지막 n초`로 접는다.
- 실행 결과: "항목: 값" 줄을 표 형태 행으로 바꾸고 판정 행은 강조한다.
