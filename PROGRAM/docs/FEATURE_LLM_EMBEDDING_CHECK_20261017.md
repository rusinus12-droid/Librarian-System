# 플러그인 기능 점검: 요청 전·요청 후·수동, 실제 LLM·임베딩 (2026-10-17)

실제 제공자: LLM은 Ollama Cloud `deepseek-v4.1-flash:cloud`(OpenAI 호환 `/v1/chat/completions`), 임베딩은 Voyage `voyage-4-large`. 키는 환경 변수로만 넘겼다. 각 플러그인은 실제 플러그인 파일을 VM 호스트에 올리고, RisuAI가 부르는 훅(`beforeRequest`, `afterRequest`, 채팅 `output` 리스너, `display`)과 공개 API·GUI 처리기를 그대로 호출했다. 판정은 반환 문자열이 아니라 플러그인 저장소·API를 다시 읽어서 했다.

| 플러그인 | 점검 도구 | LLM | 임베딩 |
| --- | --- | --- | --- |
| LIBRA | `tools/rag_eval/libra_e2e_eval.cjs --live`, `tools/rag_eval/libra_feature_check.cjs` | 사용 | 사용 |
| Flashback | `tools/rag_eval/flashback_rag_eval.cjs [--server] [--manual]` | 없음 | 사용 |
| HAYAKU | `tools/rag_eval/hayaku_feature_llm_check.cjs` | 사용 | 없음 |
| LIA | `tools/rag_eval/lia_feature_llm_check.cjs --provider custom\|ollama_cloud` | 사용(수동) | 없음 |
| GRADIA | `tools/rag_eval/gradia_feature_llm_check.cjs`, `tools/rag_eval/gradia_llm_grounding_eval.cjs` | 사용 | 없음(LIBRA 근거 사용) |

## LIBRA

| 시점 | 기능 | 결과 |
| --- | --- | --- |
| 요청 후 | 채팅 출력 → 턴 영수증 → Micro 기억(LLM) → Micro 벡터 저장(임베딩) | 30턴 실시간 재생: LLM 36회, Micro 28/30턴 |
| 요청 후 | 5턴 정규 분석(LLM) + 문서 임베딩 | 동작 |
| 요청 전 | `beforeRequest` 회상 주입(질의 임베딩) | 동작. 바꿔 말한 질문 6개 중 4개 정답 주입(p03은 그 실행에서 미주입, 단독 3회 재실행에서는 모두 주입; m01은 표현만 다름) |
| 요청 전 | 첫 요청 지연 | 30턴 기준 15.5s → 1.6s, 이후 약 0.85s. 시작 10초 뒤 한 번, 다른 기억 작업(Micro·수신·정규 분석·질의·빌드)이 없을 때만 런타임 색인을 예열한다. 바쁘면 건너뛰고 첫 요청이 예전처럼 만든다(3초 예열은 시작 직후 Micro 작업을 15초 넘게 늦춰 되돌렸다) |
| 수동 | LLM 연결 테스트, RisuAI 보조 모델 호출 | 동작(각 1회 호출) |
| 수동 | 임베딩 연결 테스트(질의·문서) | 동작(1024차원) |
| 수동 | 정규 기억 재생성 → 미리보기 → 채택 | 동작(LLM 1회) |
| 수동 | 임베딩 벡터 재생성, 수동 스캔 | 동작 |
| 수동 | 재시작 후 회상 | 93.8~100% |

새로 캡처한 30턴 상태의 회상 적중률은 100%(16/16), p50 0.85s다. 같은 상태에서 Voyage 응답이 느렸던 시점에는 질의 임베딩이 3.5s 예산을 넘어 어휘 검색만 남았고 62.5%였다. 느린 임베딩 제공자에서는 정확도가 크게 떨어진다.

발견: 실시간 재생에서 정규 분석이 도는 5의 배수 턴 직후 Micro가 늦게(180s 초과) 출판되고, 16·26턴은 `stale`로 끝나 Micro 기억이 영영 만들어지지 않았다. 재시작·요청 후 5분을 기다려도 복구되지 않고, 수신 복구 데스크도 `original_and_receipt_missing`(복구 불가)로 본다. 해당 턴의 사실은 정규 기억에는 남는다. 원인 조사가 남아 있다.

## Flashback (LLM 미사용)

| 시점 | 기능 | plugin_only | server_only(왕복 10ms) |
| --- | --- | --- | --- |
| 요청 후 → 백그라운드 | 출력 리스너 캡처 → 문서 임베딩 큐 | 동작(임베딩 58회) | 동작(로컬 키 0) |
| 요청 전 | 회상 주입(질의 임베딩) | 16/16, p50 275ms | 16/16, p50 606ms |
| 수동 | 다국어 임베딩 프로브 | verified | — |
| 수동 | 유지보수 sync / reembed, 전체 재임베딩, 점진 재임베딩, 현재 채팅 재구축, 정리 후 재임베딩, 콜드스타트 수집 | 모두 동작, 각 단계 후 회상 100% | — |

`recallRecords` 공개 API는 선택 단계 결과만 돌려주므로 레코드 1개만 보였다(요청 전 주입 경로는 정상). 점검 도구 쪽 판정 문제다.

## LIA (임베딩 없음, LLM은 모두 수동 기능)

`custom`(OpenAI 호환) 제공자 기준, 수정 전 → 수정 후(0.26.84):

| 기능 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 로어 재순위(RAG, 로컬) | 동작 | 동작 |
| 연결 테스트, 세계 청사진, 무작위 후보, 페르소나 진화, 감정 에셋(요청 후) | 동작 | 동작 |
| 페르소나 재작성 | 추론이 출력 예산을 써 JSON이 잘림 | 동작 |
| 필드 재추첨, 감사, 라이브 분석 | 빈 응답 | 동작 |
| 번역 | 다른 키(`translated`)로 응답해 실패 | 동작 |
| 등장인물 후보, 등장인물 재작성 | `identitySummary` 누락으로 항상 0명 | 동작 |

수정:
1. 추론 모델이 빈 응답이거나 길이 한도에서 잘리면, 제공자와 상관없이 추론을 끄고 한 번 재시도한다(전에는 Ollama Cloud의 빈 응답만).
2. `custom` 제공자에서 추론을 끈 요청은 `reasoning_effort: "none"`을 보내고, 거부하는 경로는 그 필드 없이 재시도한다.
3. 번역 프롬프트에 `{"personaPrompt": ...}`를 명시하고, 단일 문자열 필드 응답도 받는다.
4. 등장인물 후보 프롬프트에 JSON 형태를 명시하고, `identitySummary`가 없으면 역할·근거로 채운다.

이미지 생성은 이미지 제공자라 범위 밖이다.

## GRADIA (LLM 사용, 임베딩은 LIBRA 근거로)

| 시점 | 기능 | 모드 | 결과 |
| --- | --- | --- | --- |
| 요청 전 | SHADOW 초안 + AIDE 3단계(경량) | plugin | 동작 |
| 요청 전 | 2회 호출 단계(중량) | plugin | 동작 |
| 요청 전 | LIBRA 근거 읽기 + 초안·패치 | server | 동작, 모든 단계에 근거 도달 |
| 요청 후 | 계획 텍스트 정리, 출력 기록 | plugin | 동작 |
| 수동 | 입력 작성(rewriteInput), 선택지 번역, 장면 이어쓰기, OOC 3종, 프리셋 테스트, 모델 목록 | plugin | 동작 |
| 수동 | 입력 작성 + LIBRA 근거 | server | 동작 |

발견과 수정(0.25.88):
- AIDE 패치 출력 예산 하한이 900토큰이라 실제 모델에서 6회 중 4회 길이 한도로 잘렸다. 근거 모드에서는 같은 단계 재시도가 막혀 요청 전체가 실패한다. 하한을 1800(프로필 상한 안)으로 올렸다.
- 앞선 측정의 `LIB_READ_MODEL_TIMEOUT`(120s)은 평가 도구 문제였다. `stage_timeout_ms`는 첫 로드 때만 에이전트 슬롯에 복사되고 실제로는 슬롯의 `timeout_ms`(기본 120s)를 쓴다. 평가 도구가 슬롯 시간 제한을 직접 설정하고, 모델의 실제 `finish_reason`과 플러그인의 출력 예산을 전달하도록 고쳤다.
- 이전 측정에서 실패를 `LIB_READ_CANCELED`로 덮어쓰던 문제는 0.25.87에서 고쳤다.
- 슬롯 시간 제한 300s, 플러그인 요청 본문 그대로 전달한 서버 모드 근거 평가(질문 5개): SHADOW 초안 4/5가 LIBRA 근거의 사실을 썼다. 끝까지 완료된 2개는 최종 응답도 정답이고, 3개는 개별 모델 호출이 300s를 넘겨 `LIB_READ_MODEL_TIMEOUT`으로 끝났다. 같은 시점에 짧은 요청은 5s 안에 응답했으므로 긴 단계 요청에서의 제공자 지연이다. 느린 클라우드 모델에서는 단계 시간 제한을 더 길게 잡아야 한다.

## 공통 주의

RisuAI는 요청 메시지에 채팅 메시지 ID를 `memo`로 싣는다. LIBRA와 HAYAKU는 이것으로 현재 사용자 입력을 식별한다. `memo` 없는 메시지로 시험하면 LIBRA는 `no_safe_current_user_input`으로 회상을 건너뛰고, HAYAKU는 캡처가 한 턴 늦어진다. 점검 도구는 모두 `memo`를 싣는다.
