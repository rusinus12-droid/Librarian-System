# 관계 시뮬레이터 설계

2026-11-19 작성. 대상: GRADIA 확장 AIDE `aide_relationship_sim`(화면 이름 '관계 시뮬레이터'). 상태: 구현(§13에 설계와 달라진 점).

**연애 서사와 묘사를 보조하는 장치다**(사용자, 2026-11-19). 관계 상태·공개 범위·주도권·연애 방식이 장면의 몸짓과 거리감으로 드러나게 하는 것이 중심이다. 그 위에 고백, 재결합, 청혼, 데이트·이벤트의 결과를 확률로 판정해 **강제**하고, 기념일 같은 계기를 유저 지시 없이 **로어를 근거로** 장면에 올린다. 구현의 기준은 정사 AIDE다(인물 AIDE 하위, 코드가 장면을 읽어 필요한 지침만 붙임, 로어로 추정한 인물별 카드).

## 1. 확정된 결정 (2026-11-19, 사용자)

| 항목 | 결정 |
|---|---|
| 억결과의 관계 | 별도 기능. 억결을 꺼도 동작한다. 둘 다 켜면 억결이 시뮬레이터의 결과 위에 긴장을 얹는다 |
| 판정 | 성공률로 굴린 결과를 강제한다. 참고치가 아니다 |
| 이벤트 | 쿨다운을 둔다. 기념일(예: 첫 연애 날짜 기준 100일) 같은 계기는 자동으로 만들어 제안한다. 챙기지 않으면 상대가 서운해할 수 있다 |
| 근거 | 선호, 이벤트 내용, 반응 방식은 반드시 로어에서 나온다 |
| 상태 저장 | GRADIA가 관계 상태를 직접 가진다. 플러그인 훅 특성상 LIBRA 기록이 매 턴 공급되지 않기 때문이다. LIBRA는 실제로 만들어진 서사를 보고 따로 기록하고, 여전히 기준점이다 |

마지막 항목은 "확장 AIDE는 저장하지 않는다"(억결 설계 §14)의 예외다. 예외는 관계 상태 원장(§3.3) 하나로 한정한다.

## 2. 기존 장치와의 경계

| 장치 | 맡는 것 | 시뮬레이터와의 관계 |
|---|---|---|
| 억결 AIDE | 어떤 결이든 관계 긴장을 억지로 만드는 계기 | 시뮬레이터의 판정 결과와 관계 상태를 읽고 그 위에 긴장을 얹는다. 관계 카드를 함께 쓴다(§3.2) |
| NPC 반응 경향성 | 페르소나를 향한 NPC 태도의 방향(고정) | 성공률의 상한·하한을 정한다(§5.2). 시뮬레이터는 경향성을 바꾸지 않는다 |
| 정사 AIDE | 성교 장면 묘사와 성적 선호 카드 | 무관. 시뮬레이터는 성관계 진전을 판정하지 않는다 |
| 상태 AIDE | 몸 상태(부상, 주기, 임신) | 몸 상태가 데이트·이벤트를 막으면 그 계기는 미룬다 |
| LIBRA | 서사에서 실제로 일어난 일의 기록 | State `relationships`, 렌즈 `관계 변화 · 호감도`, 비밀 렌즈(누가 무엇을 아는가), State `sceneTime`을 읽는다(§4) |

## 3. 데이터

### 3.1 연애 선호 카드 (인물별, 로어 추정)

인물마다 하나. 정사 선호 카드와 같은 방식으로 로어에서 추정하고, 채팅별로 저장하며, 자동으로는 덮어쓰지 않는다. 저장 위치는 로어 추정 카드 저장소(`serial_gradation_agents_for_rp:lore_cards:v1`)의 새 분류 `romancePrefs`.

```
{
  name,                                   // 인물 이름
  places:   { liked: [placeId], disliked: [placeId] },
  times:    { liked: [timeId],  disliked: [timeId] },
  dates:    { liked: [dateId],  disliked: [dateId] },
  events:   { liked: [eventId], disliked: [eventId] },
  loveStyles: [styleId, ...],             // 앞의 것이 주된 방식, 1–2개
  sulk: string,                           // 서운할 때 드러내는 방식(로어 근거)
  evidence: [{ field, quote }],           // 각 추정의 로어 근거
  origin: lore_estimate | user
}
```

- 로어에 근거가 없는 항목은 비워 둔다. "모름"을 채워 넣지 않고, 일반론으로 추정하지 않는다.
- 근거(`evidence`)가 없는 추정은 카드에 넣지 않는다.
- 페르소나의 카드는 RP에서 **정보**로만 쓴다(NPC가 페르소나의 취향을 알고 계획할 때). 페르소나의 반응을 정하는 데는 쓰지 않는다(§7).

목록 값은 §9의 고정 ID를 쓴다.

### 3.2 관계 카드 (두 인물, 억결과 공용)

억결 관계 카드(억결 설계 §3.2)를 두 기능이 함께 쓰는 **관계 카드**로 넓힌다. 같은 관계를 기록하는 곳이 둘이 되지 않게 하기 위해서다. 억결 전용 필드(`tones`, `pressure`)는 억결이 꺼져 있으면 쓰지 않는다.

더하는 필드:

```
{
  status: friend | more_than_friend | less_than_friend | lovers | broken_up
        | engaged | engagement_broken | married | divorced,
  disclosure: public | partial | secret,
  knownBy: [name],              // partial의 출발값. 이후는 LIBRA 비밀 렌즈를 따른다
  lead: name | null,            // 연애 주도권
  leadReasons: [appearance | affection | devotion | wealth | ability | intellect | pride],
  datingSince: storyDate | null // 첫 연애 날짜. 기념일 계산의 기준
}
```

- 카드는 **출발점**이다. 현재 값은 원장(§3.3)과 LIBRA 기록을 따른다.
- `knownBy`는 출발값만 받는다. 이야기 속에서 누가 알게 되었는지는 LIBRA 비밀 렌즈가 기록한다.

### 3.3 관계 상태 원장 (GRADIA가 가지는 상태)

채팅별, 관계 카드별로 하나. 새 저장 키 `serial_gradation_agents_for_rp:relationship_state:v1`(설정 창 저장이 덮어쓰지 않게 런타임 설정과 분리, 정사 카드와 같은 이유).

```
{
  cardId,
  status, statusSince,           // 현재 관계 상태와 그 상태가 된 이야기 날짜
  datingSince,                   // 연인이 된 날짜(§6.1 기념일의 기준)
  disclosure,
  occasions: [{ id, kind, dueDate, state: upcoming | surfaced | kept | missed }],
  lastEventTurn,                 // 쿨다운 기준
  grievance: { level: 0–3, cause, sinceDate } | null,   // 서운함
  rolls: [{ turn, kind, percent, factors, result }],    // 최근 판정(표시·검증용, 상한 있음)
  confirmedThroughTurn,          // 확정된 마지막 턴
  pending: [{ turn, responseDigest, change }],          // 아직 확정되지 않은 변경
  reconciledAt, reconcileNote    // 마지막 LIBRA 대조
}
```

## 4. GRADIA 원장과 LIBRA 기록

### 4.1 쓰기: 대기 → 확정

판정 결과로 생긴 변경(예: 고백 성공 → 연인, 기념일 놓침 → 서운함)은 바로 확정하지 않는다.

1. 응답을 만들 때 변경을 `pending`에 넣는다. 그 턴 번호와 응답 본문 digest에 묶는다.
2. 다음 유저 턴이 왔을 때 그 응답이 채팅에 그대로 남아 있으면 확정한다.
3. 응답이 재생성, 스와이프, 편집, 삭제되었으면 그 대기 변경은 버린다.

리롤로 같은 변경이 두 번 들어가거나, 버려진 응답의 결과가 남는 것을 막는다.

### 4.2 읽기: 근거 우선순위

1. 관계 정사 잠금 사실(읽기 전용)
2. 현재 입력과 현재 채팅 작가 노트(그 턴에만)
3. LIBRA 기록: State `relationships`, 렌즈 `관계 변화 · 호감도`, 비밀 렌즈, State `sceneTime`
4. GRADIA 원장(확정분)
5. 관계 카드(출발점)

### 4.3 대조

LIBRA 기록이 공급된 턴에는 원장과 대조한다.

- LIBRA 기록이 원장의 확정 턴 이후까지 다루고 서로 다르면 **LIBRA를 따르고 원장을 고친다.** LIBRA는 실제로 만들어진 서사를 보고 기록했기 때문이다(모델이 강제 결과를 따르지 않았거나, 유저가 본문을 고친 경우).
- 고친 내용은 `reconcileNote`에 남기고 GUI에 보인다.
- LIBRA 기록이 없거나 원장보다 오래되었으면 원장을 그대로 쓴다.

### 4.4 이야기 날짜

기념일과 쿨다운의 날짜는 이야기 속 날짜다. LIBRA State `sceneTime`, 없으면 응답 머리의 시각 표시에서 읽는다. 날짜를 알 수 없으면 그 관계의 기념일 계산을 멈춘다. 날짜를 지어내지 않는다.

## 5. 판정 (결과 강제)

### 5.1 판정 종류

| 현재 상태 | 판정 | 성공 시 |
|---|---|---|
| 친구, 친구 이상, 친구 미만 | 고백 성공률 | 연인. `datingSince` = 그 장면의 날짜 |
| 결별, 파혼, 이혼 | 재결합 성공률 | 직전 관계(연인·약혼·결혼)로 |
| 연인, 약혼, 결혼 | 이벤트·데이트 성공률 | 호감 상승. 실패 시 서운함 가능 |
| 연인 | 청혼(이벤트의 한 종류) | 약혼 |

판정은 **행동이 실제로 일어났을 때만** 한다. 고백하지 않았는데 고백 성공률을 굴리지 않는다.

### 5.2 성공률 계산

모델은 요인만 읽고, 확률 계산과 판정은 코드가 한다.

1. 호스트 AIDE 호출에서 모델이 요인 태그를 근거와 함께 낸다. 예: 장소가 상대의 선호 장소인지, 시각이 비선호 시각인지, 이벤트가 상대의 비선호 이벤트인지, 최근에 서운함이 있었는지, 비밀 연애인데 공개된 장소인지.
2. 코드가 기본값(상태별)에 요인 가감을 더한다.
3. NPC 반응 경향성으로 상한·하한을 자른다. 초안 값: 적대 0–5%, 비호감 0–15%, 아는 사이 5–40%, 호감 20–75%, 애정 50–95%.
4. 시드(채팅, 관계 카드, 턴, 판정 종류)로 굴린다. 같은 턴을 다시 생성해도 같은 결과가 나와 리롤로 결과를 고를 수 없다.
5. 결과(성공/실패)와 반응 방향을 고정 지침으로 이후 단계와 초안에 넘긴다. 확률 숫자는 본문에 쓰지 않고 GUI에만 보인다.

연애 방식(§9.4)은 요인 해석에 쓴다. 예: 소유적 사랑은 질투 요인을 크게, 서운함을 강하게 받는다. 유희적 사랑은 서운함이 약하고, 실용적 사랑은 경제력·능력 요인을 크게 받는다.

### 5.3 강제와 검증

- 결과는 바뀌지 않는다. 표현(무슨 말, 어떤 행동으로 받아들이거나 거절하는지)은 그 인물의 로어가 정한다.
- 플롯 AIDE의 마지막 점검에서 응답이 판정 결과를 드러내는지 확인한다. 드러나지 않으면 그 턴의 변경은 대기에 넣지 않는다.

## 6. 이벤트 자동 발생 (제안)

### 6.1 계기

| 계기 | 기준 |
|---|---|
| 기념일 | `datingSince`부터 100일 단위(100·200·300일), 1주년 단위 |
| 생일 | 로어에 적힌 생일 |
| 데이트 제안 | 쿨다운이 지났고, 이야기 시각이 상대의 선호 시각이며, 장면이 데이트로 이어질 수 있을 때 |
| 만회 | 서운함이 남아 있을 때, 풀 기회 |

### 6.2 장면에 올리는 방식

- 계기는 **현재 장면에 묶여** 올라온다. 두 사람이 함께 있거나 연락할 수 있는 장면이고, 장면의 목적과 어긋나지 않을 때만이다. 전투나 위기 장면을 끊고 들어오지 않는다.
- 기념일은 며칠 전부터 단서로 깔 수 있다(상대가 날짜를 넌지시 말함, 달력, 주변 인물의 언급).
- 내용(장소, 데이트 종류, 이벤트)은 상대의 연애 선호 카드와 로어에서 고른다. 카드에도 로어에도 근거가 없으면 그 내용은 고르지 않는다.
- 쿨다운: 이벤트 제안 후 정해진 턴 동안 새 제안을 하지 않는다(초안 8턴). 기념일과 생일은 쿨다운을 무시한다.
- GUI에 다가오는 기념일과 제안 후보를 보인다.

### 6.3 챙기기와 서운함

- 이야기 날짜가 계기를 지나는 동안 그 계기를 챙기는 장면이 없었으면 `missed`로 기록하고 서운함을 올린다.
- 서운함의 크기는 연애 방식과 그 계기의 무게(1주년 > 100일 > 일반 데이트)에서 정한다. 드러내는 방식은 카드의 `sulk`와 로어를 따른다.
- 서운함은 다음 판정의 요인이 되고(§5.2), 만회 계기(§6.1)를 연다. 시간만 지난다고 저절로 사라지지 않는다.

## 7. 작성 모드별 동작

| 모드 | 동작 |
|---|---|
| 소설 | 모든 참여자에 대해 판정하고 계기를 연출한다 |
| RP 페르소나 전용 | 판정은 페르소나가 입력에서 한 행동에 대한 **NPC의 반응**만 정한다. 계기는 NPC 쪽에서 올린다(NPC가 기념일을 꺼내거나 데이트를 제안). 페르소나가 고백·이벤트를 하게 만들지 않고, 페르소나의 감정이나 수락 여부를 정하지 않는다 |
| RP 장면 연출 | 유저가 모든 인물을 정하므로 판정하지 않는다. 원장 기록과 기념일 알림만 한다 |
| RP 문장화 | 실행하지 않는다 |

RP에서 NPC가 페르소나에게 고백하거나 청혼하는 것은 NPC의 행동이므로 가능하다. 그에 대한 답은 유저가 한다.

## 8. 실행 위치

- 확장 AIDE `aide_relationship_sim`, `rank` 18: 세계 동역학(5) → 상태(10) → 정사(15) → **관계 시뮬레이터(18)** → 억결(20).
- 호스트는 인물 AIDE다(상태·정사와 같은 곳). 별도 호출 없이 인물 AIDE 호출 안에서 요인 태그(§5.2)를 낸다.
- 코드는 인물 AIDE의 출력을 수집할 때(`recordOutput`) 판정을 굴린다. 결과는 세계관·플롯 AIDE와 초안 단계에 고정 지침으로 들어간다.
- 억결은 플롯 AIDE 안에서 마지막으로 돌며 판정 결과와 관계 상태를 읽는다.

## 9. 고정 목록

목록은 ID와 한 줄 요지로만 둔다. 프롬프트에는 그 턴에 필요한 항목만 붙인다.

### 9.1 장소 (`placeId`)

집, 카페, 호텔, 모텔, 여관, 공원, 영화관, 전시회, 박물관, 백화점, 마트, 서점, 고궁, 바닷가, 놀이공원, 식당, 관광명소, 번화가, 골목

### 9.2 시각 (`timeId`)

## 10. GUI

- 관계 목록: 관계마다 현재 상태, 상태가 된 날짜, 공개 범위, 다음 기념일, 쿨다운 남은 턴, 서운함, 마지막 판정(확률·결과·요인).
- 연애 선호 카드: 인물별 보기·고치기·지우기(바로 저장). 각 항목 옆에 로어 근거.
- 대조 기록: LIBRA 기록으로 원장을 고친 내역.
- 확률은 GUI에만 보인다.

## 11. 테스트 기준

- 억결이 꺼져 있어도 판정과 기념일이 동작한다.
- 같은 턴을 다시 생성하면 같은 판정 결과가 나온다.
- 재생성, 편집, 삭제된 응답의 대기 변경은 확정되지 않는다.
- LIBRA 기록이 원장과 다르면 LIBRA를 따르고 대조 기록을 남긴다. LIBRA 기록이 없으면 원장으로 계속한다.
- 적대 경향성 NPC의 고백 성공률은 상한을 넘지 않는다.
- RP 페르소나 전용에서 페르소나의 행동·감정·수락을 만들지 않고, 페르소나가 행동하지 않은 턴에는 판정하지 않는다.
- 로어 근거가 없는 선호 항목은 카드에 생기지 않는다.
- 이야기 날짜를 알 수 없으면 기념일을 만들지 않는다.
- 기념일을 챙기지 않고 날짜가 지나면 서운함이 오르고, 만회 계기가 열린다.

## 12. 묘사 보조 (구현에서 더함)

장면에 있는 쌍마다 코드가 다음 줄을 만들어 `DEPICTION` 블록으로 모든 단계에 넘긴다. 라벨을 본문에 쓰지 않고 몸짓·타이밍·서로 알아채는 것으로 드러내게 한다.

- 관계 상태별 분위기: 친구 이상의 애매한 긴장, 연인의 사적인 말투와 가벼운 접촉, 결별 뒤의 어색한 배려 등. 연인·약혼은 사귄 지 100일 전(설렘·처음들)과 2년 뒤(익숙함·소홀해질 위험)를 구분한다.
- 공개 범위: 비밀이면 남 앞의 조심스러운 거리와 들킬 뻔한 순간, 일부 공개면 아는 사람과 모르는 사람 앞에서 달라지는 태도.
- 주도권: 누가 먼저 다가가고, 계획을 정하고, 사과하고, 기다리는지로 보인다.
- 서운함: 그 인물의 `sulk` 방식으로 드러나고, 풀어 주는 장면 없이 사라지지 않는다.
- 연애 방식: 6유형마다 행동 단서(예: 소유적 사랑은 자주 확인하고 거리를 거절로 읽음).
- 데이트·이벤트는 장소의 감각 묘사와 작은 몸짓이 있는 장면으로 쓴다. 선호 장소는 눈에 띄게 반기고, 비선호는 말보다 자세와 인내심에서 먼저 드러난다.

RP에서는 페르소나의 주도권·연애 방식·서운함 줄을 만들지 않는다(페르소나의 감정은 유저의 것).

## 13. 설계와 달라진 점 (구현 2026-11-19)

- **판정 시점:** 요인을 모델이 읽는 대신(§5.2 1단계) 코드가 SHADOW 초안 전에 판정한다. 하위 AIDE는 인물 AIDE 호출 안에서 정리되는데, 그 호출은 SHADOW가 초안을 쓴 뒤에 돈다. 그래서 모델이 요인을 읽으면 결과가 정해지기 전에 초안이 나온다. 코드가 읽는 요인은 상태, NPC 경향성(상·하한), 서운함, 연애 방식, 주도권, 장면의 장소(입력·직전 응답의 단어), 시각(LIBRA 이야기 시계 또는 장면의 시각 표시), 데이트·이벤트 종류(단어), 비밀 연애 노출이다. 판정은 장면에 두 사람이 다 있는 쌍만, 상태가 허용하는 행동마다 "이 행동이 일어나면 결과는 이것"이라는 조건부 결과로 넘긴다. 인물 AIDE는 실제로 일어난 행동과 결과가 드러났는지를 보고한다.
- **같은 턴 판정:** 시드는 채팅·쌍·행동·행동한 사람·현재 입력 해시·직전 응답 해시다. 같은 턴을 다시 생성해도 같은 결과가 나온다.
- **관계 카드 필드:** 억결 카드 스키마를 넓히지 않았다. 쌍의 현재 값(상태, 첫 연애 날짜, 공개 범위, 아는 사람, 주도권과 이유, 서운함, 기념일, 판정 기록)은 관계 카드 id별로 원장(`relationship_state:v1`)에 두고, 이 채팅 화면에서 직접 고친다. 상태가 비어 있으면 인물 AIDE가 로어로 추정한 값이 한 번 들어간다. 카드가 없는 연애 쌍은 시뮬레이터가 억결 공용 로어 카드로 만든다.
- **대기·확정:** 대기 변경은 다음 실행에서 직전 유저 입력이 그 턴의 입력과 같으면 확정한다. 같은 입력·같은 직전 응답이면 다시 생성으로 보고 버린다.
- **기념일 놓침:** 시뮬레이터가 미리 본 적 없는 기념일(첫 연애 날짜를 나중에 넣은 경우)이 지나 있으면 놓침으로만 기록하고 서운함은 올리지 않는다.
- **LIBRA 대조:** 인물 AIDE가 GRADIA EXTERNAL EVIDENCE(LIBRA) 블록의 문장을 그대로 인용해 상태가 다르다고 보고하면, 인용이 실제로 그 블록에 있을 때만 원장을 바로 고치고 GUI에 기록을 남긴다.
- **GUI:** 파이프라인 사다리와 미니 체인(정사 다음), 단계 패널(`#on-s9`), 이 채팅 화면의 관계 상태·연애 선호 카드, 이번 턴 판독, 실행 결과 탭 '관계'. 목록에 없는 이름은 저장할 때 빠지고 상태 줄에 알린다.

## 14. 남은 판단

- 상태별 기본 성공률, 요인 가감 폭, 경향성별 상한·하한 값은 초안이다. 실제 대화로 조정한다.
- 쿨다운 기본값(8턴)과 기념일 단서를 며칠 전부터 깔지.
- 원장 `rolls`를 몇 개까지 남길지.
- 관계 카드 하나에 억결 필드와 시뮬레이터 필드를 함께 두는 방식의 GUI 배치(억결 설계 §15의 NPC↔NPC 카드 판단과 함께 정한다).
