# 병합 후 리뷰 결함 수정

작성: 2026-10-16 (한국 시간). 기준: `claude/usability-improvements-products-23ax1n`의 병합 커밋 `294082c`.

## HAYAKU 자동 승인 경쟁 조건 — P2

기존 코드는 확인 요청 시작 시 복사한 Journal로 자동 승인 여부를 판단했다. 비동기 원문 검사 중 afterRequest 복구가 시도·실패해도 과거의 `attempted:false`가 남아 추가 호출로 이어질 수 있었다.

확인창 선점은 Journal 쓰기와 같은 저장 큐에서 최신 항목의 결정·진행 상태를 검증한다. 이때 반환한 항목으로 자동 승인 여부를 결정하고, 자동 승인 저장 및 실행 lease 획득에서도 최신 시도·실패 상태를 재검사한다. 자동 승인이 무효화되면 추가 모델 호출 없이 중단한다. 이미 실패한 항목의 명시적 사용자 승인·수동 복구 경로는 유지한다.

회귀는 최초 원문 검사, pending 기록 저장, 승인 전 재검사 중 각각 실패 이력이 생기는 경우와 설정 변경·중복 요청을 실행한다. 실제 HAYAKU 런타임에서도 실패 Journal을 대상으로 오래된 자동 승인으로 lease를 얻지 못하는지 확인한다.

## Flashback 임베딩 요청 수명 — P2

기존 1.5–4초 조회 예산은 Promise 대기만 끝냈다. provider 호출과 in-flight 항목은 계속 남았고, 늦게 받은 벡터가 캐시에 들어갔다.

이제 예산과 외부 AbortSignal 및 native hook의 요청 signal은 조회별 대기·lease에 연결된다. 같은 질의를 공유하는 다른 조회가 남아 있으면 네트워크 요청을 유지하고, 마지막 조회가 떠나면 공유 controller를 중단하며 해당 in-flight 항목을 제거한다. 자격 증명 읽기를 기다리는 단계도 조회 예산에 포함한다. 설정 변경·캐시 무효화·플러그인 종료도 공유 controller에 취소를 전달한다. 취소된 조회는 대체 근거를 출력하거나 다음 정상 조회에 provider 장애 cooldown을 남기지 않는다.

provider 완료만으로 캐시를 쓰지 않는다. 살아 있는 조회가 전체 cached/coalesced/fresh 벡터의 호환성, 현재 authority, generation과 취소 상태를 검증한 뒤 게시한다. 취소를 무시하는 transport의 늦은 응답은 캐시에 들어가지 않는다. 이미 제출한 실제 요청의 과금 취소를 보장하지는 않으며, 물리적으로 미완료인 요청은 기존 pending 진단과 재제출 차단을 유지한다.

실제 Flashback adapter를 사용한 회귀에서 단독 시간 초과, 공유 원요청·후속 조회의 개별 취소, 마지막 lease 취소, 자격 증명 지연, 사전 취소, generation 변경, 벡터 차원 혼합 및 완료 시 authority 변경을 확인한다.

## HAYAKU 작성 진단 — P3

`candidate_returned_pending_commit`은 검증된 후보가 반환됐다는 뜻이다. durable 기억 저장 성공으로 집계하지 않는다. 집계 필드를 `repairCandidates`로, 화면을 `보조 모델 후보 작성`으로 바꾸고 `저장 완료 여부는 별도 확인`을 표시한다. 실제 commit을 관측하지 않은 이력을 저장 성공 지표로 확대하지 않는다.
