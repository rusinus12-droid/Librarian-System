# 2026-10-30 리콜·기억 읽기·응답 후 복구 수정

대상: LIBRA, HAYAKU, GRADIA, Flashback. 제공된 네 디버그 JSON은 진단 자료로만 사용했다. 실사용 DATA의 기억·원문·설정은 수정하지 않았다. 실제 RisuAI에 설치된 플러그인을 원격으로 교체하거나 외부 모델을 호출한 작업도 아니다.

## 로그에서 확인한 상태

| 대상 | 관찰 | 해석 |
| --- | --- | --- |
| LIBRA | `unified_graph_query` 성공 후 `unified_final_consumer`에서 `LIBRA_GRAPH_RESOURCE_CLOSED`. 전체 34,170ms, 제한 40,000ms | 검색 결과가 없거나 전체 제한 시간을 넘긴 것이 아니라, 검색과 최종 검증 사이에 읽기 자원이 취소됨 |
| LIBRA 서버 기록 | 같은 구간의 최종 검증 직전에 해당 scope의 manifest 쓰기 확인 | 비동기 저장 작업과 리콜 검증의 경합을 추적할 근거 |
| HAYAKU | beforeRequest 진입은 있으나 `lastBeforeRequest`는 null. 요청 정보·pending capture·Other AX 실행 기록 없음. 초기 ledger 접근에 `server_unavailable` 기록 | 리콜 준비 단계의 조기 반환으로 응답 후 복구에 필요한 요청 정보도 만들어지지 않음. 원본 예외를 버리는 catch 때문에 당시 정확한 거부 코드는 로그만으로 확정할 수 없음 |
| GRADIA | `libReadStatus: unavailable`, `LIB_READ_NATIVE_ID_UNAVAILABLE`, `externalEvidence: false` | 세 소유자의 기억을 읽기 전에 요청 메시지의 native ID 검증에서 중단됨 |
| Flashback | 리콜·주입 성공. 원문 저장의 commit/readback 확인. `provisional: true`, `liveConfirmed: false`, pending 존재, monitor 0 | 원문은 보존됐으나 실제 선택된 채팅의 최종 출력과 대조하는 감시가 끝나 정본 확인이 진행되지 않음 |

`최초 출력 확인 대기 · 아직 정본 아님`은 저장 실패 표시가 아니다. 임시 원문을 실제 채팅과 대조하기 전이라는 표시이며, 이 표시를 숨기거나 확인 없이 정본으로 바꾸지 않았다.

## 구현

### LIBRA

기존 scope별 저장 작업 큐에 리콜의 선택부터 마지막 물리 검증·주입까지를 하나의 작업으로 넣었다. 같은 큐의 스캔·임베딩 후처리가 중간에 manifest를 갱신해 읽기 자원을 취소하는 경합을 막는다. 대기는 기존 리콜 제한 시간 안에서 처리한다.

compiler 무효화, 원본 변경 검증, 복구·scope 전환 시 취소는 유지했다. 실제 원본 inventory를 바꾸는 외부 쓰기는 여전히 주입을 차단한다. Micro 생성·저장 경로는 변경하지 않았다.

### HAYAKU

서버가 시작 시 사용 불가능했다가 복구되는 상태를 재현했다. 연결 준비 및 DATA identity 확정이 읽기 검증보다 늦어지는 경우 기존 구현은 그 요청에서 리콜을 거부했다. 요청 정보를 등록하지 못하므로 afterRequest의 Other AX 복구도 실행되지 않았다.

scope 설정·전환 상태를 먼저 확인하고, 서버 모드에서 아직 연결이 확정되지 않았으면 SDK의 기존 bootstrap 검증을 완료한 뒤 readset을 발급한다. DATA 변경·전환·원문 변경 검사를 완화하지 않았다. 거부 시에는 사유를 `lastBeforeRequest`와 진단 로그에 남긴다. 플러그인 모드에서는 이 준비 때문에 서버에 연결하지 않는다.

LIBRA Micro의 성공 경로와 비교해, 수동으로 pending을 심는 시험 대신 실제 beforeRequest → afterRequest → output → 다음 요청의 흐름을 추가 검증했다. Other AX는 한 번만 실행하고, output에서 복구 패킷을 내구 저장한 뒤 다음 요청이 확정된 호스트 원문과 대조해 active로 결합한다. 내구 저장과 정본 결합을 구분하는 기존 보호 장치는 유지한다.

### GRADIA

제공자용 요청에서 ID가 빠진 메시지는 선택된 RisuAI 채팅의 원문·역할과 정확히 일치하는 유일한 메시지가 있을 때만 실제 native ID에 결합한다. 새 ID를 만들지 않는다. 완료된 대화를 선택하기 전에 결합해 이전 장면까지 제외되는 문제도 해결한다. 원래 입력 배열은 변경하지 않는다.

읽기 브리지는 비동기 결합 완료를 기다린다. scope, 순서, 원문, 입력·설정 변경, 중복 문구의 모호성, 스트리밍 상태를 검사하며 처리 중 원문이 바뀌면 후속 호출을 거부한다. 호스트 조회에는 시간 제한을 둔다. 연결하지 않은 경로와 기존 엄격한 native read 계약은 유지했다.

추가로 서버 owner IPC의 기존 20초 제한은 제공된 LIBRA 검색의 29초보다 짧았다. owner 읽기와 이를 기다리는 바깥 capture에 50초의 일관된 한도를 적용했다(LIBRA 검색 한도 40초 + 통신 여유 10초). 빠른 capability 조회, 모델 호출 제한, 재시도 횟수는 변경하지 않았다. 가속 시계로 실제 IPC와 production consumer를 실행해 35초 읽기 및 바깥 45초 읽기는 성공하고, 65초 읽기는 제한 시간에 차단되는 것을 검증했다.

### Flashback

공식 output 콜백으로 임시 원문을 내구 저장한 후에도 최종 출력 감시를 유지한다. 호스트가 채팅 원문을 확정하면 같은 요청의 U+A 및 메시지 ID를 대조해 확인하고 정본으로 갱신한다. 원문이 다르면 강제 확정하지 않는다.

재시작 전의 임시 원문도 정상 요청 시 원문 대조를 거쳐 활성 기록이 되는 것을 검증했다. 저장된 원문을 지우거나 재생성할 필요가 없다.

## 검증과 한계

이번 결함을 다루는 신규 시험은 총 23건이다: LIBRA 3개 저장 모드 × 2건, HAYAKU 2건, Flashback 2건, GRADIA identity 8건·실제 파이프라인 2건·읽기 제한 3건. 모두 통과했다. 수정 전 소스 사본으로 같은 재현 시험을 실행해 LIBRA 경합, HAYAKU 재연결, Flashback 감시 종료, GRADIA ID 누락 및 짧은 읽기 제한으로 인한 실패가 발생하는 것도 확인했다.

- LIBRA: 플러그인 모드·서버 모드·미러에서 경합 해소 및 실제 원본 변경 거부. 기존 3모드 자원·물리 증거·취소·UI 영수증 수명 시험도 실행했다.
- HAYAKU: 초기 서버 실패 후 같은 요청의 리콜 성공, Other AX 1회, 중복 호출 없음, 실제 임시 SQLite 저장, 다음 요청의 active 결합 확인. 서버가 계속 불가능하면 주입·모델 호출 없이 거부한다. 기존 afterRequest 저널과 물리 readset 변경 거부 시험도 실행했다.
- Flashback: output이 호스트 commit보다 먼저 오는 순서에서 임시 저장 → 감시 유지 → 정확한 원문 확인. 재시작 후 확인도 통과했다.
- GRADIA: 생산 consumer 및 실제 SHADOW/AIDE 네 단계의 요청에 세 소유자의 기억이 포함되는지 검사했다. 중간 원문 변경은 첫 모델 호출 뒤 후속 호출을 차단했다. 외부 모델 대신 결정적인 시험 응답을 사용했다.

전체 회귀가 모두 통과한 것은 아니다. 기존 HAYAKU의 지연 ledger 반환 시험 2건과 LIBRA owner IPC 영수증 시험 1건은 수정 전·후 소스에서 모두 같은 시간 초과로 실패했다. 후자의 시험은 자체 client 한도를 10초로 고정하며, 이번 GRADIA의 50초 설정을 사용하지 않는다. 테스트의 한도를 늘려 통과시키지 않았다. HAYAKU의 실제 저장 모드 전환 시험은 로컬 서버 실행 조건에서 통과했다. 이 별도 실패를 해결했다고 간주하지 않는다.

시험 로그와 수정 전 소스 사본은 배포에서 제외되는 `.development/evidence/multiplugin-20261030/`에 있다. 실제 RisuAI GUI·실제 제공자 응답·과금·사용자 채팅에서의 최종 성공은 아직 검증하지 않았다. 적용하려면 수정된 플러그인 네 파일을 RisuAI에 다시 불러오고 새로고침해야 한다. 이후 기존 채팅에서 정상 요청 또는 점검으로 재확인한다.
