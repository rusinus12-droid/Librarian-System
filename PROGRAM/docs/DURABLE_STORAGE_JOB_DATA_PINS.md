# Durable storage job DATA pins

The standard and LIBRA canonical storage SDKs bind persisted transfer jobs to the physical server DATA instance before starting transfer. A saved job carries separate source and target pins when those roles require server access. Each pin records its namespace, normalized transport URL, server URL, physical DATA identity contract and identifier, and namespace reset epoch. Tokens and payload bodies are not part of a pin. Live request generations remain a separate runtime fence.

The SDK verifies the journal by writing and reading the exact serialized value before transfer. On startup and explicit resume, it validates the saved job metadata and compares its pins with a fresh certified physical server connection. Historical jobs without a pin, mismatched namespace/reset/identity, uncertified servers, and unverified persistence pause without automatic retry. Existing raw data, private settings and the old journal remain available. Ordinary legacy reads remain compatible; they do not establish proof for a durable transfer. A job involving only plugin storage makes no server request.

The independent automatic migration timer also admits an unfinished saved job before resolving the current scope, importing historical mode arguments, or transferring local raw data. A refused journal remains paused and does not schedule an automatic retry. Job creation in progress defers this separate startup timer visibly. Automatic migration without a pending journal retains its existing behavior.

Concurrent startup consumers await one physical journal read. Pending reads cannot appear as an empty journal, and read/parse/contract failures produce `MEMORY_SUITE_JOB_JOURNAL_UNAVAILABLE` while preserving the journal and source. An unfinished journal older than the existing two-hour automatic resume window remains visible and paused with `MEMORY_SUITE_JOB_RESUME_EXPIRED`; expiry does not permit a background migration to bypass it. Terminal journals retain the existing expiration behavior. A stopped expired job can be cancelled explicitly before creating new verified work.

Restore and connection-configuration jobs check their pins inside the restore rollback boundary, before clearing integrity recovery or committing authority. If DATA changes while a local write is awaiting acknowledgement, completed rollback leaves the job paused without publishing old recovery metadata to the replacement server. Failed rollback preserves the candidate and records a durable local integrity hold. The paused job reports that hold after a fresh restart. Existing recovery failures unrelated to the job pin retain their previous recovery behavior.

The LIBRA prepared conditional-batch/read-set boundary also contains a physical server pin. A prepared mutation from another DATA instance, or a legacy preparation without proof, is rejected before mutation dispatch. Existing digest, revision, provenance, currentness and acknowledgement checks remain required.

This is the first SDK safety slice of S01. It does not complete installation-wide inventory, verified per-key global authority, five owner payload validation, global resume/new-chat admission, or registered public GUI integration. Product embedded SDK regeneration and original integration are performed separately by the integration owner. A same-process mutex and storage readback do not provide host-wide compare-and-swap.

The owning regression is `tests/memory_suite_durable_job_data_pin_runtime_test.cjs`. It uses both canonical SDKs, fresh VMs, isolated real SQLite servers and physical store readback. Generation and embedding are disabled. Tests cover correct-root resume, identical-address replacement, old unpinned journals, namespace/reset mismatches, false/lost persistence, ordinary uncertified compatibility, zero-network plugin-only work, held local restore/configuration writes and incomplete rollback across restart, and wrong-root/unpinned prepared batches.
