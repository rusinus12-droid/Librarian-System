# HAYAKU Recovery Journal 필요성 검토 (2026-10-16)

## 하는 일

Recovery Journal은 패킷이 없거나 깨진 턴만 기록한다. 기록에는 그 턴의 사용자·AI 원문 전체, 해시, 계보, 복구 상태가 들어간다. 그 턴에 패킷이 생기면 기록을 지운다. 이 기능은 설정으로 끌 수 없다.

## 검토 결과

| 용도 | 원문 저장이 필요한가 |
| --- | --- |
| 수동 누락 복구 | 아니다. Journal 원문은 지금 채팅 원문과 같을 때만 쓰였다. 다르면 복구가 실패했다. |
| 원문 회상(raw passage recall) | 아니다. 그 턴이 지금 채팅에 그대로 있을 때만 쓰였다. |
| 실패 화면 표시 | 아니다. 채팅에서 읽을 수 있다. |
| 누락 턴 목록(잠금, 시도 횟수) | 원문은 필요 없고 해시와 계보면 충분하다. |
| RE:TRACE 새 채팅 이어가기 | **필요하다.** 인계 과정은 이전 채팅의 저장소만 읽고 이전 채팅의 메시지는 읽지 않는다. 그래서 이전 채팅에서 패킷이 없던 턴은 Journal 원문이 새 채팅으로 넘어가는 유일한 기억이다. |

## 이번 변경

1. 수동 복구와 원문 회상은 채팅 원문을 직접 읽는다. 실패 화면도 채팅 원문을 먼저 쓴다.
   - 턴 식별 정보와 해시가 지금 채팅과 맞으면 채팅 원문을 쓴다. Journal 사본은 읽지 않고 다시 쓰지도 않는다.
   - 메시지가 수정·리롤·삭제된 턴은 이전처럼 쓰지 않는다(fail-closed).
   - 이전 세션에서 인계된 기록만 Journal 원문을 쓴다.
   - 사용자에게 보이는 결과는 같다. 차이는 Journal 사본이 없거나 깨져도 복구와 회상이 동작한다는 점이다.
   - 원문 회상은 요청마다 만든 채팅 스냅샷 하나를 재사용한다. 기록마다 채팅을 다시 읽지 않는다.
2. 효과가 없던 설정 두 개를 퇴역시켰다.
   - `hayaku_raw_recall_max_items`, `hayaku_raw_recall_min_score`는 값을 읽기만 하고 어디에도 쓰지 않았다.
   - 설정 화면에서 지웠다. 저장된 값은 그대로 보존된다. 원문 회상 분량은 `hayaku_raw_recall_max_chars`가 정한다.
3. 백그라운드 복구 확인창 코드를 지웠다(191줄).
   - 지운 것: 확인창 표시 함수와 승인 요청 함수. 백그라운드 복구 퇴역 후 호출하는 곳이 없었다.
   - 남긴 것: 명시적 승인 처리 함수(`resolveRecoveryJournalBackgroundConfirmation`)와 저장 측 결정 기록 함수(`updateRecoveryJournalBackgroundDecision`). 서버 전용 저장 테스트와 저장 모드 테스트가 이 두 함수를 쓴다.

## 하지 않은 것: Journal 원문 저장 중단

Journal을 원문 없는 누락 턴 목록으로 줄이는 작업은 보류했다.

- RE:TRACE 인계가 이 원문에 의존한다. 원문을 저장하지 않으면 이전 채팅에서 패킷이 없던 턴의 기억이 새 채팅에서 사라진다.
- 피하려면 인계 시점에 이전 채팅의 메시지를 직접 읽어야 하는데, 그런 경로가 지금은 없다.
- 이번 변경으로 원문 사본은 사실상 "인계용 보존본" 역할만 남았다. 대상이 누락 턴뿐이어서 저장량도 보통 작다.
