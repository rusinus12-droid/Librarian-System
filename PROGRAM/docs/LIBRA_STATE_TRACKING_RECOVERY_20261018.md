## 정본·Micro 본문 표시 추가 확인 — 2.3.170

앞선 실모델 검증은 인물·세계·서사 상태와 열린 상태 창의 자동 갱신을 확인했다. 기억 읽기 화면에서 Micro 본문까지 실제 저장소와 연결되는지는 별도로 확인되지 않았다. 기존 턴별 근거 렌더 시험은 DTO를 직접 제공하므로 읽기 API 누락을 발견하지 못했다.

main `a8454a4`의 정본 본문 표시는 정상이다. Micro의 `loadBookTurnEvidence`는 공개 API `readActiveMicroMemoryForTurn`을 호출하지만 내부 Core에만 이 함수가 있어, 검증된 Micro가 저장돼도 기억 페이지에서는 `micro_absent`로 처리됐다. 해당 API를 기존 스코프·본문 검증 경로 그대로 공개하고, 같은 정본 범위의 Micro 게시·재분석이 끝나면 열린 기억 페이지를 다시 읽도록 했다. 갱신은 게시 식별값별로 한 번 실행하며 화면 조회는 모델을 호출하지 않는다. 비동기 Micro 근거 조회가 끝난 뒤에도 스코프와 선택 정본이 같은지 재확인하고, 선택 변경 시 이전 근거를 지운다.

`tests/libra_micro_book_gui_runtime_test.cjs`는 전체 제품 플러그인과 실제 DOM에서 정본 생성·저장·본문 표시, Micro 재분석·저장·공개 API 조회·턴별 본문/인용 표시·열린 페이지 자동 갱신을 검사한다. 다른 스코프의 조회는 거부되며 정본 본문은 변하지 않는다. 합성 모델 출력으로 정본 1회·Micro 1회를 생성했고 GUI 조회의 모델 호출과 브라우저 오류는 0회였다. `libra_book_v516_lifecycle_runtime_test.cjs`에는 늦게 도착한 Micro 근거가 새로 선택한 정본을 덮어쓰지 않는 검사를 추가했으며 전체 24개 경우가 통과했다. 해당 시험의 정본 목차 함수 추출을 실제 함수 범위로 좁히고 검색 경계 DTO도 현재의 `{refs, coverage}` 형태로 갱신해 무관한 초기화 코드 실행과 오래된 시험 계약을 정리했다. 기존 상태 GUI·본문 렌더·정본 필드 표시·벡터 정렬 검사도 통과했다.

### 독립 Micro 기억 목록

기억 서가의 **정본 기억 / Micro 기억** 탭으로 구분한다. Micro 탭은 현재 채팅의 완료된 턴을 최신순으로 보여주고 한 번에 최대 20턴만 저장소에서 읽는다. 정본이 아직 없는 T1과 정본 T1–T5 다음의 T6·T7도 표시된다. ‘이전 턴 더 보기’로 과거 페이지를 펼친다. 전체 저장소·벡터를 재스캔하거나 모델을 호출하지 않는다.

분석 완료 기록에는 주장 본문과 해당 원문 인용·출처를, 원문만 보관된 기록에는 분석 미완 표시와 발췌를 보여준다. 저장 기록이 없는 턴·원문 변경·저장 검증 실패는 구별하며, 원문이나 저장 본문이 맞지 않으면 기존 본문을 표시하지 않는다. 추출 완료 표시를 현재 상태 승인으로 취급하지 않는다. 목록 조회 실패 때는 오류와 마지막 확인 목록을 함께 표시한다.

게시 후 열린 목록과 상세를 자동 갱신한다. 스코프·화면 수명·선택 턴을 묶어 늦은 응답을 차단하고, Canonical의 논리 세계선과 Micro의 물리적 채팅 세계선을 구분한다. GUI 전용 읽기는 기존 Micro 본문 digest와 주장/인용 검증도 통과해야 성공으로 표시한다. 기존 검색·State 승인 규칙과 벡터 top-8 선별은 변경하지 않았다.

- `libra_micro_reader_gui_runtime_test.cjs`: 전체 플러그인·DOM으로 첫 정본 이전 T1, 정본 범위 밖 T6·T7, 분석 완료/미완, 자동 갱신, 원문 수정 후 이전 본문 제외, 25턴 페이지 분할, 목록 오류·마지막 목록 유지, 정본 탭 복귀를 확인한다. 합성 모델 경계이며 GUI 조회에 모델 호출은 없다.
- `libra_micro_reader_storage_3mode_test.cjs`: 플러그인 단독·미러·서버 단독에서 실제 게시 후 페이지 조회·다른 스코프 거부·저장 본문 변조 차단을 확인한다. 서버 모드는 실제 로컬 HTTP/SQLite 저장소를 사용한다.

기존 정본+Micro 근거 GUI·현재 상태 GUI·정본 읽기 계약·벡터 정렬 검사도 통과했다. 이번 독립 목록 검증에는 실제 공급자 모델을 다시 호출하지 않았다. 현재 채팅의 원문과 결속되는 기록을 읽으며, 삭제된 채팅이나 다른 스코프의 보관 기록을 합쳐 보여주는 전체 저장소 관리자는 아니다. 이 변경은 LIBRA 2.3.170에 포함된다.

실모델 확인에서 발견한 문제는 두 가지였다. Micro 모델이 근거를 배열로 출력해 추출 주장이 모두 거부됐고, 상태 승인이 성공한 경우에도 GUI가 정본 Head만 읽어 최신 Micro 상태를 표시하지 않았다. 정본 출력에도 이름·필드 위치·참조 종류의 계약 위반이 있었다.

## 변경한 경로

1. **추출 계약:** Micro 근거 객체의 JSON 형태와 명시적인 상태 변화 예시를 제공한다. 정본은 장소·관리·소유·접근 권한·관계·서사의 출력 위치와 참조 종류를 구분한다. 보관과 출입 허가, 미확인과 명시적 금지를 구분한다. 잘못된 출력을 통과시키도록 검증기를 완화하지 않았다.
2. **식별 정보:** Micro 입력에는 현재 스코프에서 검증된 엔터티 이름·별칭을 최대 64개 제공한다. 이는 식별 보조이며 사건·상태의 증거가 아니다. 정본의 확정된 현재 시퀀스에서 인용된 엔터티는 현재 상태 필드가 없어도 식별 정보를 보존한다. 과거·가정·전언을 현재 상태로 만들지 않는다.
3. **typed 위치:** Micro는 원문에 있는 목적지 이름을 제출한다. 런타임이 유일한 검증된 장소 ID로 바꿔 정본과 같은 `locationRef`에 연결한다. 미등록·모호한 장소는 보류한다. 표시와 응답에는 그 참조의 검증된 이름도 제공하며 정본 Head를 덮어쓰지 않는다.
4. **도메인별 반영:** 정본 전체가 `partial`이어도 현재 기준이 정확하고 해당 도메인이 준비됐으며 승인 결정이 유효하면 그 도메인의 Micro 변경을 투영한다. 준비되지 않은 도메인은 보류하고 전체 권위의 `pending`을 유지한다.
5. **뷰어:** `snapshot.continuityState`는 정본 기준으로 보존한다. 별도 `currentStateView`가 응답과 동일한 상태 투영을 읽으며 공개 내러티브 조회도 이 투영을 사용한다. 원문·Micro 본문·승인 결정·정본/레지스트리/세계선/설정 경계를 다시 확인한 뒤 화면 스냅샷을 게시한다. 검증에 실패한 Micro 투영은 정상 상태로 게시하지 않는다.
6. **자동 갱신:** Micro 게시와 정본 후 승인 재평가가 끝나면 갱신을 합쳐 실행한다. 열려 있는 인물·세계 뷰어뿐 아니라 상태 확인 창도 새로고침 없이 갱신한다. 창 자체를 교체하지 않아 버튼 포커스를 보존한다.
7. **표시:** 정본 기준 턴과 Micro 상태 턴을 구분한다. 원문만 보관된 Micro와 분석·상태 승인 성공을 구분한다. 필드 근거를 인물 상단 근거 개수에 포함하고, 서사 탭 배지는 각 분류의 실제 개수로 계산한다. 세계 읽기 화면에는 정본 필드 외에도 검증된 Micro 승인 근거가 있는 필드(예: 문 상태)를 표시하고 더 최신인 Micro 근거 턴을 배지에 반영한다. 임의의 예전 저장 필드를 자동으로 승인하지 않는다.

정본은 계속 유일한 영구 Head다. Micro 최신 상태는 승인된 읽기 투영이며 별도의 영구 상태 데이터베이스를 만들지 않는다. 모델 호출을 추가하는 자동 의미 수정 루프는 도입하지 않았다.

관련 기존 검사도 실행했다. 상태 승인·정본 경계·상속된 Micro·정본 재구축·부분 상태·관계/프로필 이력·읽기 전용 권위·GUI 상태 표시·서사 모델을 확인했다. 정본 후보의 물리적 저장과 세 저장 모드의 동작도 확인했다.

`libra_micro_vector_ranking_regression_test.cjs`와 `libra_micro_vector_ranking_runtime_test.cjs`는 통과했다. 후자는 1,024차원 벡터 30개를 실제 게시한 뒤 마지막 정답이 RAG 패킷에 전달되는지, 전체 30개 스캔과 top-8 선택이 유지되는지 검사한다. 검색 벡터·선별 개수·검색 임계값은 변경하지 않았다.

검사 도중 발견한 기존 시험 구성 문제도 정리했다. 프로필 이력 시험의 분리된 GUI 컨텍스트에 실제 코드가 요구하는 스코프 저장소를 제공했고, 서사 이력 시험의 오래된 소스 추출 끝 경계를 수정했다. 두 문제는 수정 전 Claude 소스에서도 발생했다.

### 기존 실패의 구분

`libra_consumed_micro_freshness_runtime_test.cjs` 전체 실행은 25개 중 21개가 Classic의 Micro 선택·상속 선택 사전조건에서 실패한다. **원본 Claude 소스로도 동일하게 4개 통과·21개 실패를 재현했다.** 이 작업에서 검색 선택이나 검사를 약화해 통과시키지 않았다. 상태 전용 본문 변조·승인 결정 삭제·무관한 결정·상속 승인 철회 4개는 별도 실행에서도 모두 통과했다. 따라서 전체 테스트 스위트가 통과했다고 주장하지 않는다.

## 실모델 검증

- LLM: Ollama `deepseek-v4.1-flash:cloud`.
- 임베딩: Voyage `voyage-4-large`, 1,024차원.
- 실제 전체 플러그인과 Chromium 1440×1000을 사용했다. 모델 출력은 대체하지 않았다.
- RisuAI 채팅·저장소·이벤트 API는 검증용 호스트이며 저장 모드는 `plugin_only`다. 실제 사용자 앱이나 원격 서버 모드의 실모델 시험은 아니다.
- 프롬프트에 실험용 문장을 끼워 넣지 않고 작업 브랜치의 제품 프롬프트를 그대로 호출했다. 관찰용 내부 참조만 메모리상으로 노출했다.
- 소유/소지/지식/관계/규칙/서사, 위치/포함 관계, 한 인물의 이동이라는 세 대화를 사용했다. 정본 저장 후 T6·T7의 Micro를 실제 생성하고 열린 화면과 상태 확인 창을 확인했다.
- 아래 수치는 최종 소스 검증 실행의 결과다. 개발 중 반복 시험은 별도 보관했다. 같은 대화 입력을 사용한 기능 검증이며 동일 저장 스냅샷을 고정한 성능 비교가 아니다.

| 입력 | 정본 | T6 Micro | T7 Micro | 열린 GUI·상태 창 |
|---|---|---|---|---|
| 소유·소지·지식·관계·규칙·서사 | `ready`, T5 | 주장 3개, 상태 승인 2개 | 주장 3개, 상태 승인 2개 | T6 → T7 자동 갱신 |
| 위치·포함 관계·문 상태 | `ready`, T5 | 주장 2개, 상태 승인 1개 | 주장 2개, 상태 승인 1개 | T6 → T7 자동 갱신 |
| 한 인물의 이동 | 공식 output 이벤트로 자동 정본 생성, `ready`, T5 | 주장 2개, 상태 승인 1개 | 주장 2개, 상태 승인 1개 | T6 → T7 자동 갱신 |

정본 3/3 저장·상태 준비, 후속 Micro 6/6 분석·상태 승인·응답/GUI 값 일치를 확인했다. 마지막 입력은 T5 Micro도 실제 생성했으므로 전체 호출은 정본 LLM 3회 + Micro LLM 7회, 임베딩 10회다. 별도의 상태 Observer나 GUI 조회용 모델 호출은 없었다. HTTP 오류·타임아웃·예산 중단은 관측하지 않았다. 브라우저 JavaScript 오류와 가짜 호스트 모델 경로 사용도 0회였다.

복잡한 입력에서는 민아의 암호 지식과 민아→지호 신뢰, 열쇠의 소유자/최종 소지자 민아, 출입 허가 `unknown`, 규칙과 관리/포함 관계를 확인했다. T6/T7에서는 인물 위치와 도서관의 `doorStatus`가 각각 변경됐다. 문 상태를 도서관 전체의 일반 조건으로 바꾸지 않았다. 영구 정본 Head는 T5로 유지됐다.

LLM 요청 지연은 정본 9.750초·4.495초·2.468초, Micro 1.241–1.690초였다. 임베딩 요청은 0.312–0.986초였다. 서버 prompt cache 적중과 VM 호스트·병렬 실행의 영향이 포함되어 있으며 콜드 성능이나 모델 간 속도 비교로 해석하지 않는다. 개발 중 반복 호출을 최종 표의 성공률 계산에 섞지 않았다.

세계 읽기 화면의 최종 필드 표시 수정은 같은 실제 모델 저장 스냅샷을 다시 읽어 모델 재호출 없이 확인했다. 원문·승인 결정을 재검증한 뒤 문 상태와 인물 근거를 표시한다.

## 한계와 기존 데이터

모델의 구조·의미 오류 가능성이 사라진 것은 아니다. 개발 중 같은 복잡한 입력에서도 `partial`이 관측됐으며, 계약에 맞지 않는 항목은 계속 보류한다. 등록되지 않은 대상·불명확한 참조·독립 검증이 필요한 고위험 상태·새 원문과 맞지 않는 승인은 자동으로 확정하지 않는다. 보류된 도메인을 다른 도메인의 성공으로 정상 처리하지 않는다.

이전에 원문만 보관된 Micro를 업데이트만으로 일괄 재분석하지 않는다. 기존 복구/재시도 경로를 사용해야 하며 새 호출에는 현재 원문과 저장 기준 검증이 다시 적용된다. 새 프롬프트의 실제 모델 시험은 작은 합성 입력 집합이므로 일반적인 정확도나 실패율을 뜻하지 않는다.

키가 들어갈 수 있는 원본 저장 스냅샷·설정·모델 로그는 `/tmp/libra-state-repair-20261018` 아래 비공개 경로에만 보관했다. 저장소에는 키·원본 스냅샷·원본 로그를 넣지 않았다.
