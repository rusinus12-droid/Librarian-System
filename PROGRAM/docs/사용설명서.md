LIBRA는 manifest와 물리 레코드가 없는 registry-only row, HAYAKU는 packet·worldline·recovery·archive 참조가 전혀 없는 단독 ledger, LIA는 content shard가 없는 index/proof metadata와 빈 shared index만 별도 껍데기 후보로 표시합니다. 같은 revision/digest 기반 fingerprint가 두 번의 명시적 새로고침에서 연속 일치하기 전에는 삭제할 수 없습니다.

검증된 껍데기도 RE:TRACE가 직접 지우지 않습니다. LIBRA 2.2.13, HAYAKU 3.0.26, LIA 0.26.59 Owner가 현재 열린 scope와 `server_only`를 차단하고 서버·pluginStorage 양쪽의 내용 부재를 다시 두 번 확인합니다. 공유 registry/index/proof에서는 대상 row만 제거하고 형제 row readback을 확인한 뒤 `plugin_only` 증명을 반환합니다. 그 뒤에만 Librarian System의 기존 전체 DB 백업과 revision/digest 조건부 mutation이 실행됩니다.

HAYAKU metadata-only ledger, ledger 없는 recovery/run 데이터, 모든 shared archive, LIBRA manifest 누락 데이터, LIA shard-only Persona 내용은 자동 삭제와 복구 페어링에서 계속 보호됩니다. LIA의 정상 저장 경로도 빈 index를 남기지 않고, shard 삭제와 Persona Proof 저장을 readback하며, shard/index 부분 실패 시 이전 shard를 복원합니다. 기존 DATA migration이나 기억·packet·Persona 재생성은 필요하지 않습니다.

## 0.3.9 Flashback 빈 서버 목록 껍데기 정리

RE:TRACE 1.9.62는 Flashback 서버 레지스트리에 행은 있지만 manifest·shard·archive·vector·tombstone이 하나도 없는 항목을 `registry_only_shell` 후보로 구분합니다. 첫 새로고침에서는 삭제를 막고, 같은 항목이 두 번째 명시적 새로고침에서도 물리 데이터 0건으로 확인되어야 정리 대상으로 전환합니다. 이런 항목은 복구할 본문이 없으므로 복구 페어링 버튼을 표시하지 않습니다.

삭제 검증을 시작하면 Flashback Memory 1.0.16이 서버 목록을 다시 두 번 읽고, pluginStorage와 local vector 저장소에도 해당 storage hash의 물리 키가 없는지 확인합니다. 현재 열린 Flashback 스코프, `server_only` 스코프, 확인 중 상태, fingerprint 변경, 물리 키 또는 tombstone 발견 시에는 중단합니다. 검증 성공 시 로컬 공유 레지스트리에서 대상 행 하나만 제거하고 형제 행 readback을 확인한 뒤, 기존 Librarian System의 서버 전체 DB 백업과 revision/digest 조건부 공유 레지스트리 rewrite를 수행합니다.

## 0.3.8 Flashback 스코프 목록 안전 복구

Flashback Memory 1.0.12는 서버 연결 실패를 `manifest 없음`으로 취급하지 않습니다. 스코프 목록을 열 때 한 번의 공용 Storage 연결 실패가 확인되면 같은 화면의 나머지 manifest 연속 조회를 중단하므로, 서버가 꺼졌거나 응답이 느릴 때 행 수만큼 제한시간이 누적되지 않습니다. 빈 manifest 조회는 기존 캐릭터·채팅 이름, 레코드·토큰·샤드 수와 마지막 데이터 갱신 시각을 덮지 않습니다.

Storage 페이지의 `목록 검사·복구`는 실제 manifest를 기준으로 레지스트리 표시 메타데이터를 다시 만듭니다. 물리 manifest가 없다는 결과가 서로 다른 검사 epoch에서 두 번 연속 확인된 항목만 `고아 레지스트리`로 표시합니다. 서버 오류, 손상 manifest, manifest 외 물리 키가 있는 항목은 자동 정리를 차단합니다. `목록 정리`는 삭제 직전에 manifest와 모든 Flashback scope/vector 키를 다시 검사하고 레지스트리 행만 제거하며 기억·샤드·벡터 데이터는 삭제하지 않습니다.

## 0.3.7 서버 스코프 관리와 Owner 탐색

RE:TRACE 1.9.61의 `서버 데이터 관리`는 삭제 가능한 스코프를 체크박스로 여러 개 선택한 뒤 한 번에 보존 증명과 삭제 계획을 만들 수 있습니다. 선택된 모든 스코프의 Owner가 서버 레코드를 pluginStorage/local에 복원하고 물리 readback까지 증명하기 전에는 서버 삭제 계획을 하나도 만들지 않습니다. 계획을 실행할 때도 스코프마다 서버 백업과 조건부 삭제를 수행하며 성공·실패 범위를 구분해 보고합니다.

잘못 연결되거나 자동 판정이 어려운 스코프는 실제 RisuAI 채팅 목록 중 현재 열려 있는 같은 캐릭터 채팅과 `복구 페어링`할 수 있습니다. 채팅 목록을 두 번 읽어 안정성을 확인하고 현재 chat ID, 캐릭터, 메시지 수, 제한된 대화 지문을 검증한 뒤 Owner 보존 readback을 통과해야 페어링 메타데이터를 기록합니다. 이 기능은 원본 서버 레코드를 임의의 대상 스키마로 재작성하지 않으며, 원본 서버 데이터와 복원된 로컬 사본을 유지합니다. 실제 정본 채택은 각 Owner의 전용 복원·승계 계약이 있을 때 그 Owner가 수행합니다.

Owner 기능 탐색은 저장 모드 조회를 기다리지 않고 이미 캐시된 상태를 사용하므로 GUI IPC 제한시간을 불필요하게 소모하지 않습니다. 서버 데이터 새로고침은 이전의 짧은 백그라운드 실패 캐시를 그대로 믿지 않고 최대 5초의 명시적 연결 검사를 먼저 수행합니다. HAYAKU Owner 응답이 없더라도 HAYAKU 서버 namespace의 읽기 전용 색인은 계속 수행합니다. Flashback은 GUI용 registry 요약을 우선 사용하고 대형 manifest 전체를 목록 판정용으로 선취하지 않습니다.

## 0.3.6 Compute GUI와 LIBRA GUI 응답성 (이력, 현재는 통합됨)

Flashback Memory 1.0.20, HAYAKU 3.0.26, LIBRA 2.2.13, LIA 0.26.59는 각 플러그인의 Server 페이지에 Compute 모드 설정을 표시합니다. `local`, `shadow`, `prefer_server` 중 하나를 고르면 해당 플러그인의 모든 채팅 스코프에 전역 적용됩니다. Storage 모드와 독립적이며 사용자 토큰·페어링 키 입력란은 없습니다. 비로컬 모드를 적용하면 자동 인증 확인을 백그라운드에서 한 번 수행하고, `Compute 연결 확인` 버튼은 사용자가 원할 때만 강제 연결 검사를 합니다.

LIBRA 설정 창은 fullscreen host RPC를 기다리기 전에 로컬 shell과 첫 화면을 구성하고, canonical job 상태를 백그라운드에서 갱신합니다. Server 페이지의 Storage와 Compute 카드는 즉시 loading surface를 표시한 뒤 독립적으로 mount되므로 어느 한 연결 확인이 느려도 페이지 전체가 빈 화면으로 남지 않습니다.

## 0.3.5 현재 요청 Compute 위임과 자동 인증 (이력, 독립 selector는 폐기됨)

LIBRA 2.2.4, HAYAKU 3.0.14, Flashback Memory 1.0.9, LIA 0.26.55는 단일 JavaScript 본체와 기존 local kernel을 그대로 보존합니다. 각 `memory_suite_*_compute_mode`의 기본값은 `local`이며 서버 탐색과 Compute 네트워크 호출이 0회입니다. 서버가 한 번도 실행되지 않았거나 실행 중 중단돼도 연산은 플러그인 안에서 완료됩니다.

`prefer_server`는 현재 요청의 snapshot을 interactive lane으로 직접 제출하고 플러그인별 제한 시간 안에 도착한 서버 후보를 검증합니다. operation, algorithm fingerprint, input/result digest, scope·branch·worldline·persona binding과 결과 shape가 모두 맞을 때만 같은 요청에서 채택합니다. 연결 거부, 자동 인증 실패, queue 포화, timeout, Worker crash, 서버 중단, 결과 불일치나 현재성 변경에서는 기존 local kernel을 정확히 한 번 실행합니다. remote-only 모드는 없습니다.

`shadow`는 local 결과만 채택하고 서버 비교를 비동기로 실행합니다. 플러그인 unload 시 SDK는 알고 있는 미완료 Job을 제한 시간 안에서 자동 취소하고 fetch·cache·timer를 정리합니다. 동기 execute의 HTTP 연결이 끊어지면 서버도 같은 namespace/operationId의 실행을 자동 취소합니다.

Compute 인증은 Storage bootstrap이나 사용자 pairing/token 입력 없이 `POST /v1/compute/bootstrap`으로 자동 수행됩니다. 서버 내부 `compute-signing-key.txt`는 token 서명용일 뿐 사용자가 열거나 플러그인 GUI에 입력하는 값이 아닙니다. 인증 신뢰 경계는 loopback과 공식 plugin ID이며, 같은 사용자 계정의 악성 로컬 프로세스를 암호학적으로 구분하는 구조는 아닙니다.

서버는 shared Worker pool과 namespace 공정 큐를 사용합니다. 여러 요청이 실제로 동시에 도착하면 빈 Worker 수만큼 병렬 실행됩니다. 다만 RisuAI가 같은 `beforeRequest`의 플러그인 훅을 순차 await하는 경계는 바뀌지 않으므로, 동일 모델 요청에서 네 foreground 작업이 반드시 동시에 시작된다고 보장하지 않습니다. output 이후의 background 작업과 별도 시점 요청은 서로 중첩될 수 있습니다.

## 0.3.3 이전 Compute 파일럿 기반

Librarian System 0.3.9는 저장 서버와 분리된 Compute Protocol 1.1 및 Compute SDK 0.3.3을 제공합니다. 플러그인의 단일 JavaScript, GUI, RisuAI 훅, 데이터 소유권과 최종 채택 권한은 그대로이며, 서버는 allowlist에 등록된 결정론적 연산 candidate만 공용 Worker pool에서 반환합니다. Compute Plane은 canonical SQLite를 직접 쓰지 않습니다.

플러그인 Compute 기본값은 `local`입니다. 이 모드에서는 capability probe와 `nativeFetch`가 0회이며 서버가 없어도 기존 JS kernel만으로 계산합니다. `shadow`는 로컬 결과를 즉시 채택하고 서버 후보를 백그라운드 비교합니다. `prefer_server`는 operation, algorithm fingerprint, input/result digest, binding과 결과 shape를 모두 검증한 후보만 채택하며 실패하면 같은 로컬 kernel을 정확히 한 번 실행합니다. remote-only 모드는 없습니다.

현재 0.3.18의 실제 파일럿은 Flashback Memory 1.0.26의 `flashback.hash-embedding-batch.v1`, LIA 0.26.62의 `lia.world-lore-rerank.v2`, LIBRA 2.3.25의 `libra.recall-bm25f.v1`, HAYAKU 3.0.42의 `hayaku.sparse-rrf-fusion.v1`입니다. 각 플러그인의 현재 스코프가 미러 또는 서버 단독이면 Compute token을 자동 발급·갱신하고 `prefer_server`로 실행합니다. 플러그인 단독이면 로컬만 사용합니다. `server-config.json`의 `computeEnabled`는 Compute만 끄며 Storage는 유지합니다. `computeWorkers`는 0(자동) 또는 1~16이고 기본 자동 pool은 CPU 수에 따라 최대 4개입니다.

LIA World Lore, LIBRA Recall BM25F와 HAYAKU sparse RRF는 `prefer_server`에서 현재 요청을 직접 위임합니다. LIA는 character/chat/persona/lore inventory/query, LIBRA는 scope/branch/manifest/query/candidate, HAYAKU는 visible transcript/worldline/query/row binding을 응답 뒤 다시 확인합니다. 서버는 점수 candidate만 반환하고 원래 객체 materialization, RRF 이후 gate, prompt 주입과 영구 저장은 각 플러그인이 수행합니다.

LIBRA Recall BM25F도 후보 hydration 뒤의 기존 로컬 scorer를 그대로 보존합니다. query와 최대 64개 canonical 후보의 8개 sparse field만 서버에 보내며, 서버는 canonical memory, Recall Catalog, manifest나 prompt를 수정하지 않습니다.

네 owner 플러그인이 요청을 제출하면 namespace 공정 큐와 `interactive`, `background`, `maintenance` lane으로 Worker 실행이 중첩될 수 있습니다. interactive admission은 낮은 우선순위 backlog를 자기 deadline의 선행 대기량으로 세지 않으며, 빈 slot을 background보다 먼저 받습니다. HAYAKU도 서버 후보가 없거나 유효하지 않으면 기존 로컬 수식을 그대로 사용합니다.

격리된 자식 프로세스의 product-kernel matrix에서 Worker 1/2/4/8의 동시 namespace 수는 각각 1/2/4/4였고 처리량 계수는 0.727/1.120/1.316/1.448, peak RSS delta는 248.96/291.41/334.75/423.34 MiB였다. 현재 시험 host에서는 Worker 8의 추가 이득보다 RSS 비용이 커서 자동 상한 4를 유지한다. 이 값은 localhost 회귀 fixture의 단일 host 관측치이며 실사용 대화나 시스템별 최적값을 보장하지 않는다.

상세 wire 계약과 구현·검증 범위는 [COMPUTE_PROTOCOL.md](COMPUTE_PROTOCOL.md), [COMPUTE_IMPLEMENTATION_REPORT.md](COMPUTE_IMPLEMENTATION_REPORT.md)를 참조합니다.

## Historical / retired helper workflow: 0.2.28 GRADIA SHADOW/AIDE 구조화 실행 보강

메인 응답에 명시적인 reasoning wrapper가 노출되면 GRADIA 모드에서만 제거합니다. 안전하게 분리할 수 없고 마지막으로 검증된 GRADIA 초안이 있으면 그 초안으로 되돌리며, Classic/Planner와 일반 응답에는 이 가드를 적용하지 않습니다.

## 0.2.27 LIBRA typed 정본 생성과 상태 추적 분리

LIBRA 2.2.0은 Ariadne의 자유형 Markdown을 바로 저장하지 않습니다. Provider는 근거 TURN 표지가 붙은 `libra.canonical_artifact.v2` JSON 후보를 반환하고, LIBRA가 스키마·근거 범위·크기·추론/메타 문구를 로컬에서 검사한 뒤 일곱 개 고정 섹션의 읽기 가능한 정본을 결정론적으로 렌더링합니다. 실패하거나 잘린 응답은 이어붙이지 않으며 원문 근거로부터 한 번만 새 후보를 교정 생성합니다. 두 번 모두 검증에 실패하면 활성 정본·리콜·상태 Head는 변경하지 않습니다.

상태 추적 기본값은 `basic`입니다. ## 0.2.25 LIBRA 가져오기 중단 복구와 손상 영수증 수리

LIBRA의 `새 채팅으로 기억 이사`와 `채팅 복사 기억 복구`는 대상 스토리지를 쓰기 전에 영속 rollback journal을 먼저 저장합니다. 플러그인 재로드나 앱 종료로 가져오기가 중단되면 다음 시작 또는 재시도에서 미완료 쓰기를 원상복구한 뒤 다시 진행합니다. 상태 전용 재분석 중 새로 만들어진 continuity delta도 같은 롤백 범위에 들어갑니다.

완료 영수증은 실제 기억·공유 archive·벡터·현재 상태 Head를 다시 읽어 검증합니다. 손상되었으면 영수증이 소유한 기억만 제한적으로 재구성하고, 다른 기억이나 비활성 variant와 충돌하면 덮어쓰지 않고 중단합니다. 구버전 채팅 복사 영수증도 `continuityRequired` 필드 유무와 관계없이 현재 상태 Head를 필수로 검사합니다.

JSON 그래프 검증은 기억의 scope, TURN 범위, revision, source digest와 continuity delta의 원본 기억 연결을 함께 확인합니다. 같은 채팅 되돌리기는 현재 scope를 값으로 소유한 레거시 키도 백업에 없으면 정리하지만 공유 archive/vector는 계속 보존합니다.

## 0.2.24 LIBRA JSON 복원 안전성 보강

동일 채팅 되돌리기는 다른 채팅도 참조할 수 있는 공유 archive/vector를 교체 삭제 대상에서 제외합니다. 채팅 복사는 기존 비활성 기억과 키가 충돌하면 덮어쓰지 않고 중단하며, 실패 롤백은 쓰기 전 값을 정확히 복구합니다. 완료된 가져오기 기록도 실제 기억·archive·상태 추적을 다시 읽어 검증한 경우에만 재사용합니다.

채팅 복사의 상태 추적 재구축과 readback은 이제 채택 완료 조건입니다. 중단 복구는 데이터 롤백 완료 표시를 체크포인트에 먼저 영구 기록하므로 journal 마무리가 일시적으로 실패해도 다음 시작에서 오래된 체크포인트를 다시 적용하지 않습니다. 성공한 내부 체크포인트와 journal은 검증 후 정리되어 반복 복원으로 플러그인 저장소가 계속 커지지 않습니다.

## 0.2.23 LIBRA JSON 기억 백업·복원과 채팅 이사

LIBRA의 JSON 기억 백업과 복원은 사이드바의 `복구` 화면에 있는 `기억 복원 · JSON` 카드에서만 사용합니다. 현재 채팅의 정본 기억·벡터·상태 delta·State Head·Story Arc·사용자 보존 버전과 복원에 필요한 참조 데이터를 JSON 파일로 내려받습니다. 불러온 파일의 무결성과 소유 scope를 먼저 검사한 뒤 현재 상황에서 안전한 방식만 선택할 수 있습니다.

- `같은 채팅 되돌리기`: 같은 캐릭터와 chatId의 현재 스코프를 백업 시점으로 정확히 교체합니다. 백업에 없는 현재 스코프 레코드는 제거하지만 다른 채팅의 데이터는 건드리지 않습니다.
- `새 채팅으로 기억 이사`: 같은 캐릭터의 비어 있는 새 채팅에서 이전 기억을 영구 과거 아카이브로 연결합니다. 이전 TURN을 현재 TURN인 것처럼 복제하지 않습니다.
- `채팅 복사 기억 복구`: 다른 chatId여도 현재 대화 본문과 백업의 5턴 묶음 내용 지문이 처음부터 연속해서 일치하는 구간만 현재 스코프에 재바인딩합니다. 최초 불일치 이후는 가져오지 않고 현재 세계선에서 다시 분석합니다.

다른 캐릭터의 파일, 이미 활성 정본이 있는 이사 대상, 불연속·충돌 구간은 차단합니다. 같은 채팅 교체 전에 트랜잭션 스냅샷과 journal을 먼저 쓰며 실패하면 원래 값으로 롤백하고 readback을 검증합니다. 쓰기 도중 플러그인이 재로드되면 다음 시작에서 미완료 journal을 찾아 스냅샷으로 자동 복구하며, 성공한 내부 복구 자료는 검증 후 정리합니다.

이 카드는 `↓ JSON 백업 다운로드`, `↑ JSON 백업에서 복원`을 명시적으로 표시합니다. 헤더나 다른 버튼 줄, 화면 우측 하단에는 백업·복원 버튼이 나타나지 않습니다. 정본 작업 또는 응답 파이프라인이 실행 중이면 JSON 작업을 시작하지 않으며, 복구 화면이 다시 렌더되어도 진행 상태와 버튼 잠금이 유지됩니다.

## 0.2.21 정본 관리와 Memory Lane 동작

Memory Lane은 새 정본 메모리나 세 플러그인 공용 저장소가 아닙니다.

- **LIBRA**: Recall Catalog가 충분히 커졌을 때만 비영속 Catalog Block Index를 사용합니다.
- **HAYAKU**: 기존 Global Packet/Hierarchical Episode Router가 희귀 구문·엔티티와 document-frequency 신호를 사용합니다.
- **Flashback**: 기존 Recall Shard Index v4가 Lane 역할을 하며 관련 shard를 먼저 선택합니다.

세 플러그인 모두 원본을 참조만 하고 신규 LLM·임베딩 호출을 만들지 않습니다. 모호한 입력에서는 후보 범위를 넓히고, 파생 인덱스가 없거나 손상되면 기존 Recall 전체 경로를 사용합니다. 일반 사용자가 Lane 크기나 TF-IDF 값을 설정할 필요는 없습니다.

Flashback hash, LIA World Lore, LIBRA Recall BM25F와 HAYAKU sparse RRF Compute 파일럿은 기존 로컬 결과와 owner 채택 경계를 유지하며 강제 재임베딩·packet·Persona 재생성을 수행하지 않습니다.

### API v3 저위험 안정성 보강

LIBRA와 Flashback은 RisuAI `getRuntimeInfo()`의 `apiVersion/platform/saveMethod`를 진단 정보로만 기록합니다. HAYAKU와 LIA는 stable UI id와 `unregisterUIPart()`를 사용해 업데이트·핫리로드 때 설정/버튼 잔존을 줄입니다. 이 정보로 기능 지원 여부를 강제하지 않으며, Inlay/fetch-log 수집도 추가하지 않습니다.


### HAYAKU 3.0.14 · 안전한 파일 기반 JSON 복원

HAYAKU의 정상 채팅 경로는 본편 응답이 작성한 `current_snapshot` 하나를 그대로 사용합니다. 현재 턴의 패킷이 없거나 사용할 수 없고 `after request 자동 복구`가 켜져 있을 때만, afterRequest가 RisuAI 공식 `runLLMModel`의 `otherAx` 모드로 정확히 한 번 복구를 시도합니다. 이 호출은 별도 확인창을 띄우지 않는 정상 파이프라인이며, 성공한 `current_snapshot`은 같은 Assistant 응답에 기록된 뒤 실제 채팅 출력 readback으로 확정됩니다. 이미 쓸 수 있는 패킷이 있으면 추가 LLM 호출은 0회입니다.

afterRequest 복구가 실패했거나 건너뛰었거나 해당 설정이 꺼져 있으면 응답은 지연시키지 않고 정확한 완료 U+A, 원본 해시, 실패 진단과 모델이 반환한 원시 후보를 Recovery Journal에 보존합니다. 자동 복구는 afterRequest 1회가 유일한 단계입니다(2026-10-16부터). 백그라운드 자동 복구와 확인창, 실패 복구 자동 처리는 퇴역했고 `hayaku_background_auto_repair`·`hayaku_native_auto_repair` 값은 무시됩니다. Journal 항목은 복구 화면의 수동 복구, 실패 복구 화면의 수동 채택·LLM 복구·직접 수정 대상으로 남습니다. 타이머 기반 무인 재시도는 하지 않습니다. HAYAKU에는 Provider, API key, 모델 선택 설정이 없습니다.

복구 결과는 현재 active worldline의 turn/node/variant와 U+A hash를 다시 확인한 뒤 원장에 채택하며, 물리 readback까지 성공해야 debt를 제거합니다. 리롤·롤백으로 대상이 달라졌다면 늦게 도착한 결과를 저장하지 않습니다. Provider/연결 실패 시 즉시 같은 요청을 중복 호출하지 않고 debt를 유지합니다. 초기 분석의 primary→repair 내부 교정은 실패 원인과 이전 응답을 포함해 한 번만 시도하며, 그 두 번째 응답이 통과해도 검토 가능한 실패 기록을 남깁니다. 반대로 실패 복구 화면에서 사용자가 `2. Cold Start는 HAYAKU의 `복구 / Cold Start` 화면에서 사용자가 직접 시작합니다. 기존 완료 U+A를 턴별 checkpoint로 분석하고, 실패 후 재개하면 이미 검증된 턴은 다시 호출하지 않습니다. 자동 Cold Start는 하지 않습니다. 복구 화면의 상태 새로고침은 LLM을 호출하지 않고 현재 세계선의 완료 턴을 검사하여 정확한 누락 턴과 즉시 복구·재시도 대기·시도 한도·처리 중·사용자 제외 턴을 구분해 표시합니다. HAYAKU 기록과 현재 대화의 유효 패킷이 모두 없는 세션은 Packet Debt가 아니라 Cold Start 대상으로 `1–N` 범위를 표시합니다. 수동 복구, Cold Start, 패킷 재생성은 같은 중앙 작업창에서 단계·대상 턴·실제 checkpoint 진척도·경과 시간을 표시하며 안전한 중단을 요청할 수 있습니다. 작업창을 최소화하면 헤더 오른쪽의 실시간 진행 표시로 바뀌고 이를 누르면 다시 열립니다. 특정 패킷 재생성은 원장을 즉시 바꾸지 않고 후보를 저장한 뒤 기존 패킷과 나란히 비교하여 기존 유지 또는 후보 채택을 선택합니다. 교체로 tombstone된 이전 패킷과 재생성 세트는 현재 세계선 검증과 durable readback을 거쳐 다시 선택할 수 있습니다.

프롬프트 상세도 `Auto`는 단순히 Balanced의 별칭이 아닙니다. 성능 모드가 Deep이거나 정밀 회상·패킷 복구 신호가 있고, 요청 압력이 normal이며 Full 주입 용량의 안전 여유가 있을 때만 Full을 선택합니다. 그 외에는 Balanced를 선택하고, 사용자가 지정한 Balanced/Full은 그대로 존중합니다. 기억 언어의 기본값 `source`는 완료된 본문과 확립된 이야기의 언어를 따라 다국어 대화의 언어를 보존합니다. `ko`·`en`·`ja`·`zh`를 직접 고르면 새 패킷의 사람이 읽는 값을 해당 언어로 고정합니다. 검색 시에는 네 언어의 공통 별칭을 계속 사용하지만, 이것만으로 `ko` 출력이 다국어 출력이 되는 것은 아닙니다. Other Ax 자동 복구는 평상시 LLM을 부르지 않지만 누락 부채를 발견하면 RisuAI Provider 호출 비용이 발생할 수 있습니다. Cold Start 기본 묶음은 안전한 1턴이며, 호출 횟수 절감을 원하는 경우 GUI의 5턴 속도 권장 프리셋을 선택할 수 있습니다.

검증 실패, JSON 형식 실패, 패킷 용량 초과 또는 정규화 과정의 필드·배열 손실이 발생하면 원문을 버리지 않고 `실패 복구` 페이지에 보존합니다. 원본 U+A는 chunk별 hash와 물리 readback으로 보존하고, 고정 시스템·요청 프롬프트 전체는 중복 저장하지 않고 역할·길이·digest descriptor만 남깁니다. 모델의 원시 후보·응답 metadata·오류·canonical preview는 별도로 보존합니다. `1. 그대로 채택`은 저장된 canonical preview만 추가 LLM 없이 승격하고, `2. LLM 자동 복구`는 사용자가 누른 시점에 Other Ax를 정확히 한 번 호출하며, `3. 직접 수정`은 사용자가 편집한 JSON을 로컬 검증한 뒤 승격합니다. 세 경로 모두 현재 scope·U+A·worldline·대상 debt를 다시 확인하고 정본 readback이 끝나야 완료됩니다. 검토 대기 중인 debt는 자동 재호출하지 않습니다.

HAYAKU 3.0.26의 Recovery Journal은 누락된 완료 턴의 U+A 전체를 `hayaku.recovery_evidence_manifest.v1`과 64,000자 이하 chunk에 먼저 기록하고, 모든 chunk의 문자 수·UTF-8 byte 수·digest와 manifest readback이 확인된 뒤에만 내부 호환 row가 이를 참조합니다. 내부 저장 키와 백업 schema의 `recovery_vault` 명칭은 기존 데이터와 Portable Backup 호환성을 위해 유지하지만, 사용자 화면과 동작 개념은 “실패 증거와 처리 상태를 남기는 Recovery Journal”입니다. 240,000자 경계의 기존 inline 자료는 완전성을 추정하지 않고 현재 채팅의 같은 pair/worldline/hash에서 전체 원문을 다시 읽을 수 있을 때만 sidecar로 재수화합니다. 요청 전체가 안전 한도를 넘으면 앞뒤를 자른 Other Ax 호출을 하지 않고 `evidence_over_request_budget`으로 실패 복구에 보냅니다. 자동 누락 복구 응답은 `hayaku.native_repair_output.v1` envelope를 사용하며, 여섯 canonical axis 밖의 필드, TARGET TURN에 없는 인용·관계·상태, grounding 누락과 coverage 부족은 자동 정본 승격하지 않습니다. 실패 복구 상세에는 원본 완전성, manifest digest, 실제 호출 여부·요청 예산, grounding/coverage 원인을 따로 표시합니다. 고정 시스템·요청 프롬프트 전체는 Journal에 중복 저장하지 않고 역할·길이·digest descriptor만 남기며, 모델의 원시 후보와 실제 실패 진단은 보존합니다. Portable Backup은 Journal row가 참조하는 manifest와 모든 chunk를 포함하고 복원 전에 내부 digest graph까지 다시 검증합니다.

복구 탭의 `기억 복원 · JSON` 카드는 format v3부터 각 레코드의 채팅 소유권과 대화 턴 해시 목록을 함께 저장합니다. 같은 채팅 복원은 현재 채팅이 소유한 기록만 교체하므로 다른 채팅의 원장을 삭제하지 않습니다. 소유권 표기는 가져올 때 원본 scope와 저장 키·최상위 소유자 필드로 다시 증명하며, 재서명된 파일이라도 외부 scope 키를 현재 채팅 소유로 위장할 수 없습니다. 공유 아카이브는 검증된 원장이 `storageKey`·`metaKey` 같은 명시적 참조 필드로 가리킬 때만 백업에 포함되고, 본문·메타데이터·누적 digest·부모 연결·원장 참조가 모두 일치할 때만 복원합니다. 같은 키에 다른 불변 데이터가 있으면 덮어쓰지 않고 중단합니다. `새 채팅으로 이사`는 원장뿐 아니라 Recovery Vault와 네이티브 복구 작업을 포함한 대상 HAYAKU 상태가 비어 있을 때만 이전 기억을 불변 과거 아카이브로 연결하고, 과거 슬롯·tombstone·복구 작업을 현재 월드라인에 그대로 이식하지 않습니다. `복사된 채팅 복구`는 현재 대화와 백업의 사용자/Assistant 본문 해시를 일대일로 대조하여 정확히 일치하는 턴만 새 메시지 ID와 월드라인에 다시 결속합니다. 불일치·중복으로 모호한 턴은 자동 채택하지 않습니다. 다른 캐릭터로의 복원은 차단하며, 세션 안에서만 유효한 `charIndex` 대체값은 다른 채팅의 동일 캐릭터 증거로 인정하지 않습니다. format v1/v2 백업은 호환 복원하되 같은 채팅에서만 사용할 수 있습니다. 백업 생성과 모든 복원·이사·복사 트랜잭션은 HAYAKU 저장 큐에서 직렬 실행됩니다. 확인 뒤 물리 트랜잭션이 끝나기 전까지 대상 기억과 대화 턴 지문을 다시 검사하며, 변경이 감지되면 중단합니다. 실패하면 이번 작업이 실제로 수정한 원장·공유 아카이브·메타데이터만 작업 전 상태로 되돌리고, 캐시가 아닌 물리 저장소 readback으로 검증합니다. 서버 라우팅 저장소가 쓰기를 거부하면 로컬 호환 저장소로 우회하지 않습니다. 복원 입력은 JSON 백업 파일 선택으로 통일했으며, 실제 쓰기 전 비교 확인과 대상 기억 자동 안전 백업을 제공합니다. 복구 엔진의 채팅 범위 미확인 상태는 늘어나지 않는 작은 배지로 표시하고, `누락 복구 실행`과 `Cold Start 실행`은 같은 크기를 사용합니다. Portable Backup UI는 이 전용 카드 안에서만 표시되며, 패킷 뷰어의 `원장 JSON 내보내기`는 조회·진단용이라 복원 파일로 사용할 수 없습니다. 원장 뷰어는 중앙의 HAYAKU 창과 작업 상태를 그대로 유지합니다. Recovery Journal 누락 확인은 원장 뷰어를 자동으로 열지 않는 독립 경량 오버레이로 표시하고, 독립 확인 UI를 표시할 수 없으면 자동 복구를 시작하지 않고 저널을 pending으로 유지합니다. 바깥 영역은 시각적으로 RisuAI를 비추지만 클릭은 통과시키지 않습니다. RE:TRACE 1.9.60에는 분석 복구 화면·실행 API·프로바이더 설정이 없으며 HAYAKU 복구 작업을 시작하거나 위임하지 않습니다. HAYAKU 3.0.14이 플러그인 시작 시 캡처한 RisuAI API 프록시로 내장 Provider의 `runLLMModel`을 직접 사용합니다.

긴 채팅의 worldline observer는 정확한 메시지 revision cache를 먼저 확인합니다. 변경되지 않은 Assistant의 packet diagnostics를 재사용하고 편집·리롤된 Assistant만 다시 분석하며, 롤백 시 사라진 메시지 entry만 제거합니다.


### LIBRA 2.1.0 · Flashback 1.0.2 장기챗 Revision Cache

LIBRA와 Flashback은 HAYAKU 구버전처럼 idle timer가 전체 채팅을 반복 재진단하지는 않지만, 긴 채팅에서 실제 send/output event마다 동일한 메시지를 다시 sanitize·hash·pair-build하는 비용이 있었습니다. 두 플러그인은 이제 scope별 exact revision cache를 사용합니다.

- LIBRA: unchanged message projection과 completed U+A pair snapshot을 재사용합니다.
- Flashback: unchanged normalized descriptor와 live U+A pair-state를 재사용합니다.
- edit/reroll은 변경된 메시지만 다시 계산합니다.
- rollback은 사라진 suffix entry만 제거합니다.
- append는 새 메시지만 계산합니다.
- sampled fingerprint를 권위 판정에 사용하지 않으며 cache는 크기 제한을 가집니다.

정확한 변경 감지를 위해 host chat array를 가볍게 순회하는 과정은 유지합니다. 따라서 완전한 O(1) 처리는 아니지만, 동일 본문의 반복 정규화와 동일 U+A 구조 재생성 비용을 줄입니다. 기존 LIBRA canonical memory와 Flashback record/shard/vector/archive 형식은 변경하지 않습니다.

### RisuAI 2026.8.240+ 최종 메시지 캡처

LIBRA, HAYAKU, Flashback, LIA는 RisuAI 공식 `addRisuChatListener('output')` 이벤트를 커밋된 Assistant 출력의 기본 진입점으로 사용합니다. Listener는 `messageIndex`, 해당 chat snapshot, character/chat 위치를 기록하고 즉시 반환하므로 네 플러그인을 동시에 사용해도 한 플러그인의 임베딩·packet 처리·Ariadne/ito·Live Persona 분석이 다음 listener를 직렬로 막지 않습니다. Auto Continue로 같은 Assistant 슬롯이 갱신되면 별도 턴을 만들지 않고 같은 논리 U+A의 새 revision으로 upsert합니다.

`output` 이벤트 뒤에도 RisuAI Auto Continue 또는 IGP가 본문을 바꿀 수 있으므로 이벤트 횟수를 턴 수로 사용하지 않습니다. LIBRA와 LIA는 각각 정본/Live Persona 5턴 결과를 적용하기 전에 원래 chat과 source revision을 재검증합니다. HAYAKU와 Flashback은 다음 authoritative beforeRequest/live-chat reconciliation에서 최신 U+A로 최종 정합화합니다. 공식 listener가 없는 구버전·포크에서는 각 플러그인이 script output 또는 afterRequest reconcile 가운데 하나의 legacy backend만 선택합니다. LIA의 Persona Proof와 감정 에셋 afterRequest 후처리는 캡처 backend와 별개로 유지됩니다.

## Historical / retired helper workflow: LIBRA의 메인 모드와 GRADIA 초안 작성

> Helper operational instructions in this section are retired. Shared memory, state, BM25F, direction and storage facts are retained as historical reference.


LIBRA 설정창의 최상위 헤더에서 `LIBRA` 또는 `GRADIA`를 선택합니다. 모드를 바꿔도 12개 공통 사이드바와 `기억 / 인물 / 관계 / 세계 / 내러티브` 읽기 화면은 바뀌지 않습니다. 둘은 같은 Canonical Memory, Current State Head, 리콜, AI·Embedding 연결과 실행 기록을 사용합니다. 내부 plugin ID, 저장 namespace·키와 RE:TRACE IPC도 기존 `LIBRA` 계약을 유지합니다.

- LIBRA: `Planner`, `Classic`
- GRADIA: `소설`, `RP`

LIBRA의 `파이프라인 > 응답 생성`에서는 Classic/Planner, Planner 작성 언어와 별도의 `서사 방향`을 정합니다. 이 서사 방향은 미래 작성 지시이며 `내러티브` Current Head의 현재 사실이나 정본 기억으로 저장되지 않습니다.

GRADIA의 같은 응답 생성 영역에서는 목표 글자 범위, 작성 언어, 소설의 `Classic`/`인풋 포함` 계약을 정합니다. 경량/중량 실행, SHADOW와 Character/World/Plot AIDE의 활성화·AI 프리셋·순서·단계별 제한 시간·컨텍스트·출력 토큰도 이 초안 경계에서 설정합니다. `Skill`에서는 내장 39개 Skill과 29개 reference의 Top-K, reference 사용, 단계별 우선도와 사용자 Skill을 관리합니다. 사용자 Skill은 초기 적용 범위, reference JSON, 기본 우선도와 설명까지 저장하며 원본 `SKILL.md`와 실제 단계 컴파일 결과를 미리 볼 수 있습니다. `출력`에서는 최종 마무리 엔진, 전달 자료, 주입 위치, 실패 처리와 최대 1회의 최종 길이 보정을 정합니다.

중량 분석에서는 최종 모델에 보낼 자료를 두 가지로 선택할 수 있습니다. `초안만 전달`은 SHADOW/AIDE가 LIBRA 장기기억, 최근 장면, Live Tail, 통합 로어와 Story Arc를 분석해 만든 초안과 최소 마무리 계약만 전달합니다. `초안 + 분석 정보 전달`은 같은 초안에 각 단계에서 실제 사용된 정규화 분석 정보를 보호 결과물로 함께 전달합니다. 초안과 선택된 분석 의미는 문자 상한 때문에 중간 절단하지 않습니다. 따라서 초안만 전달해도 기억과 에이전트의 판단이 반영된 결과이며, 원문 장기기억이나 비공개 분석을 다시 중복 전달하지 않습니다. 경량 파이프라인은 별도 단계 분석 호출이 없으므로 초안 전달로 고정되며, 중량 파이프라인에서 고른 값은 보존됩니다.

RP는 사용자가 아직 하지 않은 행동·대사·동의·감정을 대신 결정하지 않습니다. 소설은 사용자를 작가/디렉터로 보고 명시적으로 고정·예약·금지한 범위를 보호하면서 전체 캐스트를 집필합니다. `인풋 포함`은 현재 인풋의 의도와 고정 사항을 초안에 적극적으로 포함하고, `Classic`은 현재 장면의 인과에서 다음 장면을 전개합니다.

GRADIA 모드는 기존 LIBRA의 AI 연결 프리셋과 provider 인증을 재사용합니다. `AI 연결`의 `전역 기본 AI 연결`은 공통 기억 파이프라인과 LIBRA·GRADIA 초안, Input Writer에서 개별 연결을 비워 둔 단계의 공통 폴백입니다. 별도 런타임 토큰 입력이나 새 인증 절차는 없습니다.

## 최신 상태 추적

`인물`, `관계`, `세계`, `내러티브`는 정본 메모리와 다른 역할을 합니다. 정본은 5턴 단위의 사건과 근거를 계속 누적하지만 이 네 화면은 활성 정본 체인에서 마지막으로 검증된 최신값만 보여 줍니다. 모델의 비공개 분석 원문은 정본으로 저장하지 않습니다.

- 인물: 현재 위치, 신체 상태, 소지품, 목표, 지식 경계, 관찰 가능한 감정 등
- 관계: `주체 → 대상` 방향과 신뢰·애정·두려움·의무·적대·거리·협력·권한·의존·지식 차원
- 세계: 장소, 사물, 조직, 규칙, 환경, 현재 조건과 접근·소유·사용 가능 상태
- 내러티브: 현재 활성 Arc, 열린 Thread, Lock, momentum과 현재 의미

기억 작성 Ariadne와 Character/World/Narrative ito는 `canonical_artifact.v3` 정본만 작성하고 상태 patch를 만들지 않습니다. 정본 커밋과 readback 뒤 `신규 인물 승인`이 독립 decision/receipt로 새 person assertion을 fail-closed 검증합니다. 승인된 ID·별칭만 Entity Registry와 관계 endpoint가 사용할 수 있으며 검증되지 않은 관계 endpoint는 새 인물 placeholder를 만들지 않습니다. 그 뒤 Character, Relationship, World, Narrative Observer가 별도 호출로 `state_observation.v2` 후보를 만들며, 필요한 변경만 조건부 Verifier와 로컬 evidence·identity·no-op gate를 통과합니다.

Observer가 필드를 생략하면 이전 값은 그대로 유지됩니다. 새 값이 기존 값과 의미상 같으면 provenance와 `changedThrough`를 갱신하지 않고 검토 진행점인 `reviewedThrough`만 전진할 수 있습니다. `clear`는 정본의 직접적인 상실·종료·무효화·정정 근거와 조건부 검증이 있을 때만 적용됩니다. 한 도메인의 provider/schema/readback 실패는 그 도메인의 last-known 값을 보존하고 다른 도메인과 정본 커밋을 되돌리지 않습니다.

Planner와 GRADIA는 현재 정본 fingerprint와 일치하는 헤드만 사용합니다. 아직 5턴 정본 경계에 들어가지 않은 최근 대화는 Live Tail로 요청 순간에만 겹쳐 보며 저장하지 않습니다. 분기 변경으로 정본과 헤드가 맞지 않으면 오래된 상태를 주입하지 않고 새 정본 경계에서 부분 상태부터 안전하게 다시 만듭니다.

## 정본 작업과 버전 관리

`기억` 화면에서 `수동 콜드스타트`, `현재 5턴 분석`, `실패 배치 복구`를 실행할 수 있습니다. 작업 중에는 실제 배치와 단계, TURN 범위, 완료·실패 수와 경과 시간이 표시됩니다. provider 내부 진행률을 알 수 없는 단계에는 가짜 백분율을 표시하지 않습니다. 취소는 현재 안전 경계에서 적용되고 이미 커밋된 배치는 유지됩니다.

각 정본 카드의 `재생성`은 새 후보를 만들 뿐 활성 정본을 즉시 바꾸지 않습니다. `수정`도 원본의 복사본만 편집하며 TURN 범위, 원문 digest와 provenance는 잠깁니다. candidate 단계에서는 상태를 미리 쓰거나 영구 상태 preview를 만들지 않습니다. 사용자 작성 후보는 다음 순서로 처리합니다.

1. 수정본을 저장합니다. 본문을 다시 저장하면 이전 상태 처분은 폐기됩니다.
2. `편집 이후 상태 결정 · 필수`에서 `상태 변화 없음` 또는 `상태 보정 작성`을 선택합니다.
3. 상태 보정 작성일 때만 실제 변경 필드가 든 희소 JSON patch를 입력합니다.
4. `상태 결정 저장` readback 뒤 활성화된 `후보 채택`을 누릅니다.
5. 정본 채택과 활성 manifest readback 뒤 `manual_maintained` 또는 `manual_correction_replayed` 영수증이 새 basis에 기록됩니다.

상태 보정 저장과 후보 채택 직전에는 대상 시점 Head를 각각 다시 물질화하고 manifest·correction journal·active worldline·candidate·canonical job이 계산 중 바뀌지 않았는지 확인합니다. ID와 이름이 충돌하거나 별칭이 둘 이상의 인물에 걸리면 자동으로 하나를 고르지 않고 보정을 거부합니다.

재생성 후보는 이 수동 상태 처분 대상이 아니며, 채택 뒤 일반 상태 추적을 실행합니다. 모든 후보는 기존·후보 정본을 비교해 `기존 유지`, `후보 채택`, `나중에 결정` 중 하나를 고릅니다. 파생 상태만 잘못되었다면 correction을 사용할 수 있지만 ID, scope, TURN과 정본 근거는 바꿀 수 없습니다.

`버전 기록`에서는 사용자 재생성·수정으로 남은 비활성 버전을 페이지 단위로 조회하고 다시 후보로 선택하거나 명시적으로 삭제할 수 있습니다. 현재 채팅 원문의 digest가 달라진 버전은 열람할 수 있지만 채택할 수 없습니다. 활성 정본은 삭제할 수 없고, 후보 채택 전에는 manifest, recall catalog와 Current State Head가 변경되지 않습니다.

### Portable 이동·채팅 복사 중 상태 권위

기억 이사, Portable import, 채팅 복사와 RE:TRACE handoff는 target scope의 활성 정본 체인을 기준으로 상태를 다시 계산합니다. source Head는 진단 seed일 뿐 target Head로 그대로 저장하지 않습니다. 공유 archive는 exact member identity와 archive digest가 현재 transfer/import 영수증에 결속된 경우에만 replay합니다.

- `continuityStateAuthority: target_canonical_chain`: target 체인 재구축과 Current Head readback이 완료되었습니다.
- `continuityStateAuthority: none_pending`: 기억·manifest·archive 이동은 내구 완료되었지만 상태 catch-up은 남았습니다. 현재 Head가 없을 수 있으며, 있더라도 새 체인의 권위로 사용하지 않습니다.
- `continuityStateAuthority: not_required`: 상태 추적이 꺼져 있어 Head가 완료 조건이 아닙니다.

따라서 Portable 완료 영수증은 `none_pending`일 때 exact pending rebuild receipt를 읽어 확인하되 Head 존재를 강제하지 않습니다. 이후 catch-up이 끝나 `target_canonical_chain`으로 바뀔 때만 Head semantic readback을 요구합니다.
> Historical helper description: GRADIA/SGA, Planner and InputWriter behavior in this paragraph is retired. Shared memory/state/storage facts remain historical evidence.


Planner, Input Writer와 GRADIA SHADOW/AIDE 실행 중에는 채팅 아래에 실시간 작업창이 나타납니다. 완료 또는 실패한 작업창은 자동으로 사라지지 않으며 `작업 결과 확인`을 펼쳐 단계, 길이, 실패 위치와 보존된 마지막 완성 초안을 확인할 수 있습니다. 전체 기록은 공통 `실행 기록`의 초안 또는 Input Writer 탭에서 다시 확인합니다.
> Historical helper description: GRADIA/SGA, Planner and InputWriter behavior in this paragraph is retired. Shared memory/state/storage facts remain historical evidence.


GRADIA `실행 결과`에서는 Input Writer, SHADOW, Character/World/Plot AIDE, 응답 엔진, 길이 보정을 탭으로 선택할 수 있습니다. 각 탭은 기록이 있을 때 실제 분석, 초안 또는 부분 패치, 적용 Skill·사용 자료, 모델 원문과 시스템/사용자 프롬프트, provider·모델·소요 시간·usage를 표시합니다. 실행하지 않은 단계는 빈 상태로 안전하게 표시됩니다.

## 서버 실행

`PROGRAM/1_서버_실행.bat`를 실행합니다. 처음 실행하면 PROGRAM 안의 `_runtime`에 공식 Node.js 22 포터블 런타임을 설치합니다. 시스템 Node를 쓸 때는 `node:sqlite`를 플래그 없이 제공하는 22.13.0 이상이어야 합니다. DATA 검증 이후 시작 오류는 `DATA/logs/startup-error.log`에도 기록됩니다.

plugin bootstrap에는 별도 key 입력이나 인증 설정이 필요 없습니다. 서버를 실행한 뒤 플러그인의 서버 연결 화면에서 주소와 저장 방식만 확인합니다. 서버는 공식 plugin ID를 namespace와 role에 매핑해 capability token을 발급하며, 이후 요청에서는 token의 plugin ID·namespace·권한 결속을 검증합니다. bootstrap의 plugin ID 자체는 암호학적 신원 증명이 아니므로 서버는 loopback에만 bind합니다. loopback은 같은 기기의 다른 프로세스·사용자·Android 앱을 암호학적으로 배제하지 않으며, 이 서버는 로컬 기기 전체를 신뢰 경계로 삼습니다. 관리도구만 `DATA/runtime-token.txt`를 직접 읽어 backup/restore/stop을 수행합니다.

0.2.19 런처는 기존 `runtime-token.txt`에서 원문을 노출하지 않는 DATA 식별값을 자동 계산하고 실행 중인 서버의 식별값과 대조합니다. 사용자에게 토큰을 입력·복사하도록 요구하지 않으며, 토큰 원문은 health 응답이나 로그에 표시하지 않습니다. 다른 DATA의 Librarian System 또는 다른 프로그램이 같은 포트를 사용하면 서버를 이미 실행 중인 것으로 오인하지 않고 충돌을 알립니다.

## 저장 및 연산은 현재 스코프별 설정

0.2.7부터 저장 방식은 플러그인 전체가 아니라 **현재 열려 있는 캐릭터·채팅 스코프에만 적용**됩니다.

```text
Flashback
  채팅 A → 플러그인 단독
  채팅 B → 서버 단독
  채팅 C → 서버 단독
```

Flashback·HAYAKU·LIBRA·LIA의 `저장 및 연산` 화면에는 현재 스코프의 이름/ID가 표시됩니다. 새 채팅과 아직 명시적으로 설정하지 않은 스코프는 항상 `플러그인 단독`입니다. RE:TRACE는 관리·복구 도구이므로 독립 연산 selector를 갖지 않습니다.

서버 주소는 플러그인 전역 설정입니다. 한 플러그인의 여러 스코프가 같은 Librarian System 서버를 사용합니다. 서버를 사용하는 스코프가 하나라도 남아 있으면 주소를 바꿀 수 없습니다. 주소를 바꾸려면 그 플러그인의 모든 스코프를 먼저 플러그인 단독으로 전환해야 합니다.

## 세 저장 방식

1. **플러그인 단독** — 기본값. 현재 스코프 자료를 RisuAI pluginStorage/로컬 저장소에만 보관하고 결정론적 연산도 로컬에서 수행합니다. 다른 스코프가 서버를 사용 중이어도 이 스코프의 일반 저장·키 열거·Compute 작업은 서버를 호출하지 않습니다.
2. **미러 전환 단계** — 단독 모드 사이의 이동 과정입니다. 기존 정본을 유지하고 목적지 저장·재조회를 검증한 뒤 최종 단독 모드를 기록합니다. 새 설정에서는 목적지로 선택할 수 없습니다.
3. **서버 단독** — 현재 스코프 자료의 영구 정본이 서버 DATA입니다. 연산은 서버를 우선 사용하고 실패하면 로컬로 복귀하지만, 서버가 꺼져 있으면 해당 스코프 메모리 I/O는 fail-closed합니다.

플러그인 전역 설정, provider/API credential, 실제 RisuAI Persona 객체와 공유 archive/index 기반 자료는 채팅 스코프 저장 모드와 별개로 보호됩니다.

연결 테스트, 지금 동기화, 서버→pluginStorage 복원, 서버 데이터 관리처럼 이름에 서버 작업이 명시된 버튼은 플러그인 단독에서도 사용자가 요청한 서버 요청을 수행할 수 있습니다. 자동 시작·일반 메모리 I/O와 이 명시적 관리 경로는 분리됩니다.

## 0.2.6 전역 모드에서 자동 이전

기존 `memory_suite_server_mode` ARG가 `mirror` 또는 `server_only`였던 경우 0.2.7은 최초로 연 **현재 활성 스코프 하나에만** 그 모드를 가져옵니다. 그 뒤 ARG는 `plugin_only`로 되돌리고, 다른 스코프는 기본값인 plugin_only로 시작합니다.

이는 0.2.6의 전역 선택을 모든 과거 채팅에 다시 퍼뜨리지 않기 위한 안전 조치입니다. 서버에 이미 복사된 과거 데이터는 삭제하지 않습니다.

## 현재 스코프만 동기화

`설정 적용`, `지금 동기화`, `서버 → pluginStorage 복구`, `플러그인 스토리지 삭제`는 현재 스코프의 자료만 처리합니다. 다른 채팅·캐릭터 스코프의 모드나 데이터는 변경하지 않습니다.

```text
현재 채팅 B에서 plugin_only → server_only
→ 채팅 B의 manifest/shard/memory/vector만 조사
→ 서버 기준선 생성 및 readback/digest 검증
→ 마지막 보충 동기화
→ namespace 무결성 확인
→ 채팅 B만 server_only 확정
```

공유 기반 자료는 다른 스코프의 소유 자료와 구분됩니다. 일반 동기화·삭제 sweep은 현재 스코프만 처리하지만, 서버→pluginStorage 복원은 owner resolver가 현재 스코프의 의존 자료로 분류한 `shared` 항목도 함께 복원·검증합니다. 플러그인 전역 `global` 설정과 다른 스코프 소유 자료는 건드리지 않습니다.

## 진행 상태

장시간 작업 카드에는 현재 단계, 처리 건수/전체 건수, 처리 용량, 실제 전송·복구 용량, 경과 시간, 마지막 활동, 재시도/실패, 현재 처리 key를 표시합니다. 패널을 닫아도 job은 계속되고 다시 열면 같은 job을 표시합니다. 완료·실패 카드는 자동으로 사라지지 않으며 검증 결과와 다음 조치를 확인한 뒤 직접 닫을 수 있습니다.

초기 동기화가 완료되기 전에는 기존 저장 모드가 계속 정본입니다. 서버가 끊기면 작업은 대기/재시도하며, 이미 서버와 일치하는 값은 다시 전송하지 않습니다.

## 서버가 꺼진 경우

- plugin_only: 기존처럼 정상 작동하며 서버 요청을 하지 않습니다.
- 기존 mirror: 전환 미완료 상태로 표시됩니다. 단독 목적지를 선택하면 보존·복원·재조회 검증 후 최종 모드를 확정합니다.
- server_only: GUI·서버 연결 페이지·훅은 그대로 유지됩니다. 해당 스코프 메모리 읽기/쓰기는 서버 연결 오류로 fail-closed하며 pluginStorage로 몰래 fallback하지 않습니다. 원래 RisuAI 채팅 요청 자체는 가능한 범위에서 계속 진행합니다.

## 삭제와 복구

- `서버 → pluginStorage 복구`: 현재 스코프 서버 자료와 필요한 shared 의존 자료를 로컬에 복원합니다. 서버 후보, 공간별 coverage, 로컬 readback 및 owner 의미 검증을 모두 통과해야 성공합니다.
- `플러그인 스토리지 삭제`: 현재 스코프 자료가 서버에 완전히 보존되었는지 검증한 뒤 두 단계 확인으로 삭제합니다. 다른 스코프와 routing registry는 보존합니다.

복원 검증이 실패하면 화면에 실패 사유를 남기고 현재 스코프는 `server_only`를 유지합니다. 이때 `recovery_required` 잠금이 저장되어 plugin-only/mirror 전환과 로컬 우선 동기화를 차단합니다. 실패 원인을 해결하고 같은 서버 복원을 다시 실행해 검증을 통과하면 잠금이 해제됩니다.

API key, credential, 전역 설정, 실제 RisuAI Persona, 공유 기반 자료는 현재 스코프 삭제 대상이 아닙니다.

## RE:TRACE 1.9.66 GUI 작업 공간

RE:TRACE를 열면 `개요`가 먼저 표시됩니다. 개요는 현재 채팅의 LIBRA·Flashback·HAYAKU 요약 수, 네 Owner의 실제 IPC 저장 상태, 공통 승계 Gate와 플러그인 호환 계약을 함께 보여 줍니다. 임의의 서버 성공 수치나 샘플 데이터는 사용하지 않으며, 서버 스코프 전체 목록도 자동으로 읽지 않습니다. 서버 전체 대조는 사용자가 `서버 데이터` 탭을 열거나 새로고침했을 때만 시작합니다.

사이드바는 `상태 / 연속성 / 데이터 / 서버 / 진단`으로 나뉩니다. 탭을 바꿔도 셸 전체를 다시 만들지 않아 기존 패널, 스크롤과 포커스가 유지됩니다. 키보드에서는 방향키로 앞뒤 탭을 이동하고 Home/End로 처음·마지막 탭으로 이동할 수 있습니다. 좁은 화면에서는 아이콘 전용 세로 레일 대신 이름이 보이는 가로 스크롤 탐색으로 바뀝니다.

`연결 진단`은 Owner IPC 등록·대기 상태, 호환성, 저장 Gate와 서버 스코프 스캔 여부만 표시합니다. LIA 콘텐츠 뷰어와 RE:TRACE 자체 provider/저장 모드 설정은 만들지 않았습니다. 정제된 디버그 내보내기는 자격 증명을 제거하고 대화·페르소나·스코프 식별자를 해시하며, 기억 원문과 긴 본문을 제외합니다.

## RE:TRACE 서버 데이터 관리

RE:TRACE의 서버 데이터 페이지는 활성·승계 조상·고아 후보·확인 불가·보존 스코프를 표시합니다. 활성 Flashback/HAYAKU/LIBRA/LIA/RE:TRACE 스코프만 인식합니다. 지원 서버에서는 batch 조회를 우선 사용하며, 서버 버전·프로토콜·필수 capability 불일치를 별도로 표시합니다. 채팅이 없어져도 서버 기억은 자동 삭제되지 않으며, owner의 현재 스코프 복원·plugin_only 전환 증명과 삭제 직전 백업을 거쳐야 삭제됩니다.

RE:TRACE의 저장 상태 화면은 Flashback, HAYAKU, LIBRA, LIA 네 owner의 현재 스코프·저장 모드·연결·복구 잠금을 읽기 전용 현황판으로 표시합니다. RE:TRACE 자체 분석 복구 journal이나 저장 모드 설정은 더 이상 제공하지 않습니다. 과거 RE:TRACE 콜드스타트·증분 캡슐과 checkpoint는 HAYAKU 이관 및 내구성 readback을 위한 레거시 호환 데이터로만 읽습니다. RE:TRACE의 독립 기억 뷰어, 패킷 삭제·턴 이동, HAYAKU 원장 백업·목록 API와 해당 잔여 구현은 제거되었습니다. HAYAKU JSON 백업·복원과 실제 레거시 채택은 HAYAKU에서만 수행합니다. 기존 RE:TRACE 백업·카탈로그·캡슐 데이터는 삭제하지 않으며, 캡슐은 승계에 필요한 읽기 호환만 유지하고 기존 자료의 서버 관제·복원 검증은 보존합니다. 다음 세션 승계는 LIBRA·HAYAKU·Flashback이 각각 선택한 저장 위치를 유지합니다. 플러그인 단독·서버 단독을 섞어 사용할 수 있으며, 서버를 쓰는 플러그인만 해당 서버 무결성을 확인합니다. LIA는 로컬 승계에 참여하고, 각 대상 스코프가 자기 저장 모드를 readback하기 전에는 adoption하지 않습니다. RE:TRACE 연결은 서버 관제 전용이며 자체 기억 저장·자동 업로드·동기화는 실행하지 않습니다. 기존 LIA·RE:TRACE 서버 자료는 읽기 호환과 명시적 관제 백업·복원 대상으로 보존하고, 새 서버는 두 플러그인의 빈 저장 DB를 생성하지 않습니다.

## DATA 백업

1. `PROGRAM/2_서버_종료.bat`를 실행합니다.
2. `DATA` 폴더를 통째로 복사합니다.

활성 5종의 SQLite DB, scope catalog, 삭제 전 복구점, 설정, 로그, 관리용 runtime token과 마이그레이션 기록이 함께 보존됩니다. 과거 gradia.sqlite가 DATA에 남아 있어도 0.2.12는 이를 관리 대상으로 열지 않습니다. Librarian System 복원 도구는 선택한 namespace의 DB와 scope catalog 항목을 같은 백업 시점으로 되돌립니다.

자동 백업은 변경된 데이터가 있을 때만 실행합니다. change-settled는 마지막 변경 후 45초를 기다리며, 전체 snapshot이 지나치게 자주 반복되지 않도록 기본 10분 cooldown을 둡니다. 6시간 scheduled backup과 dirty 정상 종료 backup은 cooldown을 무시합니다. 보존은 최신 12개 + 일별 7개 + 주별 4개 세대로 유지합니다. snapshot·integrity·SHA 계산은 worker에서 수행하며 그동안 health/진단 요청은 응답하고 데이터 변경 요청만 maintenance 상태로 잠시 거절합니다. 새 snapshot의 예상 크기보다 디스크 여유가 부족하면 기존 정상 백업을 지우지 않고 새 백업을 중단합니다.

`관리도구/백업_건강도_검사.bat`는 저장된 backup의 manifest, SHA-256, SQLite integrity와 scope catalog를 미리 검증합니다. `복원_계획_미리보기.bat`로 복원 대상과 backup 건강도를 먼저 확인한 뒤 일반 복원을 실행할 수 있습니다.

SQLite 손상으로 정상 서버가 시작되지 않으면 0.2.12는 **Recovery Safe Mode**로 기동합니다. 이 모드에서는 plugin KV/동기화가 차단되고 백업 목록·scrub·복원만 가능합니다. 서버 기동 자체가 어려운 경우 `관리도구/복구_전용_오프라인_복원.bat`를 사용합니다. 복구 전 현재 raw DB와 scope catalog는 `DATA/backups/recovery-quarantine/`에 보존됩니다. 복원 완료 후 서버를 다시 시작하십시오.


## 플러그인 디버그 로그와 서버 진단

각 플러그인의 기존 디버그 JSON 내보내기를 실행하면 `memorySuite` 영역에 다음이 함께 들어갑니다.

- 서버 연결 가능 여부
- 현재 스코프 저장 모드
- 서버/프로토콜 버전
- 해당 namespace SQLite 무결성 및 record 수
- 현재 스코프와 관련된 최근 서버 작업 events
- 서버 진단 로그 순환 상태
- 서버가 꺼진 경우 연결 오류와 마지막 SDK 상태

일반 플러그인은 자기 namespace와 현재 스코프의 구조화된 진단만 받습니다. suite-global process text log는 다른 owner 정보가 섞일 수 있으므로 일반 플러그인에는 제공하지 않습니다.

RE:TRACE 디버그 export는 Flashback, HAYAKU, LIBRA, LIA, RE:TRACE 다섯 활성 namespace의 전체 무결성과 최근 server events를 포함하며, manager 권한으로 `startup.log`, `startup-error.log`, `server.log`의 제한된 최근 부분도 받습니다. text log는 파일 전체가 아니라 최근 부분만 포함하고 Bearer/API key/credential 표현을 `[REDACTED]`로 바꿉니다. 서버 진단에는 메모리 본문, 실제 storage value, 원본 storage key 또는 인증 토큰을 포함하지 않습니다.

## LIBRA 2.1.0 · Classic Canonical Provenance Rescue

Classic에서 현재 상태·관계·지식·위치 등의 질의가 들어오면, 사용 가능한 Current State Head의 **값**이 아니라 그 필드가 가리키는 정확한 Canonical Memory provenance를 보조 후보로 사용할 수 있습니다. 최대 2개 정본 ref만 구제되며, 최종 프롬프트에는 기존 Canonical Memory 발췌만 들어갑니다. 과거 전용 질의와 `ready`가 아닌 상태 도메인은 이 경로를 사용하지 않습니다. 별도 설정이나 데이터 마이그레이션은 필요하지 않습니다.
