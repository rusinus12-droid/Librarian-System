# 플롯 에이데 전면 교체 관찰 기록

이 문서는 기능 확장 전에 기존 실행을 재구성한 기록이다. 기준은 제공된 `gradia-debug-2026-10-30.json`, 버전 0.28.2, 실행 `sga-mvuk929p-t896vo6`이다. 파일 SHA-256은 `0360e2dafad65ff4c03db4d20f565a65ca2927d3c981f9c950d3cbb5390811e4`이다. 민감한 요청·장면 본문은 재수록하지 않는다. 기계적으로 대조한 수치는 [증거 JSON](evidence/GRADIA_PLOT_AIDE_OBSERVATION_20261030.json)에 있다.

## 실제로 일어난 일

**플롯 에이데가 초안 전체를 교체했다. 다만 별도 전면 재작성 작업을 호출한 것이 아니라, 기존 부분 패치 네 개를 조합한 결과였다.**

시간은 `stageTrace[*].elapsedMs` 기준이다. 전체 파이프라인은 42.271초였다. 로그 시각은 2026-10-30 14:57:42.965–14:58:25.236 KST이다.

플롯의 관점은 문장 몇 개의 품질보다 **현재 산출물이 이번 턴의 장면 역할을 수행하는가**에 있었다. 인물·세계 에이데는 자신의 교정 대상이 없다는 이유로 유지했고, 플롯은 장면 기능 전체의 결손을 교체 이유로 삼았다. 이 판단 범위의 차이는 관찰된 사실이다. 다른 에이데가 전면 교체 능력을 갖지 못했다는 뜻은 아니다.

## 호출·적용·전달 경로

`같은 턴 초안 → aidePatchPrompt → 패치 JSON → normalizeAidePatchResult → applyDraftPatchOperations → runAidePatchStage → 최종 초안 → buildNovelFinalOverlay → RisuAI 요청에 주입`

실행 모드는 `lightweight`, 작성 모드는 `novel`이었다. 플롯 결과의 `analysisMode`는 `single_call_serial_patch`였다. 별도 분석·재작성 응답 필드는 비어 있다. 논리 호출은 SHADOW와 세 에이데의 총 4회이고, 물리 요청은 5회다. 플롯 패치 요청에서 `length_expansion` 한 번이 있었으며, 이를 별도 전면 재작성 호출로 해석하면 안 된다. 최종 플롯 응답의 제공자 보고 토큰은 입력 13,251, 출력 4,203이다. JSON 형식 복구는 사용하지 않았다(`repairedJson: false`).

플롯의 `patchMeta`는 요청 4개·적용 4개·건너뜀 0개, 블록 4→1을 기록한다. 입력 초안 해시는 `0e4b36fb`, 출력 해시는 `bf582b30`이다. 인물·세계 에이데의 입력과 출력 해시는 모두 `0e4b36fb`다. 첫 세 단계 초안이 문자 단위로 동일한 것도 확인했다.

적용 직후 `draft.rp_text`는 문단 구분자로 인한 끝의 개행을 포함해 947자다. 공백 정리 후 945자가 `finalDraft`가 되며, 첫 교체 연산의 새 본문과 정확히 일치한다. 그 945자 전체가 `lastInjection` 안에 존재하고 `fullDraftPreserved: true`다.

**확인된 전달 종점은 최종 초안과 주입문이다.** `outputMode: draft_guided`, `engineCandidateAdopted: false`이므로 플롯 결과를 호스트 응답으로 직접 복사한 실행은 아니다. 이후 일반 RisuAI 응답이 그 초안을 얼마나 따랐는지, 실제 표시된 본문이 동일한지는 이 로그만으로 확정할 수 없다. 기존 메시지 61개를 보존하고 주입 메시지 1개를 추가했다는 전송 검사는 통과했다.

## 발견의 의미와 주의점

1. 당시 공통 프롬프트는 최소 부분 편집을 요구하고 전문 재생성을 금지했다. 그 문구가 실제 플롯 systemPrompt에 있는 것도 확인했다. 그러나 엔진은 여러 부분 연산의 합이 전문 교체가 되는 것을 별도로 구분하지 않았다. 결과 분류도 `serial_partial_patch`였다.
2. 이번 최초 산출물은 일반적인 형식 오류가 아니라 안전상 거절이었다. 따라서 이 실행을 그대로 범용 품질 복구의 정답 표본으로 삼으면 안 된다. 일반 오류를 고치는 능력과 안전상 거절을 덮어쓰는 동작은 구분해야 한다.
3. `ok: true`는 내용의 적절성·완성도를 독립적으로 입증하지 않는다. SHADOW 계보 검사는 `content_validation_disabled`, 플롯은 `serial_patch_applied`였다. 최종 commitment 검사는 성공했지만 잠금 조건 수가 0이었다.
4. 외부 기억은 `LIB_READ_NATIVE_ID_UNAVAILABLE`로 읽지 못했다. 이번 교체가 LIBRA·HAYAKU·Flashback 기억 활용 덕분이었다고 해석할 근거가 없다.

## 무해한 예제로 재현한 엔진 성질

실제 플러그인의 공개 debug 진입점에 네 문단짜리 편집 상태 안내문을 넣고, 무해한 서고 장면으로 교체하는 실험을 했다. 제공자 호출 없이 교체 1개·삭제 3개가 적용되어 한 문단이 됐다. 이는 기존 편집 엔진의 표현력을 입증하며 실제 모델의 판단 품질을 검증하는 시험은 아니다.

같은 예제에서 첫 교체의 기대 해시만 틀리게 하면, 교체는 건너뛰지만 삭제 3개는 적용되고 결과가 비어 있지 않아 구조상 성공한다. **전문 교체 기능은 기존 부분 편집을 그대로 이용하기보다, 원본 전체에 결합된 원자적 작업으로 검증해야 한다.** 실제 사용자 장면이나 거절 본문으로 이 재현을 실행하지 않았다.

## 후속 패치의 수용 기준

- 모든 에이데가 이번 턴 초안 전체가 사용할 수 없다고 판단했을 때 명시적인 전문 교체를 제안할 수 있어야 한다. 기본값은 기존 도메인별 부분 교정이다.
- 전문 교체는 원본 전체 해시에 결합하고 다른 편집과 섞지 않는다. 검증 실패 시 일부 삭제만 적용하지 않는다.
- 안전상 거절은 일반 오류 복구의 대상으로 삼지 않는다. 기존 부분 패치 조합도 같은 경계를 지켜야 한다.
- 현재 사용자 결정·응답 경계·이전 단계의 승인된 제약을 보존한다. 비어 있는 본문·편집 설명·잘못된 해시·불완전한 적용을 정상 교체로 게시하지 않는다.
- 같은 에이데 호출의 결과로 처리하고, 전문 교체를 위해 추가 모델 호출이나 자동 재시도를 새로 만들지 않는다. 기존 길이 확장 호출은 따로 기록한다.
- 결과 화면과 진단 자료에서 부분 교정과 전문 교체를 구분한다. 최종 초안의 주입과 실제 호스트 응답의 성립도 별개의 검증 대상으로 둔다.

당시 설치 파일의 소스 해시는 디버그에 없다. 따라서 설치 파일과 현재 로컬 소스의 바이트 동일성은 미검증이다. 실행 기록의 판정은 원본 JSON의 연산·해시·호출·전달 메타데이터에 근거하며, 코드 경로 설명은 로컬 기준 커밋 `3877f4c`의 `PROGRAM/plugins/GRADIA.js`와 대조했다. 이 문서 작성·재현 단계에서는 제품 동작을 바꾸지 않았다.
