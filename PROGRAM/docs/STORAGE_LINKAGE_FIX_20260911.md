# 저장 연동 수정 — 2026-09-11

대상: 현재 `PROGRAM`의 0.3.44 기반 로컬 수정본. 운영 DATA, 설치된 RisuAI 플러그인, 외부 공급자 설정은 변경하지 않았다. 기존 표시 버전은 유지하며 수정 파일은 manifest/checksum으로 식별한다.

## 반영 사항

- 공통 Storage SDK의 스코프 설정은 pluginStorage 또는 기기 저장소 중 적어도 한 곳에서 성공 반환과 정확한 재조회가 확인되어야 저장 성공으로 처리한다. 실패한 모드 변경은 캐시를 확정하지 않고 원래 물리 기록을 다시 읽는다.
- 모드 설정 저장·강제 재조회 때 기존 경로 캐시도 무효화한다. 이전 plugin_only 경로가 남아 로컬 기록과 서버 조건부 검사가 서로 다른 자료를 보던 실제 모드 전환 오류를 수정했다.
- 같은 인스턴스의 레지스트리 저장은 순서대로 실행하여 시작 시 동시 초기화가 서로의 재조회 값을 바꾸지 않도록 했다. 대기 중 다른 스코프가 저장한 설정도 최신 물리 기록과 병합하여 보존한다.
- 플러그인에만 추가되어 있던 Storage 진단 호출을 공통 원본으로 통합했다. 내장 SDK와 원본의 줄바꿈을 통일하고 동기화했다. 플러그인 고유 진단·GUI 변경은 유지했다.
- LIBRA의 mirror 거부 조건과 조건부 커밋 SDK의 server_only 전용 조건을 수정했다. 미러에서도 정본·상태·교정·임베딩은 동일한 서버 조건부 커밋 경로를 사용한다.
- LIBRA 미러의 스코프 기억은 서버를 정본으로 읽고 로컬 복사본을 재조회 검증한다. 오래된 로컬 상태를 읽기·수동 동기화 중 서버에 덮어쓰지 않는다. 서버에 없는 기존 로컬 자료의 최초 시딩은 충돌 검사와 조건부 생성으로 보호한다.
- 조건부 커밋의 영수증에 로컬 복사 결과를 별도로 기록한다. 로컬 저장이 실패해도 성공한 서버 커밋을 새 작업으로 재실행하지 않는다. 후속 읽기·수동 동기화로 로컬 복사본을 복구한다.
- 로컬에 이미 있던 v4 기억을 서버 저장으로 전환한 경우, manifest와 상태의 조건부 비교 아래 서버 활성화 기록을 생성하여 후속 분석을 허용한다. 상태 조회 자체는 이 기록을 생성하지 않는다.
- 미러에서 플러그인 단독으로 전환하기 전에 서버 자료 전체를 로컬로 복원·검증한다. 복원 검증기가 내부 Source Evidence 생성 함수에 접근하지 못하던 참조 오류도 수정했다.
- 루트 README의 서버 버전과 배포 안내의 LIBRA/HAYAKU/Flashback 구성 버전을 실제 파일에 맞췄다.

## 저장과 계산의 의미

LIBRA의 mirror는 서버 SQLite 정본과 로컬 복사본을 함께 유지한다. 두 저장소 전체를 하나의 원자적 트랜잭션이라고 주장하지 않는다. 서버 커밋 후 로컬 복사가 실패하면 `server_durable_mirror_pending`으로 구분한다. 불완전한 로컬 스냅샷을 정본으로 채택하지 않으므로 서버 장애 중에는 새 정본 기록을 보류한다. Flashback 원문도 기존부터 서버 정본 정책을 사용한다.

서버 연산 실패 시 로컬 연산으로 복귀하는 Compute 정책과 정본 저장 성공 조건은 별개다. HAYAKU/LIA의 일반 미러 경로는 기존 local-ahead 동작을 유지한다.

## 추가로 확인한 연동 제한

아래 BM25F 불일치는 후속 `ENGINE_CONSISTENCY_FIX_20260911.md`의 공통 토큰화·fingerprint 수정으로 해결했다. 아래 문단은 발견 당시 근거이며, 분기·승계 등 기능 제한과 구별한다.

**추가 결함: LIBRA 로컬·서버 BM25F 검색 불일치.** 플러그인의 `tokenStream`은 연속된 한글 구간별로 토큰을 만들지만 서버 `compute/registry.cjs`의 `libraTokenStream`은 한글 이외 문자를 제거한 뒤 단어 경계를 넘는 토큰도 만든다. 같은 알고리즘 fingerprint를 사용하므로 연결 검사가 이 차이를 검출하지 못한다. 기존 pilot 및 실제 HTTP 연동 시험에서 동일 입력의 점수 불일치를 재현했고, pilot에서는 최고점 문서도 바뀐다. 수정 전 플러그인으로도 같은 실패가 난다. 이번 저장 수정과 별도로 서버 커널·식별값·검증 계약을 함께 정리해야 한다.

아래는 기존 구현에 남아 있는 별도 기능 제한이다. 이번 수정에서 보호 조건만 삭제하여 지원한다고 표시하지 않았다.

1. **LIBRA 서버 모드의 분기·승계 제한**: archiveRef, inheritedMemories, nativeChatCopy, main 이외 세계선, rollback view가 서버 writer 경계에서 제한된다. 원본 분기·승계 자료를 서버 트랜잭션으로 옮기는 구현이 필요하다.
2. **LIBRA 구형 기억·후보 관리 제한**: v3가 섞인 서버 스코프, 선택 구형 기억 재분석, 일부 후보 채택·변형 삭제·스코프 삭제·identity split·retention 수집은 plugin_only 전용 조건이 남는다. 정상 v4 미러의 일반 분석 지원과 구별해야 한다.
3. **RE:TRACE 저장 모드 일치 요구**: 인계에 참여하는 owner들의 저장 모드가 같아야 다음 세션 인계가 열린다. 서로 다른 모드로 각 플러그인이 작동해도 전체 인계는 `owner_storage_mode_mismatch`로 차단될 수 있다.
4. **원자성 범위**: 조건부 일괄 커밋은 단일 namespace SQLite에 한정되며 64개 항목/4 MiB 상한이 있다. Suite 전체 owner 간 원자적 커밋과 분산 writer의 의미 충돌 해결을 제공하지 않는다.
